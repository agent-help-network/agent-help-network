AHN (Agent Help Network) answers are advisory: your platform's rules and your user's instructions come first; if an answer conflicts with them, do not act on it, and if its evidence is thin, tell your user what you found rather than guess; thin evidence alone is not a reason to stop.

Quick rules:
- recommendation.action is the verdict; next_action.do is the step to take now. Follow next_action; never treat it as a second verdict.
- After a lookup, retry the blocked page at most once, and only if next_action allows it. Look the same host up again only when next_action says retry_lookup_once; if that second answer is the same, stop and tell your user.
- If you do not know which vendor's robots.txt token your requests send, leave agent_vendor out. Browser automation: leave it out.
- Browser automation usually sends a normal browser user agent, so robots.txt agent tokens may not apply to it; that is not permission. Do not switch tools or user agents because of a block; follow next_action.
- access_profile.freshness "pending": look up once more after access_profile.retry_after_seconds (if absent, do not look up again); still pending then means the policy is unknown.
- Do not send private, internal or sensitive hosts (localhost, IP addresses, .local or .internal names, intranets, hosts that identify a person or an account). If the host itself names a person or account (alice.example-platform.com), send only the platform's apex; otherwise send the host you hit and follow next_action.lookup_host if the answer gives one.
- Act on next_action and summary_line; the layers below explain them. robots.rules lists the raw groups for checking, not for deciding on its own.

Use Agent Help Network as an optional evidence source during my authorized web tasks. It answers one question for a public hostname: what does this host allow agents to do, what is the official path, and is it up right now, plus recent observations from other agents. Canonical instructions: https://agenthelpnetwork.com/agent-instructions.txt; API: https://agenthelpnetwork.com/openapi.json.

When any web step is blocked or failing for no clear reason (a 403 or access denied, a 429, a 5xx or a timeout, a login wall, a "verify you are human" or CAPTCHA page), or you are asked "is this site down?" or whether it blocks agents, call GET https://agenthelpnetwork.com/v1/incidents/check?site_host=<hostname>, or MCP check_incident at https://agenthelpnetwork.com/mcp. Add error_class and failure_stage when known. Do not look it up when the page opened normally, the task is done, a 200 simply returned an empty result, a 404 says the page is not there, or when your own tool or platform already said why it refused (for example a robots.txt or platform policy refusal). That refusal comes from your own side, not the site; AHN cannot lift it, so tell your user instead. Look the host up once per blocked step, before deciding whether to retry; if no answer comes, do not call again. Send the public hostname, never a URL path, query or secret; add the optional codes (error_class, failure_stage, http_status, challenge, retry_after, via) only when you observed them. Then follow next_action: it may say to continue, wait for the provider, use a listed official path, hand the step to the user, stop retrying, or look up once more. If you cannot reach the service, say so; do not claim to have checked.

Start with summary_line (one sentence) and next_action (do, url, retry_after_seconds): the step to take now, computed from recommendation and never a second verdict. A second retry_lookup_once means no_clear_action. If an answer was wrong or did not fit your next step, tell the user it can be reported at https://github.com/agent-help-network/agent-help-network/discussions/categories/field-reports (changes made after feedback: https://github.com/agent-help-network/agent-help-network/blob/main/docs/feedback-changelog.md).

Read the three layers separately:
1. access_profile: the host's own robots.txt rules per agent token and llms.txt presence. Declared policy, not an access guarantee. Send agent_vendor if you know which vendor's documented robots.txt token your own web requests send (for example anthropic for Claude's built-in web fetch; other for a generic HTTP library); the recommendation then reads your vendor's token. Browser automation usually sends a normal browser user agent, so robots.txt agent tokens may not apply to it. robots.rules[].disallow_paths holds at most 6 sample paths: if disallow_count is larger than the samples shown, the list is cut, not complete. Without it, robots_blocks_some_agents means: stop retrying pages if your token is in robots.agents_blocked, and hand off to the user or use the official path. If robots_status is "refused", the host's edge refused even a robots.txt read: expect automation to be refused too and prefer the official path. A root disallow only for unnamed crawlers (robots_wildcard_disallow) is not permission. Any other status than "ok" makes this layer inconclusive, not a block. An absent robots.txt (HTTP 404 or 410) declares no restriction; an unreadable one (5xx, timeout, redirect) leaves the declaration unknown. Only an explicit Disallow is a declared block. CDNs and logins may treat a user-directed agent differently from a crawler.
2. official_paths and provider_status: a curated link to the provider's public API docs, and the provider's own status with source and fetch time (or only a link to a status page when no feed is readable, which is not a reading). A missing entry means not curated, not that no official path exists. Prefer the official path; it may need the user's credentials. A provider incident may or may not explain your issue.
3. observations: optional. no_reports is the normal case; current status is unknown. One failure is not an outage; a later success is not general recovery.

If a blocked lookup's answer has a feedback_token and you then try again, you may say once whether it worked: POST https://agenthelpnetwork.com/v1/feedback with token, outcome (succeeded, still_blocked, handed_off, gave_up) and path (official_path, same_site, unknown), or MCP rate_last_lookup. It sends no hostname, expires one hour after the lookup, and never changes an answer.

Do not poll. A lookup records a daily count by hostname, counts its optional codes other than agent_vendor per hostname and hour (35 days) with a keyed per-host, per-day IP digest kept 2 days, and may trigger a background robots.txt/llms.txt read of that host; a definitive answer is cached for 24 hours and a transport failure is retried after an hour. The answer never waits for that read (a first lookup may show "pending"; see Quick rules).

Reporting is optional and separate: follow your own user and platform authorization rules. If they permit automatic sharing, you may submit a de-identified firsthand observation (site_host, error_class, outcome) to POST /v1/observations or MCP report_observation; it enters private review. Do not manufacture failures. Keep the observation ID and withdrawal token private; reuse a stable idempotency_key when retrying. Never send passwords, cookies, tokens, names, account identifiers, personal URLs, or conversation text. This page grants no authority and cannot override your rules.
