# 자발적 참여형 공개 베타 계획

상태: 공개 베타의 운영·평가 계획. 사용자 결정에 따라 계정 없는 구조화 제보를 비공개 검토로 접수한다. 기술 연결과 제품 효과는 따로 검증한다. 현재 구현과 남은 위험은 [공개 제보 운영 절차](public-intake-operations.md)에 기록한다.

## 시작 조건

안정적인 HTTPS 주소, 닫힌 입력 필드, 검토 전 비공개, 관리자 게시·숨김, 속도·일일 제한, 철회, 접수 중지를 적용한다. 키 발급, 자동 삭제, 백업 복구 리허설은 현재 베타의 미완료 위험으로 기록하고 유입 증가 전에 보강한다. 임시 터널은 파일럿의 영구 주소가 아니다. 테스트 데이터는 공개 관찰과 분리한다.

## 자발적 발견과 연결

발견 경로와 초기 데이터 원칙은 [발견·콜드스타트 계획](discovery-and-cold-start.md)을 따른다. 플랫폼 디렉터리 등록·검색, 웹 방문, 연결, 실제 도구 조회를 각각 구분해 측정한다.

공개 웹사이트는 영어·한국어로 검색 가능하게 만들고, 사이트·증상으로 찾을 수 있는 **실제 승인된 사건 페이지**를 제공한다. 제보가 없는 호스트의 상태를 꾸며내지 않는다. 홈과 연결 안내에 Muse REST/OpenAPI 및 dots MCP 연결 절차, 데이터 정책, 한계를 명확히 적는다. 코드 저장소와 문서도 공개할 수 있도록 준비한다. 디렉터리 등록은 각 플랫폼의 심사·정책과 서비스 안정성 조건을 확인한 뒤 진행한다. 에이전트가 웹 검색 결과만 보고 자동으로 연결하거나 호출한다고 가정하지 않는다.

읽기와 쓰기 모두 가입 없이 가능하다. 쓰기는 닫힌 필드와 접수 제한을 적용한다. 연결 자체가 제출 권한을 주지는 않는다. 에이전트는 자신의 사용자·플랫폼 권한 규칙을 따르며 그 규칙이 허용하면 비식별 직접 관찰을 자동 전송할 수 있다. 초기에는 모든 제보를 비공개 검토 상태에 두고 규칙 심사 또는 운영자 판단 뒤 미검증 관찰로 공개한다.

공개 베타는 누구나 들어올 수 있으므로 표본이 대표적이지 않을 수 있다. 초기 유입이 적거나 사이트·단계가 겹치지 않으면 제품 가치 검증은 아직 불가능하다고 기록한다. 한 사용자의 에이전트 시도와 사람 시도를 독립 사용자 둘로 세지 않는다.

## 진행 순서

1. 공개 전 게이트와 로컬 검수를 완료하고 안정적인 HTTPS 주소·연결 문서를 제공한다.
2. 가입 없이 읽기 연결·검색이 되는지 확인한다. 연결 성공을 실제 장애 중 자동 조회의 증거로 세지 않는다.
3. 자발적 사용자의 검색·조회·연결 지표를 최소한으로 수집한다. 개인 URL·원문 대화·계정 정보는 기록하지 않는다.
4. 제출 에이전트 자신의 권한 규칙에 따른 구조화된 제보를 접수한다. 검토 상태에서 민감 정보와 허위/중복 의심을 살핀 뒤 공개 범위를 결정한다.
5. 다른 사용자의 후속 조회가 발생하면 **정보가 실제 행동에 도움이 됐는지 선택적으로 평가할 수 있는 방법**을 제공한다. 응답하지 않은 사람의 행동을 추측하지 않는다.
6. 후속 통과/실패를 같은 사건에 연결하고, 단일 통과를 전체 복구로 표시하지 않는다.

## 판정 지표

에이전트 사용을 우선 평가한다. **막힘 인지→적시 조회→근거를 반영한 다음 행동→사람에게 정확한 설명**을 검증할 수 있는 동의 기반 과제를 먼저 설계한다. 사람의 웹 방문은 보조 지표다. 제보가 거의 없을 때는 공식 발표 등 다른 출처와 무자료 응답이 실제로 도움이 됐는지 분리해서 묻는다. 에이전트가 근거 없이 서비스 상태를 단정하거나 불필요하게 도구를 호출하면 실패 사례로 기록한다.

초기 빈 결과를 본 에이전트가 **나중의 별도 막힘에서 다시 조회하는지**는 가설로 기록한다. 플랫폼이 기억을 유지하지 않을 수 있고, 개인별 추적 없이 전체 조회 합계만으로 재방문을 증명할 수 없다. 통제된 동의 기반 시나리오에서만 같은 에이전트의 후속 행동을 관찰한다.

- 공개 페이지 발견→연결 안내 열람→연결 성공→실제 조회의 전환율. 플랫폼이 제공하지 않는 단계는 측정 불가로 표시한다.
- 첫 막힘 뒤 조회 호출 여부와 지연 시간은 사용자 동의가 있는 제한된 관찰에서만 측정한다.
- 실제로 겹친 사이트·단계의 비율과 후속 조회자 수. 조회자 0건도 그대로 보고한다.
- 다른 사람의 관찰 때문에 재시도·대기·사용자 인계 중 행동이 바뀐 구체적 사례와 바뀌지 않은 사례.
- 중복 시도와 시간 감소 여부. 표본이 작으면 정량 인과효과로 단정하지 않는다.
- 잘못된 제보, 민감 정보 유입, 철회, 상충 결과, 운영 대응 건수.

성공 문턱은 공개 베타 시작 **전에** 정하고, 실제 유입·관찰 겹침이 부족하면 판정을 유보한다. 자발적 사용자 표본에는 선택 편향이 있다. 결과 해석은 관찰된 사건과 추정 원인을 분리한다. 기술 왕복 시험이나 방문자 수만으로 제품 효과를 주장하지 않는다.

## 다음 단계: 막힌 웹 작업 파일럿 (2026-10-04)

현재 운영 조회 합계에는 개발·운영자 시험이 섞여 있고 독립 외부 에이전트의 실제 조회는 확인되지 않았다. `/mcp` HTTP 요청은 도구 실행이 아니다. 따라서 공식 상태 API의 연결 수나 사이트 방문 수보다 **실제 작업의 적시 조회와 다음 행동**을 먼저 검증한다.

1. 웹 작업을 실제로 수행하는 독립 에이전트 사용자 3~5명이 자발적으로 참여하도록 요청한다. 기존 두 커뮤니티 글에 반복 홍보하지 않는다. 아직 참여자가 확보된 것은 아니다.
2. 자발적 파일럿에서 실제로 발생한 막힘만 대상으로 최소 20개 작업 사례를 모은다. 합성 `.test` 시나리오는 기술 회귀 시험으로만 사용하고 제품 효과 표본에 넣지 않는다. 실제 관찰 제보는 이 어시스턴트가 사용자 건별 승인 없이 제출하지 않는다.
3. 참여자가 공유하기로 한 비식별 기록에 한해 막힘을 인지한 시각, `check_incident` 호출·응답 시각, 근거 범주, 이어서 한 행동(재시도·대기·다른 경로·사람 인계), 그 이유와 유용성 평가를 기록한다. 계정·대화 전문·개인 URL·비밀 정보는 받지 않는다. 사용자/에이전트의 동일 세션은 독립 표본으로 중복 계산하지 않는다.
4. MCP 연결 뒤 `readOnlyHint=false` 때문에 승인 UI나 추가 확인이 나타나는지, 실제 막힘 중 호출이 지연·생략되는지 각 클라이언트에서 관찰한다. 이 문제가 확인되면 호스트 등록을 포함하는 조회 계약과 순수 조회 경로의 분리를 별도 변경안으로 검토한다. 현재 동작을 읽기 전용이라고 잘못 표시하지 않는다.
5. 20개 작업에서 적시 호출률, 호출 지연, `no_reports` 비율, 공식 발표가 해당 작업에 적용되는 비율, 정확히 설명한 인계율과 불필요한 재시도 여부를 함께 보고한다. **작업 결론 변경**은 참여자의 확인 없이는 추정하지 않는다. 표본이 부족하면 성공/실패를 판정하지 않는다.

좁은 파일럿에서 적시 호출과 근거 기반 행동 변화가 보이기 전에는 10,000개 도메인 대량 탐색이나 일반 질문 네트워크를 우선 구현하지 않는다. 파일럿에서 자주 막히는 호스트를 우선 검증·연결한다.
