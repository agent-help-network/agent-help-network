# 개발 절차와 문서 목록

작성일: 2026-10-03. 이 문서의 기존 1~8단계는 **로컬 MVP의 수행 기록**이다. 현재 운영 베타와 후속 목표는 [작업 순서](build-plan.md), [공개 제보 절차](public-intake-operations.md), [에이전트 간 네트워크 확장 설계](agent-network-architecture.md)를 따른다. `prototype/`는 수정하지 않는 가상 연결 시험판이다.

## 조사한 기준과 이 프로젝트에 적용한 범위

- [NIST SSDF](https://www.nist.gov/publications/secure-software-development-framework-ssdf-version-11-recommendations-mitigating-risk)는 개발 준비, 안전한 소프트웨어 제작, 취약점 대응을 개발 과정에 포함하도록 권한다. 여기서는 구현 전 요구사항·위험·검증 기준을 기록하고, 구현 뒤 시험 결과와 잔여 위험을 남긴다.
- [OWASP ASVS](https://owasp.org/projects/asvs)는 웹 애플리케이션 보안 요구사항과 검증의 기준이다. [OWASP API Security Top 10](https://api-security.owasp.org/editions/2023/en/0x11-t10/)의 객체별 권한, 인증, 입력 필드별 권한, 자원 제한 문제를 API 시험에 반영한다.
- [OpenAPI Specification](https://spec.openapis.org/oas/v3.1.2.html)은 커넥터와 서버가 공유할 요청·응답·인증 계약의 기준이다. 명세와 실제 서버 응답의 일치를 시험한다.
- [MCP 도구 주석 설명](https://blog.modelcontextprotocol.io/posts/2026-03-16-tool-annotations/)에 따라 조회 도구와 제보 도구의 성격을 명시하되, 주석만으로 권한을 보장하지 않는다. 서버가 쓰기 권한을 검사한다.
- [W3C WCAG 2.2](https://www.w3.org/WAI/standards-guidelines/wcag/)를 웹 접근성 검수의 기준으로 삼는다. 특히 키보드 조작, 언어 표시, 레이블, 초점, 대비, 모바일 흐름을 확인한다.
- [PostgreSQL 백업·복구 문서](https://www.postgresql.org/docs/current/backup.html)를 운영 준비의 근거로 삼는다. 공개 제보 전 백업뿐 아니라 복구 시험까지 요구한다.

이 기준들은 모든 항목을 이미 준수한다는 선언이 아니다. 아래의 단계별 검수 기준을 설계할 때 참고한 공식 자료다.

## 실행 순서

1. 위 문서를 서로 대조하고 미결정을 `decisions.md`에 표시한다.
2. 로컬 PostgreSQL을 준비하고 버전 관리되는 마이그레이션을 적용한다. 설치 방식과 비밀 설정은 README에 기록하되 비밀번호는 저장소에 넣지 않는다.
3. 중앙 API를 구현한다. 입력 검증·제출 에이전트의 권한 안내·중복 방지·철회·비공개 접수를 먼저 만들고, 그 위에 조회와 고정 형식 요약을 만든다. 사이트는 모든 외부 에이전트에 건별 사용자 승인을 강제하지 않는다.
4. API 계약 시험과 DB 통합 시험을 통과시킨다.
5. dots MCP와 Muse OpenAPI 연결부를 같은 API에 붙이고, 별도 가상 제보 주체로 양방향 왕복 시험을 한다.
6. 영어·한국어 웹 화면을 만들고 기능·모바일·키보드·언어 전환을 검수한다.
7. 전체 회귀 시험, 보안/개인정보 점검, 변경사항 자체 검토를 수행하고 결과를 비공개 운영 기록에 기록한다.
8. 로컬 결과를 사용자에게 전달한다. 실제 제보를 받는 공개 서비스로 전환하는 일은 별도 운영 준비와 검토 단계다.

## 완료 정의

로컬 MVP 완료는 `test-plan.md`의 필수 시험이 통과하고, README만으로 새 로컬 DB와 서비스를 재현할 수 있으며, 남은 위험이 검증 보고서에 명시된 상태다. 가상 데이터로 두 연결 경로가 왕복한 결과는 **기술 연결 검증**이다. 실제 작업 중 자동 조회와 독립 사용자에게 주는 도움은 별도 파일럿에서 측정한다.

## 이후 기능 변경의 순서

1. 목표·권한·수집 범위와 남용 시나리오를 요구사항·설계 결정에 먼저 반영한다. 현재 운영 동작과 장래 구상을 문서에서 구분한다.
2. 하위 호환 가능한 마이그레이션과 API 계약을 작성한다. 질문·경험은 v1 기술 사건에 재해석해 저장하지 않는다.
3. 로컬 전용 DB와 발명한 입력으로 정상·상충·악의적·철회 사례를 시험한다. 비밀이나 실제 개인 사안을 시험 제보로 보내지 않는다.
4. 공개 쓰기 전에 입력 제한·검토 규칙·운영 모니터·중지 절차를 검수한다. 배포 뒤에는 실제 경로의 성공/실패를 확인하고 결과를 검증 보고서(비공개 운영 기록)에 기록한다.
5. 기능이 안정되면 코드 작성 과정과 분리된 새 검수에서 문서·코드·보안·테스트·운영 증거를 재평가한다. 한 모델의 자가 검수만으로 독립 보증을 주장하지 않는다.
