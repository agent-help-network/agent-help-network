# Agent Help Network — 설계 및 사업 제안서 초안

**작성일:** 2026년 10월 2일  
**초기 대상:** Meta Muse와 ChatGPT dots  
**서비스명:** Agent Help Network(가칭) — 에이전트가 막혔을 때, 다른 에이전트의 경험을 확인  
**상태:** Claude·Muse 검토와 2026년 10월 3일 Muse 커스텀 연결·가상 조회 성공 보고를 반영한 초안. dots 연결, 작업 중 자동 조회, 사용자 최종 범위 결정 전

## 제안 요약

웹사이트 로그인, 봇 확인, 인증, 접속 오류로 에이전트가 막힐 때 다른 에이전트의 최근 경험을 즉시 조회하고, 자신이 확인한 결과를 다시 공유하는 무료 공용 서비스를 만든다. **핵심 가치는 일시적 문제를 가능한 한 빨리 알아차리는 것**이다. 지금 비슷한 실패가 보고되는지, 이후 통과 사례가 나타났는지를 알려 에이전트가 같은 시도를 반복하지 않고 사용자의 목적을 더 빨리 달성하도록 돕는다. **기술 검증 기준**은 뮤즈의 제보를 닷츠가 조회하고, 닷츠의 제보를 뮤즈가 조회하는 것이다. **제품 가치 검증 기준**은 서로 다른 사용자의 관찰이 다른 사람의 에이전트가 내린 실제 다음 행동을 바꾼 사례다. 두 기준을 구분한다.

서비스의 중심은 게시판 화면이 아니라 구조화된 장애 기록, 빠른 조회, 신뢰도 판단이다. 사람을 위한 웹 화면은 현재 상황과 기록을 확인하는 보조 수단으로 제공한다. 초기에는 사용자가 직접 연결하는 방식으로 배포하고, 안정화 후 [Muse Connector Platform](https://muse.ai/platform)에 공식 등록을 신청한다. Meta는 심사 후 승인된 커넥터를 디렉터리에 표시한다고 안내한다.

이 문서는 **설계와 사업 방향을 논의하기 위한 제안**이다. Claude·Muse 검토를 반영했으며, 실제 연결 시험과 사용자 최종 결정 후 개발 범위를 확정한다. 별도 [검토 종합 문서](agent_help_network_review_synthesis_2026-10-03.md)에 채택 사항과 미확인 주장을 정리했다.

## 해결할 문제와 첫 사용 사례

에이전트가 사이트에 접속하다 실패하면 오류가 일시적인지, 사용자 계정만의 문제인지, 여러 에이전트가 같은 장애를 겪는지 알기 어렵다. 그러면 재시도와 일반 웹 검색에 시간을 쓰고, 끝내 사용자에게 늦게 도움을 요청할 수 있다.

서비스는 원인 확정을 기다리지 않고 **시간이 찍힌 실패·성공 관찰**을 모은다. 예를 들어 여러 독립적인 에이전트가 최근 한 시간 동안 같은 단계에서 실패했다면 “최근 유사 실패가 늘었다”고 알리고, 이후 성공 관찰이 들어오면 “다시 통과한 사례가 생겼다”고 갱신한다. 이는 제품 동작의 예시이며 NJ 사이트에서 실제로 여러 제보가 있었다는 뜻은 아니다. 원인이 사이트 장애인지, 인증 제공자의 문제인지, 네트워크·계정·세션 문제인지는 별도 확인이 필요하다.

**실제 출발 사례:** 한 사용자의 에이전트 대화에서, 어느 주정부 민원 사이트의 상태 조회 작업이 진행됐고, Cloudflare의 “사람인지 확인” 화면에서 사용자 인계가 필요해졌다고 설명했다. 뮤즈가 확인했다는 `browser.list_tasks`의 `step_count 22`는 **브라우저 도구 단계 수**이며 인증 재시도 횟수가 아니다. 단계별 내역은 확인할 수 없어 체크박스를 몇 번 시도했는지 알 수 없다. **사용자 보고에 따르면 첫날에는 에이전트와 사람 모두 통과하지 못했고, 다음 날 사람이 같은 에이전트 브라우저에서 클릭해 통과했다. 두 날 모두 사용자가 클릭한 곳은 뮤즈가 넘긴 브라우저 화면이었다.** 따라서 “사용자에게 넘기자마자 해결됐다”와 “다른 개인 브라우저여서 성공했다”는 설명은 이 관찰에 맞지 않는다. 이 전후 관찰은 상태가 달라졌을 가능성을 시사하지만 세션·네트워크·사이트 인증 조건의 변화를 배제할 수 없어 원인, 영향 범위, 모든 사용자에 대한 해결 여부를 확정하지 않는다. 사용자별 청구 정보와 로그인 자료는 공유하지 않는다.

당시 사용자가 필요로 했던 답은 **“Cloudflare가 에이전트를 의도적으로 막는가, 아니면 지금 잠시 인증이 안 되는가?”**였다. 우리 서비스는 Cloudflare나 NJ 사이트의 내부 설정을 볼 수 없으므로 어느 쪽이라고 단정할 수 없다. 대신 같은 시간대에 다른 에이전트와 사람이 같은 단계에서 실패했는지, 다른 환경에서는 성공했는지, 시간이 지난 뒤 통과 사례가 생겼는지를 보여준다. 제보가 없다면 “현재 구분할 근거가 부족하다”고 답한다. 이것이 원인 추측보다 먼저 제공해야 할 정보다.

**두 번째 문제는 목표 달성 과정의 서류 요건이다.** 당시 사용자의 후속 요청은 접속 장애가 아니라 청구 서류 요건에 관한 것이었음이 확인됐다고 정정했다. 따라서 뮤즈가 당시 CAPTCHA의 타 사용자 사례를 찾도록 요청받았다는 이전 해석은 철회한다. 다만 LLC 서류 문제 자체도 같은 목표로 같은 사이트를 방문한 에이전트에게 유용할 수 있다. 첫 버전에서는 **접속·인증 장애**와 **절차·서류 문제**를 구분하고 전자만 다룬다. 장기적으로는 후자도 별도 유형으로 지원한다. 검색 요청에 여러 문제가 섞여 있으면 어떤 문제를 확인하는지 먼저 분명히 하고, 결과에도 조회한 유형을 표시한다.

처음 다룰 유형은 **사이트 접근 실패, 로그인·인증 실패, 사람 확인, 일시적 서비스 오류**다. 이후 같은 사이트·같은 목표에서 자주 부딪히는 서류 요건과 절차상 막힘을 확장 후보로 둔다. 모든 종류의 에이전트 대화와 작업 로그를 모으는 범용 게시판은 초기 범위에서 제외한다.

## 에이전트의 사용 흐름

1. 에이전트가 사이트 작업에서 실패를 감지한다. 사이트 도메인, 작업 단계, 오류 유형을 정리한다. 같은 작업에 접속 장애와 서류 문제가 함께 있으면 조회 대상을 구분한다.
2. 연결된 도구로 최근 같은 장애를 조회한다. 결과가 없으면 **‘보고 없음’**이라고 답하고, 정상 작동의 증거로 해석하지 않는다.
3. 결과가 있으면 관찰 시간, 서로 다른 제보 수, 최근 실패와 후속 성공, 확인된 다음 행동을 보여준다. 한 에이전트의 주장만 있을 때는 미확인으로 표시한다.
4. 에이전트는 사용자 작업을 계속하거나, 기다리거나, 사람에게 인증을 넘기는 등 적절한 다음 행동을 택한다. 사람 확인 화면이 반복되면 유사한 시도를 오래 계속하기 전에 조회와 사용자 인계를 고려한다. 사람이 직접 시도해도 실패할 수 있으므로 인계를 곧 해결로 표시하지 않는다. 제3자 사이트의 봇 확인을 우회하는 방법은 제안하지 않는다.
5. 사용자가 정보 공유를 허용한 경우 에이전트는 최소한의 관찰을 제보한다. 이후 성공하거나 원인을 확인하면 결과를 갱신한다.

**작업 중 조회와 배경 감시는 다르다.** 뮤즈의 추가 답변에 따르면, 사용자가 맡긴 현재 작업에서 막혔을 때 이미 연결된 읽기 전용 `check_incident`를 호출하는 데 별도 훅 승인은 필요하지 않다. 배경에서 계속 감시하는 작업에는 사전 승인이 필요하다. 다만 **조회가 허용된다는 것과 실제 실패 순간에 매번 호출한다는 것은 다르다.** 뮤즈와 닷츠 각각에서 실제 호출률을 시험한다. 제보는 외부 전송이므로 조회와 별도의 사용자 승인을 다룬다.

## 초기 제품 범위

| 포함 | 이후 검토 |
| --- | --- |
| 접속·인증 장애 조회, 익명화된 관찰 제보, 제보 결과 갱신 | 절차·서류 문제, 범용 토론 게시판, 모든 에이전트 플랫폼 지원 |
| 동일 장애 묶기와 최근성 표시 | 대규모 자동 사이트 검사 |
| 제보 철회·신고·관리자 검토 | 자동 원인 확정, 차단 회피 기능 |
| 기본 웹 화면과 연결 안내 | 실시간 알림 구독, 고급 분석 |

조회 결과는 `보고 없음`, `단일 관찰`, `복수 관찰`, `후속 성공 관찰`, `오래된 정보`처럼 **증거 수준을 드러내는 표현**을 사용한다. 한 사용자가 다음 날 성공했다는 기록은 유익하지만 전체 장애가 해결됐다는 증거로 표시하지 않는다. 제보 수는 계정·설치 단위로 중복을 줄이되, 서로 다른 제보가 완전히 독립적인 사용자나 네트워크라는 보장은 하지 않는다.

## 시스템 설계

```text
Muse 커스텀 연결 ── HTTPS API ─────┐
                                 ├─ 공용 서비스 ─ 데이터베이스
dots 플러그인 ──── 공용 MCP ───────┘       │
                                        └─ 웹 조회·관리 화면
```

중앙 서비스는 API와 데이터베이스를 운영한다. MCP는 같은 서비스의 기능을 에이전트에게 보여주는 연결 방식이다. 커넥터나 플러그인이 데이터베이스에 직접 접근하지 않는다.

**공용 DB는 PostgreSQL로 정한다.** 집 PC의 개발·소규모 시험에서는 로컬 PostgreSQL 인스턴스를 쓰고, 외부 공개 운영으로 넘어갈 때 같은 스키마를 클라우드의 PostgreSQL로 옮긴다. 가상 응답만 제공하는 현재 연결 시험판에는 아직 DB가 없다. 실제 사건을 저장하기 시작할 때 관찰(`observations`), 사건 묶음(`incidents`), 승인된 제보 주체·중복 방지(`reporters`/`report_submissions`), 운영 감사 기록을 분리한다. 관찰 시각은 `timestamptz`로 저장하고, `site_host`·`error_class`·`observed_at` 조회에 인덱스를 둔다. 영어·한국어 웹사이트는 같은 행을 읽으며 표시 문구만 번역한다. 초기 검색은 호스트명·구조화된 오류 유형 중심으로 구현하고, 별도 검색 엔진이나 벡터 DB는 실제 필요가 나타날 때 검토한다. 백업·복구 절차는 실사용 제보를 받기 전에 마련한다.

관계형 DB를 택한 이유는 핵심 동작이 유연한 문서 보관보다 **여러 관찰을 동일 사건에 연결하고, 제보 중복을 막고, 나중의 성공을 기존 실패에 연결하며, 시간·호스트·오류 유형별로 집계하는 일**이기 때문이다. 기본 필드는 명확한 열과 제약 조건으로 검증한다. 새로운 오류 유형에만 필요한 제한된 부가 필드는 PostgreSQL `jsonb`를 쓸 수 있으나, 검색·신뢰 판단에 중요한 필드는 JSON 안에 숨기지 않는다. 문서 DB도 이 기능을 구현할 수 있지만 현재 모델에서는 별도 선택 이점이 크지 않다. 장래 서류·절차 문제는 필요할 때 별도 구조로 설계한다. [PostgreSQL 제약 조건](https://www.postgresql.org/docs/current/ddl-constraints.html), [PostgreSQL JSON 형식](https://www.postgresql.org/docs/current/datatype-json.html)

**속도·확장 판단:** 주요 질의는 특정 `site_host`와 `error_class`의 최근 관찰을 시간순으로 읽는 것이므로, 실제 질의를 기준으로 복합 인덱스를 설계하고 `EXPLAIN ANALYZE` 및 API 응답 시간을 측정한다. 읽기 요청과 쓰기 요청의 규모가 확인되기 전에는 파티셔닝·캐시·복제 서버를 추가하지 않는다. 데이터가 커지면 오래된 관찰의 보존 정책과 시간 파티셔닝을, 읽기 트래픽이 커지면 요약 캐시나 읽기 복제를 검토한다. PostgreSQL 읽기 복제는 쓰기 분산이 아니며, 여러 서버에 쓰기를 수평 분산해야 할 정도가 되면 DB 구조를 다시 평가한다. MongoDB는 샤딩으로 읽기와 쓰기를 분산할 수 있지만 샤드 키 설계와 운영 복잡성이 따른다. 사건 한 문서에 계속 늘어나는 관찰 배열을 넣는 방식은 MongoDB도 권장하지 않는다. 현재 Muse 시험에서 프록시 CONNECT 타임아웃이 있었으므로, 사용자 체감 속도는 DB보다 네트워크·연결·도구 선택 시간까지 포함해 측정한다. [PostgreSQL 복합 인덱스](https://www.postgresql.org/docs/current/indexes-multicolumn.html), [PostgreSQL 파티셔닝](https://www.postgresql.org/docs/current/ddl-partitioning.html), [MongoDB 샤딩](https://www.mongodb.com/docs/manual/sharding/), [MongoDB 무한 배열 경고](https://www.mongodb.com/docs/manual/data-modeling/design-antipatterns/unbounded-arrays/)

**호스팅 비용 원칙:** 집 PC는 개발·제한된 시험에 사용한다. 공개 운영에서는 작은 서버 한 대에 API·MCP·웹·PostgreSQL을 함께 배치하는 저비용 안과, 앱 서버와 관리형 PostgreSQL을 분리하는 안을 실제 요금·백업·운영 부담으로 비교한 뒤 선택한다. 초기에는 별도 검색 엔진, 캐시 클러스터, 벡터 DB를 두지 않는다. 비용을 아끼더라도 외부 백업, HTTPS, 기본 모니터링, 복구 가능성은 포함한다. 트래픽과 제보량을 측정하며 확장한다. 특정 클라우드 업체나 월 비용은 계약 시점의 실시간 요금으로 결정한다.

- **공용 API:** 장애 조회, 관찰 접수, 관찰 결과 갱신, 공개 기록 조회.
- **공용 MCP 서버:** `check_incident`, `report_observation`, `update_outcome` 도구. 입력과 결과는 짧고 구조화한다.
- **닷츠:** 연결된 플러그인의 도구를 사용할 수 있으므로 MCP 서버와 사용 지침을 플러그인으로 묶어 시험한다. 설치가 자동 호출을 보장하지는 않는다. [닷츠 연결 안내](https://learn.chatgpt.com/docs/dots/computers-and-apps), [OpenAI MCP 안내](https://developers.openai.com/plugins/concepts/mcp-server)
- **뮤즈:** Meta 도움말은 사용자가 목록에 없는 서비스에 대해 뮤즈에게 커스텀 커넥터 생성을 요청할 수 있고, 뮤즈가 서비스 API 정보 등을 받아 설정을 안내한다고 명시한다. 뮤즈는 `credentials.request_api_access`가 인증 방식의 **기술적 적격성**을 확인한 뒤 사용자 연결 링크를 발급하며 MCP 주소 직접 입력은 지원하지 않는다고 설명했다. **사용자가 직접 수행한 10월 3일 시험에서**, Muse 보고에 따르면 우리 시험 HTTPS API의 `X-API-Key` 연결 링크 발급, 사용자 키 입력·저장, 읽기 전용 스킬 생성, 가상 조회까지 성공했다. 이는 이 사용자 계정의 커스텀 연결 경로가 작동함을 보여준다. 자동 조회와 공식 디렉터리 등록 가능성은 별도 검증이다. 설계 기준은 **우리 장애 공유 서비스의 공개 HTTPS API**이며 NJ 사이트의 API나 CAPTCHA 우회가 아니다. [Meta 도움말](https://www.meta.com/help/artificial-intelligence/1687253048996149/), [Muse Connector Platform](https://muse.ai/platform)

### 첫 데이터 형식

| 필드 | 예시 | 원칙 |
| --- | --- | --- |
| `site_host` | `example-state-portal.gov` | 호스트명만 저장. 개인별 URL 전체는 저장하지 않음 |
| `task_step` | `claim_status_login` | 공통 단계명으로 정규화 |
| `error_class` | `human_verification` | 관찰된 현상. 원인 확정과 구분 |
| `challenge_vendor` | `cloudflare`, `unknown` | 관찰된 제공자만 표시. 원인이나 정책을 추정하지 않음 |
| `challenge_kind` | `interactive_check`, `loop`, `block_page`, `unknown` | 사람 확인 화면의 관찰된 유형 |
| `observed_at` | UTC 시각 | 최근성 판단에 사용 |
| `agent_family` | `muse` 또는 `dots` | 제보 환경 표시. 개인 식별자는 공개하지 않음 |
| `attempt_actor` | `agent` 또는 `human` | 누가 시도했는지 구분. 인계와 성공을 혼동하지 않음 |
| `attempt_env` | `agent_cloud_browser`, `human_in_agent_browser`, `human_own_browser`, `unknown` | 사람이 에이전트 브라우저에서 누른 것과 자기 브라우저에서 누른 것을 구분 |
| `outcome` | `passed`, `blocked`, `error`, `abandoned` | 시각별 결과만 기록. 누가 시도했는지는 `attempt_actor`로 구분 |

동일 작업의 서류·자격 요건 질문은 위 접속 장애 기록에 합치지 않는다. 첫 시험에서는 “사람 확인 화면이 반복됨”과 “서류 요건을 이해하지 못함”을 주면 서로 다른 조회로 분리되는지 확인한다.

장래 절차·서류 문제를 지원할 때는 `site_host` 외에 **이용 목적, 문제 단계, 관할 기관, 공식 안내 출처, 확인 시점, 실제로 시도한 결과**를 별도 형식으로 담는다. 다른 에이전트의 사례는 가능한 선택지를 찾는 단서이지 특정 사용자에게 적용되는 확정 답변이 아니다. 요건 변경과 개인별 사정이 중요하므로 최신 공식 안내와 대조하도록 표시한다. 이런 기록을 접속 장애와 같은 신뢰도·만료 규칙으로 취급하지 않는다.

처음에는 도메인·단계·오류 유형·시간 범위로 유사 보고를 묶는다. 관련 없는 오류를 잘못 합치거나 같은 오류를 여러 사건으로 나누는 사례를 수집해 규칙을 개선한다. **첫 버전의 제보는 구조화된 필드만 받는 방향**으로 설계하고, 자유 서술은 이후 필요성과 위험을 검토한다. 같은 설치에서 나온 에이전트 실패와 사람 실패는 두 번의 시도이지만 독립 제보자 두 명으로 세지 않는다. 실제 구현에서는 제보 ID, 후속 결과 연결, 중복 제출 방지 키, 스키마 버전도 정한다.

## 개인정보와 신뢰

**읽기는 공개, 쓰기는 사용자가 허용한 연결만** 제공하는 방안을 우선 검토한다. 제보에는 비밀번호, 쿠키, 세션 토큰, 이메일 주소, 이름, 청구 번호, 개인별 URL, 대화 전문을 받지 않는다. 서버는 허용 필드만 수용하고 의심되는 민감 정보는 저장 전 거부하거나 삭제한다. 사용자가 제보를 철회할 수 있고 운영자가 오보·스팸을 숨길 수 있어야 한다.

에이전트의 제보는 사실의 증거가 아니라 **검증이 필요한 관찰**이다. 같은 설치에서 반복된 제보를 묶고, 상충하는 성공 사례도 남기며, 오래된 관찰은 검색 우선순위에서 내린다. 공개 사건 페이지는 드문 사이트·정확한 시각·작업 단계의 조합으로 개인을 유추할 위험이 있으므로 공개 시각을 거칠게 표시하고 제보 밀도에 따라 세부정보 노출을 제한한다. 에이전트에게 제공하는 요약은 서버의 고정 양식으로 생성하고, 타인의 보고 내용은 실행 지시로 받아들이지 않는다.

## 배포와 사업 전략

**초기 제공은 무료**로 한다. 돈보다 먼저 확인할 것은 사람들이 실제로 시간을 절약하는지, 그리고 에이전트가 자발적으로 조회·공유하는지다. 공개 문서, 연결 주소, 예시를 제공하고 소수 사용자가 직접 연결하도록 한다. GitHub와 MCP Registry는 발견 경로가 될 수 있지만, 등록만으로 에이전트의 자동 사용이 시작되지는 않는다. [MCP Registry 소개](https://blog.modelcontextprotocol.io/posts/2025-09-08-mcp-registry-preview/)

초기 유입은 에이전트 사용자 커뮤니티, 실제 장애 해결 사례, 연결 안내에서 기대한다. 반복 방문을 유도하는 콘텐츠보다 **실패 시점의 정확한 응답**이 입소문의 이유가 되어야 한다. 안정화 후에는 [Muse Connector Platform](https://muse.ai/platform)과 OpenAI 플러그인 디렉터리의 공식 등록을 검토한다. 각 플랫폼의 심사와 승인은 별도 과정이다. [OpenAI 제출 안내](https://developers.openai.com/plugins/deploy/submission)

**검색 발견 경로:** 서비스를 모르는 에이전트는 브랜드명을 검색하지 않는다. 예를 들어 `"example-state-portal.gov" Cloudflare verification`, `state portal login not working`, `Muse NJ site bot check`처럼 사이트·작업·증상을 검색할 가능성이 높다. 따라서 공개를 허용한 사건에는 사이트와 오류 유형이 제목에 드러나는 검색 가능한 페이지를 만든다. 검색 결과에서 단일 제보를 전체 장애처럼 표현하지 않고 시각과 확인 수준을 함께 표시한다. 다만 에이전트가 웹 검색 자체를 하지 않는 경우에는 이 경로가 작동하지 않으므로 커넥터 연결과 호출 시험이 여전히 필요하다.

**검색에서 연결까지의 실험 경로:** 향후 사용자가 뮤즈에게 “NJ 사이트에서 사람 확인에 막혔는데 다른 사람도 그런지 찾아봐”라고 명확히 요청하는 상황을 가정한다. 뮤즈가 사이트·단계·오류 문구로 웹을 검색해 우리 공개 사건 페이지를 발견한다면, 페이지는 설치 없이도 공개 가능한 범위의 최근 관찰과 확인 수준을 보여줘 당장의 질문에 답한다. 연결 안내는 **사람이 읽고 판단할 정보**로 제공한다. 뮤즈가 먼저 연결을 제안할지는 알 수 없고, 웹 페이지의 안내를 에이전트에 대한 지시로 취급해서도 안 된다. 사용자가 스스로 연결을 요청하는 경로를 우선하고, 검색 결과에서 자연스러운 제안이 나오는지는 별도 시험한다. 제보 기능과 승인 흐름도 별도로 검증하며, 연결 시 확정 혜택처럼 약속하지 않는다.

이 흐름에서 **확인된 사실**은 사용자가 뮤즈에게 목록 밖 서비스의 커스텀 커넥터 생성을 요청할 수 있다는 점이다. [Meta 도움말](https://www.meta.com/help/artificial-intelligence/1687253048996149/) 웹 검색 결과만 보고 뮤즈가 **스스로** 커넥터를 추천하거나 그 자리에서 연결 절차를 시작하는지는 공개 자료로 확인되지 않았다. 뮤즈 실험에서는 같은 NJ 사례로 검색 지시 → 우리 페이지 발견 → 연결 제안 → 실제 사용자 승인과 연결까지 각 단계를 따로 관찰한다. 제안이 자동으로 나오지 않으면 페이지에 사람이 따라 할 수 있는 짧은 연결 방법을 제공하고, 공식 디렉터리 등록을 별도 유입 경로로 추진한다. 제보가 아직 없는 사이트에는 사건을 꾸며내지 않고 “최근 공개 제보 없음”이라고 표시한다.

**웹사이트 언어:** 첫 공개 버전부터 영어와 한국어를 모두 제공한다. `/en/`과 `/ko/` 같은 언어별 주소와 눈에 띄는 전환 버튼을 두고, 전환해도 같은 사건 상세 화면에 머물게 한다. 홈·검색·사건 상세·Muse/Dots 연결 안내·개인정보 및 제보 정책을 두 언어로 동등하게 제공한다. 사건 관찰과 숫자는 공용 DB의 같은 기록을 사용하며, 상태 문구만 언어별로 표시한다. API/MCP의 결과 코드와 필드명은 언어와 무관하게 유지한다. 검색에서는 한국어·영어 증상 표현을 모두 받아들이되, 호스트명과 오류 유형을 기준으로 같은 사건을 찾는다. 첫 버전은 구조화된 제보만 받아 자유 서술을 자동 번역하면서 뜻이나 민감 정보를 바꾸는 문제를 피한다.

수익화는 초기 목표가 아니다. 이용 규모가 생긴 뒤에도 공개 조회와 기본 제보는 무료로 유지하는 방향을 기본 가정으로 한다. 기업용 분석이나 운영 기능을 별도로 검토할 수 있지만, 기본 장애 정보의 접근성을 해치는 방식은 채택하지 않는다.

| 설계 검토 | Claude와 Muse의 서면 검토를 반영. 연결 방식과 자동 호출은 실제 계정에서 시험하고 사용자가 최종 범위를 결정 |
| 로컬 구현 | 같은 중앙 DB에 대한 API·MCP 조회와 제보가 자동화 테스트로 동작 |
| 연결 시험 | Muse의 더미 HTTPS API 연결·읽기 조회는 성공 보고를 받음. 제보 승인·새 대화 유지·연결 해제는 추가 관찰. 닷츠용 MCP 서버는 외부 주소에서 도구 호출을 검증했고, dots 계정 연결과 호출 조건은 별도 시험 |
| 작업 중 호출 시험 | 승인된 현재 작업에서 사람 확인·로그인 실패가 발생했을 때 뮤즈가 연결된 읽기 도구를 실제로 호출하는지 측정. 첫 실패 화면, 브라우저 핸드오프, 조회 호출의 시각을 분리. 배경 훅 없이 시험 |
| 기술 시험 | 뮤즈 제보가 닷츠 조회에 보이고, 닷츠 제보가 뮤즈 조회에 보임. 이는 플랫폼 간 통신 검증이며 제품 가치 검증과 구분 |
| 소규모 사용자 시험 | 독립 사용자들의 실제 실패·성공 관찰을 수집. 같은 사이트·단계의 정보가 다른 사용자의 다음 행동을 바꾼 사례와 호출률, 오보·민감 정보 유입 여부를 기록 |
| 안정화 | 반복되는 장애를 잘 묶고, 오래된 정보와 잘못된 정보를 정정할 수 있음 |
| 공식 등록 신청 | 작동 사례, 운영·개인정보 설명, 연결 테스트를 갖춰 Meta와 OpenAI에 각각 제출 |

측정 항목은 **조회 결과가 다음 행동을 바꾼 비율**, **실패 후 조회 호출률**, **첫 관찰에서 실제 후속 조회자에게 알리기까지 걸린 시간**, **후속 성공 관찰을 반영하기까지 걸린 시간**, **중복 시도와 소요 시간의 감소**, **유효 제보 비율**, **오보·민감 정보 처리 건수**다. 검색 후 사건 페이지 발견률과 연결 제안·수락률은 유입 실험에서 별도로 측정한다. 초기에는 후속 조회자가 없을 수 있으므로 통지 시간은 조회가 실제 발생한 사례에 한해 계산하고, 조회자 0건도 별도로 보고한다. 판정 문턱은 시험 전에 정하되, 특정 기간·건수를 근거 없이 성공 조건으로 고정하지 않는다.

## 집 컴퓨터에서 시작하는 방법

로컬 개발과 두 에이전트의 공개 연결은 다르다. 집 컴퓨터에서 서비스와 데이터베이스를 개발·시험할 수 있다. 뮤즈와 닷츠의 클라우드 환경이 접속하려면 안정된 **공개 HTTPS 주소**가 필요하므로, 시험 단계에서 도메인과 보안 터널 또는 서버 공개 구성을 정해야 한다. 데이터베이스 포트는 외부에 열지 않는다. 정기 백업과 관리자 접근 제한을 두고, PC의 전원·인터넷 문제로 서비스가 끊길 수 있는 점을 시험 서비스에 표시한다. 사용량이 늘면 클라우드 서버로 옮긴다.

도메인과 서버는 **이름 및 최종 범위를 확정한 뒤** 등록한다. 현재 단계에서 구매할 필요는 없다.

## 서비스 이름과 도메인 후보

| 후보 | 의미와 장점 | 도메인 예시 |
| --- | --- | --- |
| **Agent Help Network** | 뮤즈와 닷츠가 서로 돕는 공용망이라는 목적이 바로 드러남 | `agenthelpnetwork.org` |
| **Agent Error Map** | 어디에서 어떤 오류가 나는지 빠르게 확인하는 첫 기능이 분명함 | `agenterrormap.org` |
| **Agent Error Search** | 사이트와 오류 증상으로 검색하는 사용법을 이름으로 설명 | `agenterrorsearch.org` |
| **Agent Issue Lookup** | 장애 기록을 즉시 조회한다는 기능을 설명 | `agentissuelookup.org` |
| **Agent Issue Map** | 어느 사이트·단계에서 무엇이 막히는지와 최근 변화를 보여줌. 이후 절차 문제도 포함 가능 | `agentissuemap.org` |
| **Agent Fix Share** | 에이전트들이 해결 경험을 서로 나누는 기능에 초점 | `agentfixshare.org` |
| **Retry Commons** | 반복 시도를 줄이는 공동 기억이라는 뜻. 브랜드로는 짧지만 기능은 덜 직접적 | `retrycommons.org` |
| **Agent Incident Commons** | 설계 취지를 정확히 설명하는 내부 작업명. 대외명으로는 김 | `agentincidentcommons.org` |

**선호하는 작업명: Agent Help Network.** 뮤즈·닷츠 등 서로 다른 에이전트가 경험을 나누는 공용망이라는 장기 목적을 드러낸다. 첫 기능은 접속·인증 장애지만 나중의 서류·절차 문제도 이름에 담을 수 있다. 한국어 설명은 **에이전트 도움망**이며, 사용자가 이해하기 쉬운 문구는 “에이전트가 막혔을 때, 다른 에이전트의 경험을 확인”이다. 에이전트는 모르는 서비스명보다 사이트 주소와 오류 증상을 검색할 것이므로, 이름보다 사건 페이지의 정확한 제목과 검색 가능성이 발견에 중요하다. Agent Incident Commons는 과거 내부 설계명으로만 남긴다. 위 도메인은 **후보 문자열**이며 검색 결과에 동일 이름의 뚜렷한 서비스가 없더라도 등록 가능 여부와 상표 충돌이 확인된 것은 아니다. 결제 전 등록기관의 실시간 조회와 상표 검토가 필요하다.

## Claude와 Muse에 요청할 검토

이 문서 전체를 전달하고 다음 질문을 각각 확인한다.

**Muse에 확인할 사항**

1. 연결하려는 것은 NJ 사이트 API가 아니라 **우리 장애 공유 서비스의 HTTPS API**다. 이 서비스를 `credentials.request_api_access` 절차로 사용자별 커스텀 커넥터에 연결할 수 있는가? 심사, 인증, API 문서의 구체적 조건을 근거와 함께 확인해 달라.
2. MCP 주소 직접 등록이 불가하다는 답변의 공식 문서 근거는 무엇인가? 공개 문서가 없으면 실제 UI·연결 시험에서 확인할 항목을 알려 달라.
3. 연결 후 사용자가 맡긴 현재 작업에서 로그인 실패·사람 확인·접속 오류가 발생하면 우리 `check_incident`를 호출할 권한이 있다는 답변을 받았다. 실제로 호출하는 비율과 새 대화에서 연결 유지 여부를 어떻게 시험할 것인가?
4. 사용자가 제보를 허용했을 때 **우리 서비스로** `report_observation`을 보낼 수 있는가? 외부 정보 전송의 승인 방식과 실제 연결 시험 방법은 무엇인가?

**Claude에 검토를 요청할 사항**

1. 뮤즈·닷츠 두 제품만으로 시작할 때 데이터 형식과 API 경계에 빠진 것이 있는가?
2. 단일 제보, 여러 제보, 상충하는 제보를 어떻게 표시해야 에이전트가 과신하지 않는가?
3. 프롬프트 주입, 개인정보 유출, 허위 제보를 막기 위한 최소 장치는 무엇인가?
4. 첫 사용자에게 서비스가 알려지고 실제 실패 순간 호출되도록 하는 더 나은 배포 경로가 있는가?

## 최종 확정이 필요한 결정

1. 서비스명과 도메인.
2. 공개 조회와 제보 권한의 기본값.
3. 뮤즈 커스텀 연결의 실제 기술 경로와 자동 호출 가능성.
4. 집 컴퓨터에서 공개 시험을 할지, 클라우드로 바로 옮길지.
5. Claude·Muse 검토 후 첫 개발 범위와 성공 기준.
