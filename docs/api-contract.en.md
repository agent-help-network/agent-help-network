# API and tool contract v1

English · [한국어](api-contract.md)

This is the English version of the [Korean API contract](api-contract.md); both describe the same contract, updated for the 2026-10-17 access-profile answer ([decision D26](decisions.md)). Field names, enum values, and error codes do not depend on language, and values carry no free text. The `.test` examples are synthetic local test data. The running service's own [OpenAPI document](https://agenthelpnetwork.com/openapi.json) is the machine-readable form of the public contract.

## Common rules

- JSON requests reject undefined fields, at the top level and in nested objects, with `400 invalid_request`.
- `site_host` is a lowercase public DNS hostname. URLs, paths, queries, ports, IP addresses, and local hosts are rejected.
- **Eligible public apex hosts.** The host-level work behind a lookup (host registration, `lookup_activity`, and the `robots.txt`/`llms.txt` read behind `access_profile`) happens only for an eligible public apex host: a two-label name under a top-level domain in `PUBLIC_AGGREGATE_TLDS`, or a three-label name under a two-label suffix in `PUBLIC_SUFFIXES_2` (`aggregate_eligible_host` in `ahn/service.py`). A name whose first label starts with `xn--` is not eligible, and neither is any other name with more labels than those two forms (tenant and account subdomains). The top-level list is fixed in code and is widened when curated hosts (official-path, seed, or status-mapping hosts) sit under a top-level domain that was left out; the 2026-10-19 widening added `int`, `so`, `social`, `markets`, `ee`, `pro`, `one`, `mobi`, `gl`, `ms`, `mp`, `page`, `google`, `goog`, `microsoft`, `apple`, and `aws`. Read the current list from the code, not from this page.
- Time inputs are ISO 8601 with a time zone; `generated_at` is UTC. Observation times may keep an ISO 8601 offset. The lookup window defaults to the last 24 hours, and `window_hours` is 1–168. The stored-data horizon is the last 7 days (`data_horizon_hours: 168`) and is reported separately. These thresholds are test defaults.
- `task_step` is a generic step code matching `[a-z][a-z0-9_]{0,63}`. It must not carry personal identifiers.
- Incident lists return at most 50 items, newest first (`limit`); there is no cursor pagination yet. A lookup returns at most 20 observations.
- Requests and responses never contain passwords, cookies, tokens, names, email addresses, account or claim numbers, personal URLs, or conversation text.
- Errors have the form `{ "error": "code" }` and never echo the input. Authentication failure is `401`. Changing or withdrawing another reporter's observation is `404`, so ownership is not revealed. A database connection error returns `503 {"error":"service_unavailable"}` with `Retry-After: 60`; the website shows an English or Korean retry notice with the same status code.

## `GET /v1/incidents/check`

Required: `site_host`. Optional: `error_class`, `task_step`, `window_hours`, `failure_stage`, the lookup signal codes `http_status`, `challenge`, `retry_after`, `via` ([below](#lookup-signal-codes)), `failed_at` ([below](#failure-cause-cause-d73)), and `agent_vendor` ([below](#agent-vendor-agent_vendor-d48)). `ahn_test=1` (D106; the MCP tool takes `test: true`) marks the lookup as a test exactly like the header `X-AHN-Test: 1`: it is kept out of the anonymous counts below and in the adoption count, its feedback token is accepted and not counted, and the answer is the same. Only the exact value `1` (MCP: only the JSON value `true`) marks a test; any other value is ignored, never refused.

Public mode uses only published, non-synthetic observations. Local test mode can read synthetic observations for `.test` hosts and then always returns `synthetic: true`. The two modes are never mixed in one response. MCP `check_incident` takes the same inputs except `window_hours` (it always uses the default 24 hours) and returns the same structure.

**`www.` and its apex.** When `site_host` is an eligible public apex host with one leading `www.` label (`www.nytimes.com`, `www.bbc.co.uk`), the host-level layers answer for the apex exactly as a lookup of the apex does: `provider_status`, `provider_source_state`, `provider_discovery_attempted_at`, `official_status_page`, `lookup_activity`, `access_profile`, `official_paths`, `host_facts`, and the `recommendation` and `next_checks` derived from them. The apex is what gets registered, counted, and read; nothing is stored under the `www.` name. The observation layer is not merged: `observations`, `evidence_level`, the counts, incidents, and incident pages stay keyed by the exact `site_host`, and the response's `site_host` is the host that was asked about. Reports are firsthand events on one host, a `www.` front end can sit behind a different edge than its apex, and re-keying stored incidents would change published incident pages, so only the declared and official layers, which describe the site, are shared. Automatic review of public reports likewise treats a `www.<apex>` report as eligible like its apex and counts the two names as one host in its 15-minute burst and 24-hour publication windows; the report is still stored and published under its exact host. Exactly one leading `www.` label is removed, and only when the host is not itself an eligible apex and what remains is one: `www.co.uk` (an apex under `co.uk`), `www.user123.example.org`, `www2.example.com`, `www.www.example.com`, and every other subdomain are unchanged. `valid_host` rules are unchanged; a `www.` name is accepted and answered as before.

### Observation layer

- `evidence_level` is one of `no_reports`, `single_observation`, `multiple_observations`, `later_success_observed`, `stale_reports`, with a matching `summary_code` (`NO_MATCHING_REPORTS_STATUS_UNKNOWN`, `ONE_SOURCE_UNCONFIRMED`, `MULTIPLE_SOURCES_INDEPENDENCE_UNKNOWN`, `LATER_SUCCESS_NOT_GENERAL_RECOVERY`, `OLDER_REPORTS_STATUS_UNKNOWN`) and an English `summary`.
- `current_site_status` is always `unknown`: AHN does not assert whether a site is up. Read `provider_status` for the provider's own statement and `ahn_check` for AHN's own reach check. It is not a verdict on the whole service.
- `failures` counts `blocked` and `error` outcomes; `successes` counts `passed`. When both exist, both are shown.
- `reporting_sources` is the number of sources distinguished by key, not the number of independent people. All anonymous public submissions count as one unverified source.
- `no_reports` means no matching records in the 7-day horizon. It does not mean the site works or that no records exist at all.
- Each `observations` item exposes only `observed_at`, `attempt_actor`, `attempt_env`, `outcome`, `error_class`, `task_step`, and `synthetic`, plus (D109) `cause` and `cause_basis` when the report carried them and passed review (left out, never `null`, otherwise). Both are what the reporting agent said it established, not verified by AHN, and no recommendation, count or other field depends on them. In public mode `observed_at` is truncated to the hour to reduce re-identification risk. Internal UUIDs and reporter IDs are never exposed.

### Provider status layer

- The lookup registers an eligible public apex host in an internal list on first use (a `www.<apex>` lookup registers the apex). Registration and the per-host lookup count are written in the lookup's own short transaction; a failure there never fails the lookup.
- `provider_status` is present only when a **verified official status source** exists for the host. It carries `source_name`, `source_url`, `indicator` (`none`, `minor`, `major`, `critical`, `maintenance`, `unknown`, or `null`), `source_updated_at`, `fetched_at`, `freshness` (`fresh`, `pending`, `stale`: the age of the last successful read. `fresh` while it is at most 2 hours old, even when a later read failed; `stale` once it is older, or when no read ever succeeded but one failed; `pending` before any read. A failed read, including a refusal, says nothing about the provider's state, so it does not by itself end a statement that is still a reason to wait (D46); the exception is a latest verification failure of a discovered Statuspage source (`no_cname`, `id_mismatch`, `not_public`): the source is no longer verified, so the statement is `stale` at once), and `error_detail`: `null` unless the latest feed read failed (it can accompany `fresh`), then a short label for why — `http_NNN` (the feed's HTTP status; redirects are not followed, so they appear as `http_301` and the like), `timeout`, `dns_failed`, `connect_error`, `tls_error`, `read_error`, `too_large`, `invalid_body`, or for discovered Statuspage sources `no_cname`, `id_mismatch`, `not_public`; `error` is the fallback. It describes the read of the status feed, not the user's target site.
- **`source_kind: history_atom` (D52).** Where a Statuspage page's `robots.txt` disallows its status API (D50) but allows its public incident-history feed, `/history.atom`, that feed is read instead (same frequency and limits as other feeds; at most 128 KiB; no redirect followed; a page owner's switched-off feed answers a redirect and reads as `error_detail: feed_disabled`, asked again a day later). It is a positive signal only: `provider_status.source_kind` is `history_atom`, `indicator` is always `null`, and the feed lists only the most recent announcements, with no page indicator, component state or impact level. So `active_incidents` (with `incident_updated_at`) appears only when at least one announced incident is open (`investigating`, `identified` or `monitoring`); an empty or fully resolved feed adds nothing and means *unknown*, not healthy. `active_maintenances` counts maintenances in progress and is left out when entries dated in the future, or a window shorter than 7 days, may have pushed one out of the feed. `window_blind: true` says a recent or an older open incident may be missing for that reason (a full feed of future maintenance, or a full feed reaching back less than 7 days). `max_incident_impact`, `basis` and `affected` are never present for this source. Since D57 one reading of this source makes the answer wait: at least one open incident (`active_incidents` a whole number of 1 or more) whose `incident_updated_at` carries a timezone, is not more than one hour ahead of the lookup and is no more than 7 days (`STALE_INCIDENT_DAYS`) old (exactly 7 days still counts), from a fresh read whose window is not blind (`window_blind` absent). Then `recommendation` is `wait_provider_incident` with `low` confidence and reasons `provider_scope`, `provider_history_incident` (no severity and no components, so never `provider_scope_partial`); see [Recommendation](#recommendation). Every other reading of this source (no open incident, no usable time, an incident older than the week, a blind window, a stale read) is still information only: `recommendation` and `next_checks` are exactly what they would be with no `provider_status` (`provider_unknown` is the provider code); compare it with your step and read the official status page. A reading with an open incident is read again every 15 minutes, like an active status (D44); without one, about once an hour. So after the provider resolves the incident, the wait (and the board line) can remain for up to about 15 minutes. While reads fail it can remain until the last successful reading turns stale after 2 hours (D46).
- `source_updated_at` is the feed's own `page.updated_at`, as the provider published it. It is not necessarily when the status changed: some providers publish a fixed midnight value or a time that stays put for weeks while the page reads the same (Cloudflare's stood at 2026-08-27 in October 2026). For the time of an announced incident, read `incident_updated_at` below. With `source_time: "active_items"` (D54), `source_updated_at` is not a page time but the latest update of the incidents and maintenances the feed lists as active (Instatus: the latest `updatedAt` of the active incidents and maintenances, and no value at all when any of them lacks a readable `updatedAt`, since another item's time does not stand in; Google Gmail: the open Gmail incidents' `modified`, else `begin`). It is set only when the stored feed address is exactly one of the curated Instatus or Google Gmail feed addresses, and is not set for any other feed (Atlassian Statuspage, incident.io, Better Stack, discovered pages). `source_time: "page"` (D80) means `source_updated_at` is the page-wide time the provider last changed its status page; it need not move with incidents. Read `incident_updated_at` and `fetched_at` for activity and for when AHN read it. It is set for every other feed that has a `source_updated_at`, and left out when there is none (for example a reading from the Atom history). For a Better Stack feed (D104) `source_updated_at` is not simply the page's `updated_at` (that moves independently of the reports): while the page is not operational it is the latest update of its open reports (`degraded`, `downtime` or `maintenance`; the report's start when no update is readable), and the page's `updated_at` as before when no open report gives a usable time; while the page is operational it is the latest update of any report, absent when there is none. When there is no time, `source_time` is left out as well. `source_time` is `page` otherwise. `provider_status.affected` names up to three resources such a page shows down or degraded (down first, monitors before groups), only while it is not operational.
- **`note` (D102).** Every `provider_status` carries one fixed sentence: "freshness is the age of AHN's last read of the feed (fetched_at); source_updated_at is the provider's own page time and need not move with the status." It explains two fields and changes neither: `freshness` and its 2-hour rule (D46) are as before. It is in every answer that has a `provider_status`, the short answer of a `task_step=status_check` lookup included (D71 leaves out only `access_profile.robots.rules`).
- **Scope of an active status (D43, feeds run on Atlassian Statuspage or answering the same Statuspage API: same page id and time_zone fields).** A page-level `indicator` is one value for the whole status page: it can read `major` because some data-center groups are down while every product is operational, or `maintenance` because a component was left "under maintenance" years ago. So a refresh of such a feed whose `status.json` reads an active indicator (`minor` or above, or `maintenance`) also reads two small public lists of the same status page, `/api/v2/incidents/unresolved.json` and `/api/v2/scheduled-maintenances/active.json` (maintenances in progress or being verified), each with the same 32 KiB cap as the feed; nothing else is read. `provider_status` then carries these optional fields, each left out (not `null`) when its list was not read:
  - `active_incidents` — the number of unresolved incidents; `max_incident_impact` — the highest impact among them (`none`, `minor`, `major`, `critical`; `none` when there are none); `incident_updated_at` — the latest `updated_at` among them (absent when there are none, or when any unresolved incident has no update time). The recommendation reads it as "has any active incident moved lately" (D45).
  - `active_maintenances` — the number of maintenances in progress.
  - `basis` — what an active `indicator` (`minor` or above, or `maintenance`) rests on: `incident` (at least one unresolved incident), `maintenance` (no incident, at least one maintenance in progress), or `components_only` (neither: only component states make the page read as active). Absent when the indicator is not active or a list could not be read.
  - `affected` — at most 3 names the provider published, 80 characters each: the components named by the unresolved incidents, then by the maintenances (an item that names no component contributes its own title). Present only when both lists were read.

  A list that fails, is not JSON of the expected shape, belongs to another page, or is over the cap (`too_large`) only leaves its own fields out; the `indicator` is kept as read and `error_detail` still describes only the `status.json` read. A list that answers 401, 403 or 429 is a refusal: the other list is not asked for in that refresh either. After any failed list (a refusal, `too_large`, a timeout, a bad body) the two lists rest: they are not asked for again for 15 minutes (an hour after a refusal), doubling with each further failure, at most a day; meanwhile refreshes read `status.json` only and the scope fields are absent. Reading both lists again clears the count. A first discovery reads `status.json` only, so the fields appear from the next refresh. Pages of other platforms that answer `status.json` (for example incident.io, told apart by the page id format and the missing `time_zone` in `status.json`) and the Instatus, Better Stack and Google feeds get no extra request and no scope fields. A refresh of an Atlassian Statuspage feed therefore makes 3 requests to the status page (`status.json` and the two lists) while it reads an active indicator, 2 when the first list is refused, and 1 when it reads `none` or `unknown` or while the lists rest (then no scope field is present); any other feed makes 1.
- Without a fixed mapping, the first lookup queues a check of whether `status.<host>` is delegated to Statuspage (at most once a day per host, see [Background reads](#background-reads-stale-while-revalidate)); that lookup answers as before discovery, and a verified source appears from a later lookup. A connected feed is answered from its cache at once (`pending` with `indicator: null` before its first read) and refreshed behind the lookup once its statement would read as `stale` (older than 2 hours), not again within 15 minutes of the last attempt. The review cron also reads feeds on its own schedule (D44): every feed of the fixed mapping is registered and read whether or not the host was ever looked up, as is every feed a lookup registered through discovery, so a first lookup of a mapped host usually gets a `fresh` statement at once. A quiet feed is read about hourly. A failing feed is retried after 15 minutes, doubling with each further failure up to one hour (shorter than the 2 hours after which a statement reads as `stale`), and every 15 minutes while its last successful statement was active, so a status page that errors during a large outage does not silently drop out. A refusal (`http_401`, `http_403`, `http_429`) is never retried another way: it waits one hour, doubling up to 24 hours. The lookup path follows the same rule. Hosts that share one feed address are read once per run; a database lock on the feed address keeps the cron and the web process from reading one feed at the same time. One cron run reads at most 180 feeds and starts none after 100 seconds (nor the scope lists of a feed after that; the two lists of one feed are read together or not at all, D46), and at most one request per second goes to one status host. While the cached `indicator` is active (`minor` or above, or `maintenance`), both the lookup and the cron treat the read as due after 15 minutes instead, so, while feed reads succeed, a problem the provider has resolved stops reading as active within about 15 minutes rather than up to 2 hours (D43). While feed reads fail, the resolution cannot be read, so the last successful statement remains a reason to wait for up to 2 hours after it (D46). Feed reads identify themselves with the `AgentHelpNetwork` user agent. A failed refresh keeps the previous statement and its `fetched_at`, records why in `error_detail`, and is retried later; the statement reads as `stale` only once it is more than 2 hours old (D46).
- `indicator: maintenance` means the provider's status page reports scheduled maintenance in progress (Statuspage-format `maintenance`, Instatus `UNDERMAINTENANCE`, Better Stack `maintenance`). It is provider-announced work, not an incident: `recommendation` and `next_checks` treat it like `minor` (`wait_provider_incident`, check `provider_scope`), with a `provider_scope` text that says scheduled maintenance (the same text is used, with `provider_maintenance_only`, for any active indicator whose `basis` is `maintenance` with no incident, D55). Like `minor`, it does not lead to `wait_provider_incident` when `basis` is `components_only` (a `major` or `critical` page still does; see [Recommendation](#recommendation)). Like the other values it describes the page-level state, not the user's target site.
- `indicator: none` means the provider's status API shows no active issue as of its last successful read; when that read is stale or the latest read failed, `indicator` is `unknown` instead (D76). It does not guarantee that a given agent's sign-in or access will succeed. Provider status never overwrites another source's data.
- `provider_source_state` is `feed_connected`, `official_page_only`, or `not_verified_by_current_methods`. With `official_page_only`, `official_status_page` gives only a source name and URL, not a current reading. For a few sites whose listed status page needs the user's own sign-in (D72; `SIGN_IN_STATUS_PAGES` in `ahn/status_refresh.py`), the object also carries `requires_sign_in: true`; it is omitted otherwise. AHN cannot read such a page, and a lookup with `task_step=status_check` then answers with the status sentence T3-S: hand `next_action.status_url` to your user instead of searching for the page. Where the page's own name says it covers only the provider's API or developer services (D80; `API_ONLY_STATUS_PAGES` in `ahn/status_refresh.py`, for example `DHL API Service Status` for `dhl.com`), the object carries `covers: "api"`, also omitted otherwise: read it as the state of those services, not of the whole site. The page-only mapping (`OFFICIAL_STATUS_PAGES` in `ahn/status_refresh.py`; for example Netflix, Webex, Adobe, and Microsoft 365) is used only when no feed is connected for the host. A lookup of a status page's own host (for example the host in a mapped site's `provider_status.source_url`) shows the feed or the link mapped for the site that page belongs to, only when the host has no mapping of its own and the page host is not ambiguous between different feeds, and only for a host that serves status alone (the page is at the root, or the host name says status or health; a page under a path of a general site is not used) (D70). Feeds come from the fixed `SOURCES` mapping in the same file or from the Statuspage discovery above; [Status source curation](#status-source-curation) describes how both mappings are built and how to count them. `not_verified_by_current_methods` means the current discovery methods could not verify a source, not that the provider has no status API. When the status host's own `robots.txt` disallows the feed for automated readers (D50; many hosted status pages disallow `/api/` for every user agent by default), or could not be read because of a server error or a timeout (unless a file read successfully less than 48 hours earlier is still in force, RFC 9309 section 2.4), there is no `provider_status` for that host: AgentHelpNetwork does not request the feed, and `official_status_page` links the status page instead. The same link is given while the feed's host has no stored robots decision yet (a newly registered feed, or one outside the interim list) and the feed is not shown: the link is the mapping's `status_page_url`, never a reading, and the verdict does not change. That absence says nothing about the provider's health: open the page yourself.
- `provider_discovery_attempted_at` is the time the host's last automatic discovery actually ran (not when it was queued), or `null` if none is recorded.

### Status source curation

Both fixed mappings in `ahn/status_refresh.py` are edited by hand; nothing a script finds is applied automatically. Count them from the code (`len(SOURCES)`, `len(OFFICIAL_STATUS_PAGES)`) instead of trusting a number written here.

- `SOURCES` maps a host to a feed. Each source has a `kind` that picks the parser and the read cap (`FEED_KINDS`): `statuspage` (page address plus `api/v2/status.json`; incident.io pages answer it too), `instatus` (`summary.json`), `betterstack` (`index.json`), and `google_gmail`. A feed is listed only when its address returned 200 over https, stayed under the kind's cap, and was accepted by that parser; the address is always the page address plus the kind's fixed path (a feed that redirects is recorded at its final address). `OFFICIAL_STATUS_PAGES` maps a host to a publisher status page that loaded as a real status page but has no feed the parser reads; a link is never turned into an indicator. A source name states its scope when the page covers only part of the host (for example one cloud or one product family).
- Keys are plain lowercase hosts without `www.` that pass the eligibility check above. No host is in both tables, URLs are https, and no placeholder or status-aggregator address is accepted (`tests/test_status_mapping.py`, no database or network).
- `scripts/discover_status_sources.py` is the curation aid. It is not run in CI and the service never imports it; its output goes to the ignored `work/status-discovery/<batch>/` folder. For a list of hosts it skips hosts that are already mapped, that are not eligible, or that are `www.<apex>` names, then proposes candidate status pages from the DNS target of `status.<apex>`, status links on the host's own `OFFICIAL_PATHS` pages, an optional local copy of the MIT-licensed Statusphere list, and common name patterns. A candidate whose name does not resolve to a public address is never contacted. A candidate is a `feed` when the Statuspage parser accepts its `/api/v2/status.json` (the script looks for that format only; `--classify` names other products such as Instatus and Better Stack so that a feed of another kind can be added by hand), a `link` when it answers 200 with a page that reads like a status page, and unverified when it refuses the script (401/403/429/202, a bot wall).
- Ownership evidence is decided by rule and recorded with each row: **A** the status host is on the publisher's registered domain (shared hosting such as `statuspage.io`, `github.io`, or `instatus.com` never counts); **B** the publisher's own `status.<apex>` redirects to it; **C** a publisher documentation page already in `OFFICIAL_PATHS` links to it, and that page's URL is recorded. A candidate with none of the three, and a page that refused the script without one, is written as `needs_review` and stays out of the mapping.
- Etiquette matches `scripts/verify_official_paths.py`: one HTTPS request per second overall (a smaller `--min-interval` is refused), 10 s timeout, the curation User-Agent, redirects followed by hand with every hop checked for a public address, and only status hosts plus publisher documentation pages already in the official-path table are read. The site's own front page is never probed and no `robots.txt` is fetched. An interrupted run resumes from `cache.json` without repeating requests. `--classify` names the product behind each linked page, and `--candidates-csv` runs the same checks on addresses found by hand.
- Before the script requests a feed path (`/api/v2/status.json`, `/summary.json`, `/index.json`) it reads that status host's `/robots.txt` and applies the service's own decision (`ahn.feed_robots`, RFC 9309). A path the file disallows, or one that cannot be decided because the file could not be read, is not requested and is recorded as `robots_blocked` or `robots_unreadable`; a missing or 4xx robots.txt allows it.
- The rules of the script itself are covered by `tests/test_discover_status_sources.py` (no network; a stub network drives the end-to-end cases).

### Lookup activity

`lookup_activity` appears from the first lookup of an eligible public apex host; lookups of its `www.` name count toward the apex and show the apex's band. Instead of exact counts it gives `volume_band` (`1-4`, `5-9`, `10-49`, `50+`), `period_days: 7`, `unit: requests_not_agents`, and `trend: increased` when the conditions are met (otherwise `null`). It does not count independent agents or failures. Lookup volume and provider status are never copied into `observations` or `incidents`.

### Access profile layer

`access_profile` is the host's **declared** agent policy, read from its own `robots.txt` and `llms.txt`. It is `null` outside public mode, for hosts that are not eligible public apex hosts, and if the layer fails; a read failure never turns a lookup into an error. A `www.<apex>` lookup returns the apex's profile, from the same cached read. The files are read in the background, never while a lookup waits ([Background reads](#background-reads-stale-while-revalidate)); until the first read of a host finishes, the profile is the `pending` shape below.

```json
{"robots_status": "pending", "robots": null, "robots_detail": null, "llms_txt_status": "pending", "llms_detail": null,
 "read_host": "example.org", "source_urls": {"robots_txt": "https://example.org/robots.txt", "llms_txt": "https://example.org/llms.txt"},
 "fetched_at": null, "freshness": "pending", "retry_after_seconds": 5, "note": "Declared crawler policy read from ...",
 "content_use": {"status": "not_read", "reason": "pending", "source_url": "https://example.org/robots.txt", "fetched_at": null, "freshness": "pending"}}
```

- **What is read.** For the profile itself, only `/robots.txt` (cap 256 KB) and `/llms.txt` (cap 4 KB, presence only), on the eligible apex host or its own `www.` alias. A 3xx is followed only when it points to the same path on the host's own `www.` alias (one hop); any other redirect is recorded as `redirected` and not followed. If the apex `robots.txt` read ends as `error`, `refused`, `redirected`, or `invalid`, `https://www.<host>/robots.txt` is read once as a fallback and replaces the apex result when it ends as `ok`, `absent`, or `too_large`. `llms.txt` is read from the host that supplied `robots.txt`. One attempt makes at most five HTTPS requests: the apex `robots.txt`, one hop to the `www.` alias, the `www.` fallback, `llms.txt`, and its hop. The [site-declared files](#site-declared-files-site_declared-d59) are read after that, each only where `robots.txt` allows it.
- `robots_status`: `ok`, `absent` (404/410), `redirected` (a 3xx other than the single hop to the host's own `www.` alias, not followed), `refused` (the host's edge answered 401/403/429/503 to a plain robots.txt read from a public data-center address — a strong hint, not a declaration), `invalid` (a web page came back instead of a policy file: soft 404), `error` (transport failure: DNS, TLS, connect, timeout, or any HTTP status other than 200, 3xx, 401, 403, 404, 410, 429, and 503), `too_large` (over 256 KB), `not_public` (the host does not resolve only to public IPs), or `pending` (no read has finished yet; a read is queued). A transport failure never overwrites an earlier answer: `robots_status`, `robots`, `llms_txt_status`, `llms_detail`, and `fetched_at` keep the last definitive read, `freshness` becomes `stale`, and `robots_detail` carries the failure label. `error` therefore appears only before any definitive read, with `freshness: pending`. `robots` is non-null only when `robots_status` is `ok`. When the status is not `ok`, the policy layer is **inconclusive**, not a block — except `refused`, which the recommendation treats as a hint to prefer the official path.
- `robots_detail` / `llms_detail`: a short machine label saying why a read ended as it did — `http_<status>` for any HTTP answer (`http_200`, `http_401`, `http_403`, `http_404`, `http_410`, `http_429`, `http_500`, `http_503`, ...), `redirect:<host>` (the whole label cut to 32 characters; `http_3xx` when the redirect names no host), `dns_timeout`, `dns_failed`, `connect_error` (refused or unreachable), `connect_timeout`, `read_timeout`, `tls_error`, `read_error`, `html_body`, `too_large`, `not_public`, or `invalid_input`. When a connection cannot be made, the read moves on to the host's other resolved addresses (IPv4 first, at most three, all attempts within one connection-time budget of 4 seconds); a failure after the connection is established is reported as is and not retried on another address. After a transport failure, `robots_detail` describes that failure while the rest of the profile shows the last definitive read. Both can be `null` for a profile cached before these labels existed.
- `read_host`: the host whose URL was read — the looked-up apex host (also for a `www.<apex>` lookup), or its `www.` alias when the `www.` fallback replaced the apex result. A followed one-hop redirect from the apex to its own `www.` alias does not change it: `read_host` and `source_urls` keep the apex, whose URL redirects to the file that was read.
- `robots.rules[].crawl_delay` (seconds, from the applicable group) and `robots.rules[].disallow_paths` (up to 6 sample disallowed path prefixes, 80 characters each) qualify a `root_allowed: true`: a host may allow `/` while disallowing search, cart, or account paths. `robots.sitemaps` lists up to 5 declared sitemap URLs; `robots.wildcard_crawl_delay` and `robots.wildcard_disallow_paths` describe the `*` group. Only these parsed values and the read status are stored; the rest of the file is not.
- `robots.rules`: one entry per agent token the service knows, computed with RFC 9309 precedence (longest matching rule wins, Allow wins a tie) and lenient prefix matching of user-agent names: a group whose user-agent name has 3 or more characters also applies to every known token that starts with that name (case-insensitive). Groups follow RFC 9309 and Google's reference parser: a group is one or more User-agent lines and the Allow/Disallow lines after them, so Sitemap, Crawl-delay, Content-Signal, and unknown lines between User-agent lines do not split a group, a blank line alone does not either, and rules before the first User-agent line are ignored. One exception, where parsers disagree: when such a line is followed by a blank line before the next User-agent line (`User-agent: *` / `Crawl-delay: 10` / blank / `User-agent: BadBot` / `Disallow: /`), that User-agent line starts a new group, as Python's `urllib.robotparser` reads it; Google's parser merges the two and would block `*` as well. `robots.grouping_differs_by_parser` lists `*` and the agent tokens whose `explicit_group` or `root_allowed` would differ under Google's grouping (empty when the readings agree, and absent from profiles read before this field existed); `recommendation` never uses it, and `next_checks` then carries `robots_grouping_differs_by_parser`. `kind` is `user_agent`, `search_crawler`, or `training_crawler`. `explicit_group` says whether the file names a group for that token; `root_allowed` says whether `/` may be fetched; `disallow_count` is the number of non-empty Disallow lines that apply. Tokens without their own group inherit the `*` group. The token table is `AGENT_USER_AGENTS` in `ahn/access_profile.py`, one `(token, kind)` pair per token; count it from the code. Each token's spelling and `kind` follow the vendor's own documentation, whose address is recorded per token in `AGENT_SOURCES`. The few tokens that sites still name but that no vendor page confirms are in `UNCONFIRMED_AGENT_TOKENS` (all `training_crawler`). Each token belongs to one vendor (`AGENT_VENDOR`), and the recommendation reads a vendor's governing tokens: its `user_agent` tokens, or its `search_crawler` tokens when it documents no `user_agent` token ([Agent vendor](#agent-vendor-agent_vendor-d48), D48). A `training_crawler` token appears in `rules` and `agents_blocked` but never changes the recommendation. Group names are matched after Unicode dashes (U+2010 to U+2015, U+2212, U+FE63, U+FF0D) are read as `-`, so `perplexity‑user` names `Perplexity-User`, and, as in Google's parser, only the leading run of letters, digits, `-` and `_` of each name is used (`Claude-User/1.0` names `claude-user`). A line listing several agents separated by commas (`User-agent: Claude-User, ChatGPT-User`) names every one of them: the host plainly means them all. Google's parser reads only the first name (and reads `*,` or `*, Claude-User` as naming nobody: only `*` alone or followed by whitespace is its wildcard), so such a file lists the other tokens, or `*`, in `robots.grouping_differs_by_parser` (information only). At most 64 comma-separated names are read from one User-agent line (`MAX_AGENTS_PER_LINE`); the rest of that line is dropped, so a token listed after the 64th falls back to the `*` group. A group keeps each name once; this applies from the next read of a host after the 24-hour cache window. Lenient prefix matching also applies across related tokens: a group named `Diffbot` covers `Diffbot-User`, `Applebot` covers `Applebot-Extended`, and `MistralAI` covers all three Mistral tokens. A profile cached before the table changed keeps its old `rules` until the host is read again, which happens on the first lookup after the 24-hour cache window. **Status checks (D71).** An answer to a lookup with `task_step=status_check` and no failure signal (`error_class` and `failure_stage` both absent) leaves `robots.rules` out and gives `robots.rules_omitted`, the number of entries left out (the key is absent when there were none); every other `robots` field stays, and `recommendation`, `next_checks` and `summary_line` are computed from the full profile and are the same as without the switch. To get the rules, look up without `task_step=status_check` (or with a failure signal), unless they were folded because every value is the same (`rules_uniform`, below). `AHN_STATUS_CHECK_COMPACT=0` keeps `robots.rules` in status-check answers too. **Uniform rules (D94).** Where every token in `robots.rules` has the same `explicit_group`, `root_allowed`, `disallow_count`, `crawl_delay` and `disallow_paths` (typically a host with no group naming an agent: only a `*` group, or none) and `agents_blocked` is empty, the answer leaves `robots.rules` out and gives `robots.rules_omitted` (the count) and `robots.rules_uniform` (the shared `explicit_group`, `root_allowed`, `disallow_count`, plus `crawl_delay` and `disallow_paths` when set), which apply to every token the service knows. This applies to every lookup, with or without a failure signal or `task_step`; a status-check answer without a failure signal keeps the D71 shape (`rules_omitted` only). One differing token, or any token in `agents_blocked`, keeps the full `rules`. The verdict is computed from the full profile and is the same. The public incident detail (`GET /v1/incidents/{id}`) and the HTML search page always keep the full `rules`. `AHN_ROBOTS_RULES_FOLD=0` keeps the full `rules`.
- `robots.agents_blocked`: tokens with an explicit group that disallows the root. `robots.agents_allowed`: tokens with an explicit group that allows it. Nothing is said about tokens that are not listed. `robots.vendor_aliases_blocked` (D48): the names from the curated `VENDOR_ALIASES` table (retired or variant names sites use for a vendor's agent, such as `claude-web`; matched exactly) whose own groups disallow the root. These names are not tokens and never appear in `rules` or `agents_blocked`. The field is absent from profiles read before D48. `wildcard_root_allowed` is the `*` group's root decision, and `sitemap` says whether the file declares a sitemap. A file whose `*` group disallows the root while at least one agent user-agent or search-crawler token is named by no group (and no group that names such a token disallows the root) is reported through the recommendation and `next_checks` as `robots_wildcard_disallow`, never as "allows agents".
- `llms_txt_status`: `present` (including a file over the 4 KB cap, `llms_detail: too_large`), `absent` (including a soft-404 page, see `llms_detail: html_body`), `refused`, `error`, `redirected`, `not_public`, `pending`, or `not_read`. `not_read` means we did not request `/llms.txt` because the host's own `robots.txt` disallows it for us (`llms_detail: robots_disallowed`) or could not be read (`llms_detail: robots_unreadable`); it says nothing about whether the file exists, and the `llms_txt_present` code is absent for that host. `/robots.txt` itself is always read (RFC 9309, section 2.2.2). Only presence is recorded; the content is neither stored nor passed on.
- `source_urls`: the two file URLs on `read_host` (the apex, or its `www.` alias after the fallback); following them reaches the file that was read, directly or through the apex's own one-hop redirect. `fetched_at`: the last definitive read (UTC). `freshness`: `fresh` (a definitive read within 24 hours and no transport failure since), `stale` (older, or a transport failure since), or `pending` (no definitive read yet). `retry_after_seconds`: an integer only while `freshness` is `pending` and a read is queued, and absent otherwise (never `null`): the seconds to wait before one more lookup, never a polling interval. A `pending` profile whose only attempts so far failed (`robots_status: error`) carries it again once the one-hour retry is due. `note`: a fixed English caveat.
- **Cache and retry.** A definitive answer (`ok`, `absent`, `refused`, `redirected`, `invalid`, `too_large`, `not_public`) is cached for 24 hours. A transport failure (DNS, TLS, connect, timeout, unexpected HTTP status) is retried after one hour. A lookup never makes a network request: inside the cache window it answers from the cache, outside it it answers from the cache (or `pending`) and queues the read. Repeated lookups of one host share one queued read. Hosts on the public seed list `ahn/seed_hosts.txt` are pre-read by the review cron (`python -m ahn.auto_review`: 10 per 5-minute run by default, `AHN_WARM_BATCH`, `0` disables) and re-read about weekly, under the same limits (`ahn/profile_warm.py`); hosts not yet read go first, and this pre-read tries a host whose last attempt was a transport failure again after 24 hours, including a host that already had an answer (a lookup of that host retries after one hour).
- **Declared policy is not an access guarantee.** `root_allowed: true` does not mean a request will succeed; CDNs, bot filters, logins, and rate limits can treat a user-directed agent differently from a crawler. An Allow line does not replace the site's terms. Conversely, if the token your own requests send is in `agents_blocked`, the expected behavior is to stop retrying that page and hand off to the user or use the official path; send `agent_vendor` to get that answer from the recommendation itself.

#### Content-use preferences (`content_use`)

`access_profile.content_use` reports how the host says its content may be **used**, as declared inside the same `robots.txt`: Cloudflare Content Signals (`Content-Signal: search=yes, ai-input=yes, ai-train=no`) and IETF AIPREF (`Content-Usage: train-ai=n`, draft-ietf-aipref-attach-05 with the draft-ietf-aipref-vocab-08 vocabulary; both drafts). It is parsed from the bytes already read for the robots rules, so it adds no request. It is information only: it is not an access rule, not permission, and not a legal reading, and it never changes `recommendation`. Whether a preference covers a user-directed agent is not settled by either format and is up to each agent's operator.

When something is declared:

```json
"content_use": {
  "status": "declared", "reason": null, "formats": ["cloudflare_content_signal"],
  "signals": {"search": "yes", "ai_input": "unset", "ai_train": "no", "use": "reference"}, "usage": null,
  "scope": "all_paths", "path_specific_samples": [],
  "named_groups": [{"agents": ["ChatGPT-User", "Claude-User"], "other_agents": 1,
                    "signals": {"search": "yes", "ai_input": "no", "ai_train": "no", "use": null},
                    "usage": null, "path_specific_samples": []}],
  "named_groups_total": 1, "vendor_default_hint": true,
  "ai_input_declared_no": true, "ai_input_no_agents": ["ChatGPT-User", "Claude-User"], "ignored_keys": [],
  "vocab": "ahn-content-use/1; Cloudflare Content Signals; IETF AIPREF draft-ietf-aipref-attach-05 / draft-ietf-aipref-vocab-08 (drafts)",
  "source_url": "https://example.org/robots.txt", "fetched_at": "2026-10-20T09:00:00Z", "freshness": "fresh",
  "note": "Content-use preferences the host declares in robots.txt ..."
}
```

Otherwise the answer is the compact shape, without the vocabulary and note strings:

```json
"content_use": {"status": "not_read", "reason": "robots_refused", "source_url": "https://example.org/robots.txt",
                "fetched_at": "2026-10-20T09:00:00Z", "freshness": "fresh"}
```

- `status`: `declared` (at least one `Content-Signal` or `Content-Usage` line in a group), `none_declared` (`robots.txt` was read and has none, or there is no `robots.txt`: `reason: robots_absent`), or `not_read`. **Not reading is never reported as `none_declared`.** `not_read` carries `reason`: `pending` (no read yet), `robots_<robots_status>` (`robots_refused`, `robots_invalid`, `robots_redirected`, `robots_too_large`, `robots_not_public`, `robots_error`), or `read_before_content_use`: there is no current result for the `robots.txt` the profile describes, because the profile was cached before this field existed, or the stored result was written for a different file (its `robots_sha256` differs from the row's, for example after a rollback rewrote the row) or by another parser version (`vocab`). The next read fills it.
- `signals` (Cloudflare) and `usage` (AIPREF) describe the `User-agent: *` group for the whole site: a line with no path, `/`, or `/*`. Values are normalized to `yes`, `no`, or `unset` (`y`/`n` become `yes`/`no`; a signal the host did not state is `unset`, which grants and restricts nothing). `signals.use` is Cloudflare's experimental fourth signal (`immediate`, `reference`, `full`) or `null`. Either object is `null` when the `*` group has no site-wide line of that format. `formats` lists the formats found anywhere in the file.
- Several statements for the same scope resolve to the most restrictive one (`no` over `yes`; `immediate` over `reference` over `full`), the AIPREF rule (vocab-08 section 5.1), applied to repeated `Content-Signal` lines too.
- Parsing follows each format: `Content-Signal` names and values are read case-insensitively and only `yes`/`no` count. `Content-Usage` follows vocab-08: keys are case-sensitive, a value that does not parse as a dictionary (an uppercase key, an empty member) leaves every category `unset`, unknown keys are ignored, a value other than the tokens `y`/`n` leaves that category `unset`, parameters are ignored, and a repeated key keeps its last value. `ignored_keys` lists up to 5 key names that were not used, each a short token (`unparsable` otherwise).
- Groups are exactly the groups the robots rules are judged by (`split_groups`, with its default reading including the blank-line exception), so a `Content-*` line never ends a group's agent lines. A line before the first `User-agent` line belongs to no group and is ignored. `named_groups` (up to 5; `named_groups_total` counts them all) lists declarations in groups that name other user agents, identical declarations folded into one entry, the ones declaring `ai-input=no`/`ai-use=n` first. `agents` holds only names from the service's agent-token table (`AGENT_USER_AGENTS`, vendor spelling, user-directed agents first, at most 8); every other name is only counted in `other_agents`.
- A line whose value starts with a path other than `/` or `/*` applies to part of the site only: it is never folded into `signals`/`usage`. At most 3 such paths (80 characters each) are kept **in total**, the `*` group's first, then the named groups' in order. `scope` is `all_paths` when the `*` group has a site-wide line, `path_specific` when it has only path-scoped lines, otherwise `null`.
- `vendor_default_hint` is `true` when the `*` group's signals are exactly the line Cloudflare's managed `robots.txt` inserts by default (`search=yes, ai-train=no`, with or without `use=reference`, nothing about `ai-input`). It is a hint that the line may be a CDN default the site owner never chose, not a finding: an owner can write the same line.
- `ai_input_no_agents` lists the user-directed agent tokens (`kind: user_agent`) whose **effective** site-wide preference is `ai-input=no` or `ai-use=n`, computed with the same group rule as `robots.rules`: a token named by any group (with or without `Content-*` lines) takes only the declarations of the groups that name it, and only a token named by no group falls back to the `*` group. It is computed from every group before any cap. `ai_input_declared_no` is `true` when the list is not empty, and then `next_checks` carries the informational `content_use_ai_input_declared_no`. `recommendation` is computed without `content_use`.
- `source_url`, `fetched_at`, and `freshness` are the robots read's own. A transport failure keeps the last declaration with `freshness: stale`, exactly as for `robots`.

#### Site-declared files (`site_declared`, D59)

`access_profile.site_declared` reports what the host publishes **for agents at standard locations**, read next to its `robots.txt`: its API catalog, its text-and-data-mining reservation, and (experimental) its catalog of MCP servers. It helps an agent take the host's own official route from the start instead of retrying a blocked page. It is information only: not an access rule, not permission, and not a legal reading. `recommendation`, `next_checks`, `summary_line`, and `next_action` are computed without it. Links are reported as the host published them; the service does not open or check them.

```json
"site_declared": {
  "api_catalog": {"status": "declared", "source_url": "https://example.com/.well-known/api-catalog",
    "apis": [{"anchor": "https://developer.example.com/apis/foo_api",
              "service_desc": ["https://developer.example.com/apis/foo_api/spec"],
              "service_doc": ["https://developer.example.com/apis/foo_api/doc"],
              "status": ["https://developer.example.com/apis/foo_api/status"]}],
    "apis_total": 1, "items_total": 0},
  "tdm": {"status": "declared", "source_url": "https://example.com/.well-known/tdmrep.json",
    "rules": [{"location": "/", "tdm_reservation": 1}], "rules_total": 1, "root_reservation": 1, "any_reserved": true},
  "mcp_discovery": {"experimental": true, "status": "declared", "source_url": "https://example.com/.well-known/ai-catalog.json",
    "servers": [{"identifier": "urn:air:example.com:mcp:weather", "card_url": "https://example.com/mcp/server-card"}],
    "servers_total": 1, "spec_version": "1.0"},
  "fetched_at": "2026-10-31T04:05:06Z", "freshness": "fresh", "note": "Files the host publishes for agents at standard locations: ..."}
```

- **What is read.** Three paths, each fixed by its specification, never a guessed one: `/.well-known/api-catalog` ([RFC 9727](https://www.rfc-editor.org/rfc/rfc9727), sent with `Accept: application/linkset+json`), `/.well-known/tdmrep.json` ([W3C TDMRep](https://www.w3.org/community/reports/tdmrep/CG-FINAL-tdmrep-20240510/) Community Group final report), and `/.well-known/ai-catalog.json` (the AI Catalog that the MCP Server Card extension, SEP-2127, names for domain-level discovery). Each is requested only where the host's own `robots.txt`, read just before, allows that path for the `AgentHelpNetwork` user agent (the same gate as `llms.txt`, D56: a readable file decides by its rules, a missing file or a 4xx other than 429 allows, anything else forbids; unlike `llms.txt`, a `robots.txt` the host refused with 401 or 403 stops these reads, `robots_refused`), from the host that supplied `robots.txt` (a redirect from the apex to its own `www.` alias is followed once, as for `robots.txt`, so a file can take two requests), once per profile read (the profile's 24-hour cache window), with the same pinned-IP reader, timeouts and redirect rule as `robots.txt`, a 64 KB cap, and 0.5 seconds between two of these reads. The reads run after the profile row is written, still in the background, so the `robots.txt` answer of a first lookup does not wait for them. Only the parsed fields below are stored; the files are not.
- Each of `api_catalog`, `tdm`, and `mcp_discovery` has `status` and `source_url`. `status` is `declared`, `none_declared` (the file is missing: 404 or 410, `reason` `absent`; or it parses with nothing to report: `empty_catalog`, `empty_file`, `no_mcp_entries`), or `not_read` with `reason`: `pending` (no read yet, or the profile row is written and its standard files are still being read; the next read replaces it), `read_before_site_declared` (the profile was read before this field existed, or while `AHN_SITE_DECLARED=0` had it switched off; the next read fills it), `store_failed` (the files were read but their result could not be stored; the next read tries again), `not_public` (the host is not eligible, nothing requested), `robots_refused` (the host refused even `robots.txt` with 401 or 403, so these three files are not requested from it), `robots_disallowed`, `robots_unreadable`, `html_body` (a web page answered for the path: a soft 404 or a bot challenge, so neither a file nor its absence), `redirected` (a redirect other than the one hop to the host's own `www.` alias, not followed), `invalid_format` (not the specified JSON shape), or a read label such as `http_403`, `too_large` or `connect_timeout`. Text a file publishes (an identifier, a name, a location pattern, a URL) is dropped when it contains a control character (C0, DEL, C1) or a bidirectional formatting character, never cleaned up and shown. **Not reading is never reported as `none_declared`.** Other fields appear only when `declared`; empty lists are left out.
- `api_catalog`: `apis` lists up to 10 Linkset contexts that carry RFC 8631 links, each with `anchor` (the API it describes, `null` if absent) and up to 3 URLs per relation in `service_desc` (machine-readable description such as OpenAPI), `service_doc` (documentation for people), `service_meta`, and `status`; `apis_total` counts them all. `items` lists up to 10 `item` bookmark URLs (`items_total` counts them) and `nested_catalogs` up to 3 `api-catalog` links to further catalogs. URLs are kept as published (a relative one resolved against the catalog's URL), only `http`/`https`, without credentials, at most 300 characters.
- `tdm`: `rules` lists up to 10 rules of `tdmrep.json` in file order (`rules_total` counts them), each with `location` (the path pattern, at most 120 characters), `tdm_reservation` (`1` rights reserved, `0` not reserved, `null` for any other value, which TDMRep reads as unset), and `tdm_policy` (a URL, when given). `root_reservation` is the value for the path `/` (the first matching rule, TDMRep section 6.1; left out when no rule matches or its value is unset), and `any_reserved` says whether any rule reserves. `headers` lists up to 5 `tdm-reservation`/`tdm-policy` HTTP response headers (TDMRep section 6.2) seen on the responses to the files this read requested anyway (`robots.txt`, `llms.txt`, and the files above), each with the `path` it came on; no request is made for them. A header makes `tdm` `declared` even when `tdmrep.json` is missing; `file_status` and `file_reason` then keep what the `tdmrep.json` read itself found (for example `none_declared` / `absent`). The values are quoted, not judged: whether a reservation applies to a given use is not decided here.
- `mcp_discovery` (**experimental**, `experimental: true`): the AI Catalog entries whose `type` is `application/mcp-server-card+json`, up to 5 (`servers_total` counts them), each with `identifier` and either `card_url` (the hosted Server Card) or, for a card given inline, `inline_card: true`, its `name`, and up to 3 `remote_urls`. The card itself is not fetched: read it yourself before connecting, and verify it against the server's live metadata as the extension advises. `AHN_MCP_DISCOVERY=0` stops this read and leaves `mcp_discovery` out of the answer.
- `fetched_at` and `freshness` are the profile read's own. `note` appears when at least one file is `declared`. `AHN_SITE_DECLARED=0` stops all three reads and leaves `site_declared` out of the answer. The field is not in the offline bundle or Export v1.
- Cloudflare Content Signals (`Content-Signal:` in `robots.txt`) are reported in [`content_use`](#content-use-preferences-content_use), not here.

### AHN server check (`ahn_check`, D67)

Information only, added after the recommendation is decided: it changes none of `recommendation`, `next_action`, `next_checks` or `summary_line`, with one exception (D85): when the lookup reports `error_class=site_access` and this check was refused too (see the `hand_off_to_human` row of [Recommendation](#recommendation)), the answer is `hand_off_to_human` with reason `edge_refusal_confirmed`, and this answer's `note` says so. The same stored measurement may inform the optional `cause` (D73), which is also information only. The field exists only while the operator has set `AHN_SITE_PROBE=1` (default off; with it off the response is byte-for-byte what it was) and only for an eligible public apex host that is registered. It reports what AHN's own server received when it requested the host's home page (`GET /`) with the `AgentHelpNetwork` user agent, no cookies and no sign-in, from a data-center address (`vantage.kind: datacenter`; a different network can get a different answer). If that request is answered by a redirect to the host's own `www.` name, one more request goes to the www name (two at most, never a third), and only when the www name's own `robots.txt` verdict for `/` is fresh (under 24 hours) and allows the home page; otherwise the redirect itself is the result, and when there is no fresh verdict for the www name its profile read is queued so that a later check can follow. When the www request is made, `outcome`, `http_status`, `bot_defense` and `edge_vendors_seen` describe the www answer and `redirect.followed_www` is `true`; `redirect.to_relation` and `redirect.path_class` are then the codes of the last redirect seen. Any other redirect is recorded and not followed. The documentation example hosts (`example.com`, `example.net`, `example.org`) get a `not_measured` view with `not_measured_reason: not_eligible` that is built in memory: nothing is stored or requested.

- **When it runs.** Unless the host's own `robots.txt` disallows `/` for `AgentHelpNetwork` (or for `*`); an absent file (404) or any other 4xx answer except 401/403 does not disallow. A `robots.txt` that is refused (401/403) or cannot be read (5xx, timeout) is treated as disallowing, and nothing is requested. The verdict (`home_gate`) is decided in memory while the profile is read, stored with it, and good for 24 hours; with no fresh verdict nothing is requested (`not_measured_reason: robots_stale`). During a lookup the request is tried synchronously for at most 3 seconds in total, with at most 4 such requests at a time per web process and concurrent lookups of one host share a single request. If it does not finish in time, it runs at the next background pass (kind `site_probe`, lowest priority, no delay) and the answer says `status: pending`. How often a host is requested is governed by internal politeness limits (a minimum spacing per host, hourly and daily caps, back-off after a refusal or challenge). They are configuration and may change; they are not a promise.
- **Shape.** `status` is `measured`, `pending` or `not_measured`; `basis: ahn_server`; `vantage`; `ua_token`; `path_kind: home`; `fingerprint_version`; `note` (on a measured view it ends with "freshness is the age of measured_at." (D102); `pending` and `not_measured` views have no `freshness`, so they do not say it). When measured: `measured_at`, `age_seconds`, `freshness` (`fresh` when `measured_at` is within 24 hours, else `stale` up to 8 days; the age is `age_seconds`), `outcome` (`reachable`, `redirected_same_host`, `bot_challenge`, `refused`, `rate_limited`, `login_wall`, `redirected_offsite`, `server_error`, `unreachable`, `other_status`), `http_status` (only a real 100 to 599 status; any other number is `other_status` with no code), `response_ms`, and where they apply `bot_defense` (`vendor` of `cloudflare`, `datadome`, `perimeterx`, `aws_waf`, `vercel`, `generic_captcha` or `unknown`; `signal`; `confidence`), `edge_vendors_seen` (a provider's presence marker, not a challenge), `redirect` (`followed_www`, `to_relation`, `path_class`; never the path) and `login_signal`. Fields that do not apply are left out, never null. A `pending` view carries `retry_after_seconds` (60, unless the answer's `access_profile` is itself pending with its own `retry_after_seconds`, in which case it is that same number so the answer gives one wait): ask again once after that. A host whose `robots.txt` AHN has never been able to read (`access_profile.robots_status` `error`, no `fetched_at`, no `retry_after_seconds`) and that has no stored check gets `status: not_measured` with `not_measured_reason: robots_unreadable` instead (D99): no home-page check can start without a readable `robots.txt`, so there is no wait to offer. `AHN_D99_UNREADABLE_NOT_PENDING=0` restores `pending` only together with `AHN_D103_FAILED_PROFILE_NOT_PENDING=0`: D103 covers the same host, so both switches must be `0` for the earlier answer. The same view is shown when no check is stored and the profile's last read failed with no robots.txt verdict newer than 24 hours (a host read once and failing since, D103); it is built for the answer only and nothing is stored. `AHN_D103_FAILED_PROFILE_NOT_PENDING=0` restores `pending`. One request ends after 8 seconds of wall-clock time at the latest, whatever the host sends. When `not_measured`, `not_measured_reason` is one of `robots_disallowed`, `robots_refused`, `robots_unreadable`, `robots_stale`, `not_eligible`, `budget`, `backoff`, `disabled`.
- **What is kept.** Codes only: never the page, a header value, a cookie or a path. The current row per host is deleted 30 days after the check and daily counts after 35 days (see the privacy policy). Fingerprints are versioned (`ahn-fp/1`), each with its source URL and check date in `ahn/probe_fingerprints.py`.
- **MCP.** `check_incident` adds one line to the first text block when a measurement exists, for example `AHN server check just now: 403, bot challenge (DataDome).` followed by the data-center caveat. `structuredContent` carries the same `ahn_check` object.
- **Automatic stop.** If the robots.txt refusal rate among control hosts (seed hosts that are not measured) rises more than 3 percentage points over the baseline taken before the first check, for two days running, or status-feed 403/429 counts double, list-driven checks stop; so do they when the bandwidth guard is not normal or has no recent record.
- **Refusals, retries and the board history (D68).** A refusal is not a failure: a 401, 403, 429 or 503 answer, a bot challenge or a login wall takes the host off the list-driven checks for 7 days (flat; a `Retry-After` neither lengthens nor shortens it), with one exception (D83): a bot challenge, a 401 without a sign-in request or a 403 that comes after any result other than a refusal (an answer, a failure or no check) is checked once more after 24 hours (or its `Retry-After`, if longer, up to 7 days), and every check after that waits 7 days; a 401 with a sign-in request is a login wall and waits 7 days. That first, shorter wait is what an early `cause.recheck_after` shows (D86: a one-time update gave first refusals stored before D83 the same wait); the verdict rules, `recommendation` and `next_action` do not change. In a list-driven check, a 5xx other than 503 or a failure to connect (DNS, connection, TLS, timeout) is asked once more after the usual pause before it counts; a check that asked again never follows a www redirect, so it is still two requests at most. The address of every request is resolved first and a private, loopback, link-local, metadata or other non-public address is refused before any connection; IP literals and names outside the public suffix list are never checked. For the hosts whose AHN-check history is kept (the curated part of the seed list, the official-paths table, the status mappings, the public check list `ahn/probe_hosts.txt` and the consumer-paths table), each list-driven check is also recorded in that history as codes only: answered, refused, or the kind of failure, the HTTP status code, and for an answer a response-time range (`lt1s`, `1to3s`, `3s_plus`), never the exact time, the page or a path. A failure is a statement that AHN could not connect from this one point, not that the site is down; it opens a period on the board only after 2 failed checks at least 45 minutes apart, and one answer ends it. This history changes neither this field nor the recommendation.

### Official paths layer

`official_paths` comes from a curated table in code (`ahn/official_paths.py`) and has `name`, `api_docs`, `developer_portal`, and `note`, plus an optional `access` bundle for some hosts ([below](#access-bundle-official_pathsaccess-2026-10-20)); any of `api_docs`, `developer_portal`, and `note` can be `null`, and the whole object is `null` for hosts not in the table. A subdomain matches its apex entry (`api.github.com` gets the `github.com` entry). An entry with only a `note` (for example, "No public API") is shown but does not count as an available official path for the recommendation or `official_path_available`; that needs `api_docs` or `developer_portal`. Only hosts whose public developer documentation was actually checked are listed. `null` does not mean no official path exists. Listing is not an endorsement or affiliation, and using an official API usually requires the user's own credentials and the provider's terms.

How the table is curated and verified (2026-10-18):

- **Absence means "not curated", not "no API".** `official_paths: null` only says this service has not curated the host; the agent can still look for the provider's own developer path.
- Keys are lowercase registrable apex hosts that pass `valid_host`; a subdomain resolves to its nearest apex key (`api.github.com` → `github.com`). Public suffixes such as `gov.uk`, `go.kr`, or `police.uk` are never keys, because unrelated bodies beneath them would inherit one entry (the police data portal is keyed `data.police.uk`). `tests/test_official_paths.py` checks the keys against a list of public suffixes that is independent of `PUBLIC_SUFFIXES_2`, so a gap cannot pass on both sides. Aliases are listed only when they are real separate hosts (`x.com` / `twitter.com`).
- URLs are publisher-owned developer documentation, API references, or developer portals only: no third-party mirrors, blog posts, or marketing pages. A URL on a domain other than the key's (`learn.microsoft.com`, `developers.google.com`, the publisher's GitHub organisation) must be declared in `PUBLISHER_DOMAINS` in `scripts/verify_official_paths.py`; the pure test `tests/test_official_paths.py` rejects undeclared domains.
- **Scope: sites that people or agents open to do work.** Hosts that exist to serve other sites (CDN, DNS, ad-tech, tracking, asset and media delivery, link shorteners, update servers) get no entry, even when their operator publishes documentation, because an agent does not open them to do a task. Tenant-site hosts such as `herokuapp.com` or `myshopify.com` are also left out, since the host's owner is not the platform, as are shared-hosting suffixes such as `pages.dev` or `workers.dev`.
- A host without a public API gets a `note` only when the note is factual and useful (for example that a public API was retired, plus the official status page). URLs are never guessed.
- Verification: `scripts/verify_official_paths.py` sends one HTTPS GET to every distinct URL in the table, including URLs inside notes: 10 s timeout, at most one request per second overall, User-Agent `AgentHelpNetwork-curation/0.1 (+https://agenthelpnetwork.com/en/policy)`, one retry only after a transport error, 429, or 5xx. `--hosts a.com,b.org` checks only those table keys and `--json FILE` writes per-URL and per-host results. Redirects are followed for verification only. A URL passes with final status 200, an `https` final URL on a publisher-owned host, no redirect to a sign-in page or bot challenge, and no "not found" page title. `blocked:*` means the publisher refused the automated check (401/403/429, a WAF 202, or a challenge page); it is not evidence that the page is gone. Nothing else is fetched: no `robots.txt`, no login pages, no crawling.
- The script is not run in CI, so CI never depends on third-party sites. Run it by hand whenever the table changes. The 2026-10-18 full-run result is recorded at the end of this section.
- `ahn/seed_hosts.txt` starts with the table's aggregate-eligible keys in table order and then lists further public hosts (`tests/test_profile_warm.py`).
- Full run 2026-10-18 (a dated record: the table has grown since, and the entries added on 2026-10-19 were checked the same way with `--hosts` rather than in a new full run): 546 hosts in the table at that time (540 with URLs); of 722 distinct URLs, 707 passed, 13 were `blocked:*`, and 2 failed. Every URL that did not pass belongs to an existing entry and was kept, since nothing showed the page is gone. Bot challenge or 403: `binance.com` (api_docs), `coupang.com`, `ebay.com`, `nih.gov` (api_docs), `pexels.com`, `salesforce.com`, `stackexchange.com` and `stackoverflow.com` (stackapps.com), `stlouisfed.org` (portal), `unsplash.com`. Connection dropped: `tumblr.com` (curl with the same User-Agent gets 200). Every newly added entry was confirmed with a 200.

#### Access bundle (`official_paths.access`, 2026-10-20)

A link to the documentation is often not enough: an agent that hit a bot wall or a login wall also needs to know which credential the official path takes, where the user gets it, whether there is a free quota or a sandbox, where the spec and the rate limits are, whether the publisher runs an MCP server, and where the terms are. For some hosts `official_paths` carries that as `access`. It comes from a second curated table in code (`OFFICIAL_ACCESS` in `ahn/official_paths.py`); nothing is read at lookup time. Hosts without a bundle get no `access` key at all (never `null`), and inside a bundle every unknown field is left out, so answers stay small.

```json
"official_paths": {
  "name": "Stripe", "api_docs": "https://docs.stripe.com/api", "developer_portal": "https://docs.stripe.com/", "note": null,
  "access": {
    "auth": [{"method": "api_key", "source_url": "https://docs.stripe.com/api/authentication"}],
    "key_signup_url": "https://docs.stripe.com/keys",
    "rate_limits_url": "https://docs.stripe.com/rate-limits",
    "sandbox_url": "https://docs.stripe.com/sandboxes",
    "openapi_url": "https://raw.githubusercontent.com/stripe/openapi/master/openapi/spec3.json",
    "official_mcp": [{"endpoint": "https://mcp.stripe.com", "doc_url": "https://docs.stripe.com/mcp"}],
    "terms": {"url": "https://stripe.com/legal/ssa",
              "quote": "If User uses an AI Agent to access the Stripe Services, User is solely responsible for each action initiated by or through the AI Agent."},
    "verified_at": "2026-10-20"
  }
}
```

| Field | Meaning |
| --- | --- |
| `auth` | List of `{method, source_url}`, one per method the publisher's page at `source_url` documents. `method` is `none` (some endpoints answer without credentials), `api_key` (a static key or app token from the publisher's console), `oauth1`, `oauth2` (a user authorizes the app), `device_code` (OAuth 2.0 device authorization, RFC 8628: the user approves on another device, no page automation), or `pat` (a personal access token that acts as the user). |
| `key_signup_url` | The publisher's page that explains how to get a key or token. Console pages behind a sign-in are not listed. |
| `free_tier` | `{quote, source_url}`: the publisher's own sentence stating how much can be used free of charge or on what condition (for example a default daily quota), copied verbatim (at most 200 characters). Pricing slogans, free-trial adverts, and price-list headers are never used. |
| `rate_limits_url` | The publisher's page on rate limits or quotas. |
| `sandbox_url` | The publisher's page on a test or sandbox environment. Only the link: test values are never copied. |
| `openapi_url` | A machine-readable OpenAPI or Swagger document at a publisher-owned URL. |
| `official_mcp` | List of `{endpoint, doc_url}`: an MCP endpoint exactly as the publisher's page at `doc_url` gives it. This service never connects to it. |
| `feeds` | List of one to three official RSS or Atom feed URLs on a publisher-owned domain (news, releases, changelog). Same information as the pages, in a form that needs no page automation. Optional; the service never requests these URLs, they are curated links. |
| `llms_full_url` | The publisher's own `llms-full.txt` (the full documentation as one text file), at a publisher-owned URL. A curated link: the service does not read it. |
| `docs_repo` | The publisher's official documentation repository (a publisher-owned URL, or on `github.com` inside the publisher's declared organisation). |
| `data_export_url` | The publisher's official data export or dump page (for example a public dataset or bulk download). |
| `terms` | `{url, quote}`: the publisher's terms or policy page for the API, and one sentence or clause copied verbatim from it (at most 200 characters). |
| `verified_at` | UTC date on which every URL and quote in the bundle was last read. |

- **Terms are linked and quoted, never interpreted.** `terms` has no verdict, stance, or summary such as "automation allowed"; the quote is one excerpt, not legal advice and not the whole document. Read the linked page.
- **Publisher-owned, read, never guessed.** Every URL is on the key's registrable domain (public-suffix aware, as for the table), on a domain declared for that key in `PUBLISHER_DOMAINS`, or, on `github.com` and `raw.githubusercontent.com` where one domain serves many owners, inside the publisher's own organisation declared in `PUBLISHER_GITHUB_ORGS` (both in `scripts/verify_official_paths.py`). Each page was fetched and read on `verified_at`. A page that refused the read (401, 403, 429, or a challenge) leaves its field out; the refusal is not worked around.
- **Stale bundles are hidden.** A bundle whose `verified_at` is more than 90 days old is left out of answers until it is verified again; the rest of `official_paths` stays.
- **No change to the advice.** `access` does not change `recommendation` or `next_checks`. That holds for `feeds`, `llms_full_url`, `docs_repo` and `data_export_url` too (D60): they are links for the caller to use, never read by this service, and a test pins that filling them leaves `recommendation` and `next_checks` identical. Each URL is an https URL of at most 300 characters; `feeds` holds at most 3. The advertised `outputSchema` of `check_incident` lists the four fields as optional and, like every object in it, accepts further keys (D58).
- Hosts of the same publisher and API share one bundle (`chatgpt.com` with `openai.com`, `notion.com` with `notion.so`, `twitter.com` with `x.com`, `wikimedia.org` with `wikipedia.org`). Count bundles with `len(OFFICIAL_ACCESS)`.
- Verification: `python scripts/verify_official_paths.py --access-only [--hosts a.com]` reads every page URL in the bundles with the etiquette above (every hop must also resolve only to public addresses), checks that each quote and each MCP endpoint appears verbatim in the page's visible text (whitespace and typographic quotes folded), and checks that `openapi_url` is an OpenAPI or Swagger document. MCP endpoints themselves are never requested. The pure rules (shape, method list, 200-character cap, publisher-owned domains, no future date) also run in CI in `tests/test_official_access.py`.
- First run 2026-10-20 (a dated record): bundles for `github.com`, `stripe.com`, `openai.com`, `youtube.com`, `slack.com`, `notion.so`, `reddit.com`, `x.com`, `wikipedia.org`, and `cloudflare.com`; 54 distinct URLs, all 200 from a publisher-owned host; 28 quotes and MCP endpoints, all found. Left out because the page refused the read: OpenAI's terms and key console (`openai.com`, `platform.openai.com`: 403), Reddit's rate-limit wiki (403). Left out because the page has no readable text without scripts: Notion's developer terms.
- Second run 2026-10-20 (a dated record): bundles for 40 more publishers, chosen from table keys that have an API reference or developer portal, in agent-demand order (D35): `gitlab.com`, `bitbucket.org`, `google.dev`, `stackexchange.com` (with the alias `stackoverflow.com`), `discord.com`, `telegram.org`, `zoom.us`, `asana.com`, `figma.com`, `twilio.com`, `vercel.com`, `netlify.com`, `digitalocean.com`, `sentry.io`, `datadoghq.com`, `huggingface.co`, `anthropic.com`, `perplexity.ai`, `mistral.ai`, `groq.com`, `together.ai`, `deepseek.com`, `x.ai`, `openrouter.ai`, `elevenlabs.io`, `supabase.com`, `linear.app`, `shopify.com`, `paypal.com`, `squareup.com`, `spotify.com`, `twitch.tv`, `kakao.com`, `tosspayments.com`, `replicate.com`, `coinbase.com`, `plaid.com`, `mongodb.com`, `sendgrid.com`, and `render.com`. 136 distinct URLs, all 200 from a publisher-owned host; 30 quotes and MCP endpoints, all found. Left out because the page refused the read: Stack Exchange's API terms, Discord's developer terms and policy, and x.ai's legal page (403). Left out because the text appears only after scripts run, or because the address is not https: Twitch's terms, Kakao's developer terms (redirect to http), and the MCP endpoints of Atlassian, Vercel, and Datadog (not in the page's visible text). Hosts read and not bundled because their documentation pages have no readable text without scripts: `airtable.com`, `dropbox.com`, `hubspot.com`, `cohere.com`, `naver.com`, `data.go.kr`, `mapbox.com`, and `nasa.gov`.

#### Consumer paths (`official_paths.consumer`, 2026-10-31, D61)

A developer API is the path for building on a site's data. For a task in a person's own account on that site (refill a prescription, pay a bill, change a booking) it may not help: many such APIs are for partners, while some reach the user's account through OAuth (see `access`). For some hosts with a clear consumer service, `official_paths` also carries `consumer`: where the site itself sends its customers.

```json
"official_paths": {
  "name": "...", "api_docs": null, "developer_portal": "https://developer.example.com/", "note": null,
  "consumer": {
    "paths": [
      {"kind": "customer_help", "url": "https://www.example.com/help", "source_url": "https://www.example.com/"},
      {"kind": "official_app", "url": "https://apps.apple.com/us/app/example/id123", "source_url": "https://www.example.com/app"}
    ],
    "verified_at": "2026-10-31"
  }
}
```

| `kind` | Meaning |
| --- | --- |
| `customer_help` | The site's own help centre or contact page. A phone number is never copied into the answer: the page that lists it is linked instead. |
| `official_app` | An App Store or Google Play listing that the site's own page (`source_url`) links to. Only the listing identifier is kept. |
| `entry_link` | A public entry point the site itself links to for a common customer task. |

- `consumer` is present only when curated and current (verified within 90 days, the same rule as `access`); otherwise the key is absent, never `null`. A host with no developer entry may be curated too (D64): its `official_paths` answer then carries `name` (the host) and `consumer` only, `api_docs`, `developer_portal` and `note` are `null`, and the verdict is the one for a host with no official path (`use_official_path` needs a developer path). At most 6 paths; each `url` and `source_url` is an `https` URL of at most 200 characters.
- **`topic` and the list (D102).** A path may carry `topic`, one of `returns`, `orders`, `contact`, `help`, `account`, `shipping`, when the table says what the page is for (left out, never `null`; any other value is invalid). It is information for choosing among several pages: `customer_url` is chosen as before (the first `customer_help`) and ignores `topic`. ### Host facts layer

`host_facts` carries **registry facts about the domain**: which public government domain list names it and the organisation that list gives, and the registry rule that a suffix is reserved for government bodies. It is a fact about who registered a name. It does not say that a site, page or link is genuine or safe, it does not change `recommendation`, and a missing field does not say anything about the site. It is **left out of the response entirely** (no `null`) unless a government list or a government-only suffix rule applies to the host, so ordinary hosts get no extra bytes.

```json
{
  "host_facts": {
    "government_registry": {
      "status": "listed",
      "registry": "us_dotgov",
      "registry_name": "U.S. .gov domain list (CISA)",
      "domain_type": "Federal - Executive",
      "organization": "Department of the Treasury",
      "suborganization": "Internal Revenue Service",
      "state": "DC",
      "list_version": "2026-10-20",
      "source_url": "https://github.com/cisagov/dotgov-data/blob/main/current-full.csv",
      "license": "CC0-1.0",
      "fetched_at": "2026-10-20T18:05:00Z"
    },
    "suffix_rule": {
      "suffix": "gov",
      "rule": "registration_limited_to_government",
      "text": "Only verified U.S. government organizations can register a .gov domain.",
      "source_url": "https://get.gov/domains/eligibility/"
    },
    "note": "Registry facts about a domain: which public government list names it, and whether its suffix is reserved for government bodies. They are not a judgement about the site, any page or any link."
  }
}
```

A `.go.kr` host has the suffix rule and no list entry, because this service reads no list of individual `.go.kr` domains:

```json
{
  "host_facts": {
    "suffix_rule": {
      "suffix": "go.kr",
      "rule": "registration_limited_to_government",
      "text": "Under the KRNIC domain name management rules, .go.kr is for administrative agencies and legislative or judicial agencies.",
      "source_url": "https://krnic.kisa.or.kr/jsp/eng/policy/domainNewRules.jsp"
    },
    "note": "Registry facts about a domain: ..."
  }
}
```

- **`government_registry`** is present for names under `.gov` (U.S. list) and `.gov.uk` (UK list) once that list has been loaded. `status` is `listed`, or `not_in_list_version` when the name is under the list's suffix but not in the loaded version. The second is a statement about the list version shown in `list_version`, not a finding about the site: lists follow the publisher's schedule, so a newly registered name can be missing. `registry` is `us_dotgov` or `uk_govuk`. `organization`, `suborganization`, `domain_type` and `state` are the list's own values, only when the name is listed and the list gives them. The UK file has the domain name only, so UK entries carry no organisation. `list_version` is the UK list's "as of" date, or for the U.S. list the UTC date on which this service first received the current file contents (the publisher updates the file daily when something changes). `fetched_at` is the last time the list was checked successfully. `source_url` is the publisher's page, `license` is `CC0-1.0` (U.S.) or `OGL-UK-3.0` (UK), and `attribution` carries the licence's required statement for the UK list: "Contains public sector information licensed under the Open Government Licence v3.0."
- **`suffix_rule`** is present for `.gov`, `.gov.uk` and `.go.kr`: the registry's own rule that only government bodies may register under the suffix, with the rule's source. `.or.kr`, `.co.kr` and other suffixes have no rule here.
- **Which hosts.** The answer is for the same host as the other host-level layers: an eligible public apex host, and `www.<apex>` as its apex (`www.irs.gov` is answered as `irs.gov`). Other subdomains and tenant hosts (`tenant.irs.gov`), and the suffix zones themselves (`go.kr`), get no `host_facts`: a list names registered domains, not what runs under them.
- **Where the data comes from.** Public whole-file downloads by the review cron, never during a lookup: the U.S. registry's `current-full.csv` (CISA, `cisagov/dotgov-data`, CC0-1.0) is checked every 24 hours with a conditional request, and the UK "List of .gov.uk domain names" (GOV.UK, Open Government Licence v3.0) is found through the GOV.UK content API and checked every 30 days. Only those publishers are contacted, never a site on a list. The files' contact columns are dropped: the U.S. security contact email and city are read and not stored.
- **A bad download changes nothing.** A failed request, a redirect, a file over the size cap (8 MB U.S., 2 MB UK), changed columns, too many unusable rows, too few rows, or fewer than half the rows of the stored version keeps the stored data, logs a warning with a short label, and is retried after 6 hours. `fetched_at` then shows how old the stored copy is.
- **Lookups read the database only.** `AHN_HOST_FACTS=0` turns both the downloads and the field off.
- Attribution for the UK list: Contains public sector information licensed under the Open Government Licence v3.0.

Setting `AHN_D98_ROBOTS_REFUSAL_HANDOFF=0` (D98) makes every answer equal to the one before it: a `site_access` lookup on a host whose plain `robots.txt` read was refused and that lists no developer path then gets `unknown` with `robots_fetch_refused` again. On by default; an unknown value counts as `0`. With the D98 row `next_action.do` is `hand_off_to_human`, `next_action.url` and `retry_after_seconds` are `null`, `next_action.customer_url` is present when a customer page is curated, and the `summary_line` says the site's edge refused both the caller and AHN's plain `robots.txt` read. A host with a listed developer path (`use_official_path`), a robots.txt that was read, another `error_class` or `failure_stage`, no failure signal, and a `task_step=status_check` answer are answered as before; `ahn_check` keeps its D67 note.

Setting `AHN_D101_NO_PATH_HANDOFF=0` (D101) makes every answer equal to the one before it. On by default; an unknown value counts as `0`; it also needs `AHN_PROCEED_WITHOUT_FAILURE` and `AHN_FAILURE_KIND_LINES` on. With the D101 row `next_action.do` is `hand_off_to_human`, `next_action.url` and `retry_after_seconds` are `null`, and the first line ends "if one more try fails, tell your user" (one more attempt at the page, not a repeat of the lookup), so the line and `next_action.do` agree; with a customer page it hands the user `next_action.customer_url` (kept in the answer). Rows U7-O and U9-O, and a hand-off with a customer page on a host that also lists a developer path (O7-H), keep the "API work: official_paths" pointer. A customer page on another site, a 5xx with a customer page, a failure that is not a `service_error`, a failure-free lookup and a pending read are answered as before. Also with the switch on: when the `edge_refusal_confirmed` hand-off rests on an `ahn_check` older than a day (`ahn_check.freshness` is `stale`), its first line says so (also needs `AHN_PROCEED_WITHOUT_FAILURE` and `AHN_FAILURE_KIND_LINES` on, and never for a `task_step=status_check` lookup). Limits: counts of `hand_off_to_human` in the `recommendation.action` distribution (adoption figures) rise and those of `unknown` fall from this change on, so ratios across it are not comparable.

**Robots block, caution, clear (D48).** For a profile with `robots_status: ok`, the robots part of the answer comes from the vendor states defined under [Agent vendor](#agent-vendor-agent_vendor-d48). With an accepted `agent_vendor` (that vendor's state):

| State | Robots part | Reason |
| --- | --- | --- |
| `explicit` | block | `robots_blocks_agents` |
| `alias` | caution | `robots_names_vendor_alias` |
| `wildcard` | caution | `robots_wildcard_disallow` |
| `allowed`, while some `user_agent` or `search_crawler` token is explicitly disallowed (another vendor's, or this vendor's own search crawler) | clear | `robots_blocks_not_your_agent` |
| `allowed`, nothing explicitly disallowed | clear | `robots_allows_agents` |

Without `agent_vendor` (or with a value outside the list), the states of the twelve vendors are combined (`other` is not among them). The answer is never more permissive than the answer for any vendor, because the caller may be the blocked one, and never stricter than the answer for every vendor:

| Vendor states | Robots part | Reasons |
| --- | --- | --- |
| every vendor `explicit` | block | `robots_blocks_agents` |
| some vendors `explicit` | caution | `robots_blocks_some_agents`, then `robots_wildcard_disallow` when a vendor is `wildcard` |
| none `explicit`; some `alias` or `wildcard` | caution | `robots_names_vendor_alias` when a vendor is `alias`, then `robots_wildcard_disallow` when a vendor is `wildcard` |
| all `allowed`, a `user_agent` or `search_crawler` token explicitly disallowed (no vendor's governing token) | clear | `robots_blocks_not_your_agent` |
| all `allowed`, nothing explicitly disallowed | clear | `robots_allows_agents` |

So the declared-block answer (`stop_declared_block`, or `use_official_path` high) needs the caller's own token, or, without a vendor, every vendor's. In the 2026-10-22 sample of 161 readable `robots.txt` files, no host got a stricter answer than before for any vendor or for an unknown one.

**Failure signal (D63).** `error_class` or `failure_stage` (any value, including `unknown`). The optional signal codes `http_status`, `challenge`, `retry_after` and `via` are not failure signals for the recommendation: they are only counted (D47). A lookup made after a failed request should send `error_class`. **`robots_status: absent`** (HTTP 404 or 410) declares no restriction for any agent (RFC 9309); it is not an access guarantee, and site terms and platform rules are separate. `robots_allows_agents` carries a separate sentence for it. `AHN_PROCEED_WITHOUT_FAILURE=0` restores the answers from before D63: the recommendation, the `next_checks` codes and texts, the summary line, `next_action.url` and `customer_url`. `AHN_PROCEED_WITHOUT_FAILURE=d65` (D66) answers a lookup that reports no failure like one that reported `site_access`: the same recommendation and `next_checks` (including `locate_failure_stage`), so a host with a listed developer API gets `use_official_path`, and a `proceed` row says that no block is declared and that a refusal the caller saw came from its tool, the site's edge or a login, to be told to its user. A lookup with `task_step` `status_check` or `preflight` (exact, lowercase) says it was not refused and keeps the D63 answer, and with `d65` those two words do not filter observations. A failure signal always wins over the word. The search page without a chosen error class counts as `status_check`; the home card shows the answer an agent gets. An empty value, `1` and `d63` are the D63 answers (the default); `0` is the answers from before D63. No field, enum or schema changes.

**The previous rule** still applies when `AHN_VENDOR_AWARE_BLOCK=0`, to a profile read before D48 (no `robots.vendor_aliases_blocked`), and when a governing token that the answer needs is missing from a cached profile's `rules` (every vendor's without `agent_vendor`, that vendor's own with it). A missing token is never read as allowed. Under the previous rule a **declared block** (robots block) means `robots_status` is `ok` and at least one `user_agent` or `search_crawler` token has an explicit group (a group that names it) that disallows the root. Training-crawler blocks appear in `agents_blocked` but do not trigger it. A **wildcard-only disallow** (robots caution) means `robots_status` is `ok`, no declared block applies, and at least one `user_agent` or `search_crawler` token that no group names inherits a `*` group that disallows the root (`User-agent: *` with `Disallow: /`); groups that name other tokens (an allowed search crawler, a blocked training crawler) do not prevent it. It is not a declared block and is never reported as "allows agents": treat it as not inviting automation, prefer an official path, and do not read it as permission.

### Summary line and next action

Every lookup answer also carries `summary_line` and `next_action` (D51). Both are computed from `recommendation`, `access_profile`, `official_paths` and `provider_status` after the answer is decided; they never change `recommendation` or `next_checks`, which remain the verdict.

- `summary_line` is one English sentence pair of at most 200 printable ASCII characters (401 for the two-sentence line of a robots-based status check, D79), chosen from a fixed table of templates in `ahn/response_guide.py`. The only value filled in is a whole number of seconds. It never contains the hostname, an agent token, a URL, or any text taken from the site or the provider. The same inputs always give the same line.
- **Failure-kind lines (D87).** In a lookup that reports a failure (`error_class` or `failure_stage`), the sentence of two kinds of row follows the kind of failure; `recommendation`, `next_action`, `next_checks`, `cause` and `links` are those of the row. A `proceed` answer for `error_class=service_error` says that no block is declared (for P2: unless the caller's token is in `robots.agents_blocked`), that AHN sees hosts and not single pages so it cannot judge this page's 5xx, and to retry once later and tell the user if it persists (`SERVICE_ERROR_ROWS` in `ahn/response_guide.py`); where a customer path is curated (`next_action.customer_url` present) the sentence ends "tell your user and hand them next_action.customer_url" instead (`SERVICE_ERROR_CONSUMER_ROWS`), so the 5xx answer still points to the person's path; it no longer says that a refusal came from the caller's tool, the site's edge or a login. The `unknown` answer with `robots_blocks_some_agents` (`next_action.do` `stop_if_listed`) says that robots.txt blocks some tokens, including those in `next_action.stop_if_you_are` (the list holds only the listed vendors' root blocks, at most 16, so other tokens may be blocked too), to stop if the requests send one, and in either case not to switch tools or user agents to retry after a refusal but to tell the user (for `service_error`, the 5xx sentence takes the place of the second clause); it no longer says to send `agent_vendor`. Lookups without a failure signal, `task_step=status_check` lookups without a failure signal (the service never passes a failure to a status check, D69) and every other row keep their sentences. Only with the D63 sentences on.
- **No-response lines (D92).** When the same lookup also reports `failure_stage=before_target_response` (a timeout or a connection that never produced a response), the D87 `service_error` sentence no longer says "5xx": a `proceed` answer keeps its prefix and then says "No response came (timeout or connection). Check your tool and path; retry once later; if it persists, tell your user." (`NO_RESPONSE_ROWS`; with a curated customer path "Check your tool; retry once later, then hand your user next_action.customer_url.", `NO_RESPONSE_CONSUMER_ROWS`), and the `stop_if_listed` answer ends "Either way, no response came; check your tool, retry once later, then tell your user." (`FAILED_U3_NO_RESPONSE`). With `failure_stage=response_observed` or no stage the D87 5xx sentences are unchanged. Only the sentence changes; `recommendation`, `next_action`, `next_checks`, `cause` and `links` are those of the row, and `AHN_FAILURE_KIND_LINES=0` restores the sentences before D87. The `cause.line` of `your_side_likely` now says how old AHN's home-page check was ("AHN's home-page check 5 h ago was normal, but it does not see single pages; the cause may be on your side."), or "AHN's home-page checks that day were normal..." when the day's counts are the source; `hint`, `branch`, `confidence` and `basis` are unchanged.
- **Consumer-task and context wording (D93).** Wording only. The `use_official_path` sentences for a listed developer path with no curated customer path (rows O1, O7, O7-N, O7-K) now say the path is for API work and that a task in the user's own account goes to the user (O7: "Prefer that documented API or portal over page automation for API work; for a task in the user's own account, hand the step to your user."; O7-N and O1 the same meaning in their own words; O7-K also keeps "ask before signing up"). The `lookup_apex_host` sentence says to look up `next_action.lookup_host` "once, with the same fields you sent" (also in the `profile_not_read` next check), so the second lookup keeps the failure and the `task_step` of the first. The `cause.line` of `new_bot_defense` and `robots_now_disallows` names AHN's own check or read as the source ("AHN's home-page check sees a bot-defense page from a new provider (since ...); what your tool sees may differ.") instead of stating the site's state as a general fact. `recommendation`, `next_action` (`do`, `url`, `retry_after_seconds`, `customer_url`, `lookup_host`), `next_checks` (apart from that one sentence), `links` and `cause.branch`, `hint`, `confidence`, `basis`, `window`, `recheck_after` are those of the row; every `summary_line` stays within 200 printable ASCII characters.
- `next_action` always has `do`, `url` and `retry_after_seconds`:

| `do` | When | `url` | `retry_after_seconds` |
| --- | --- | --- | --- |
| `wait_for_provider` | `recommendation.action` is `wait_provider_incident` | The provider's status page | 900: the earliest time the provider statement can be read again |
| `hand_off_to_human` | `hand_off_to_human` | `null` | `null` |
| `use_official_path` | `use_official_path` | `official_paths.api_docs`, else `developer_portal` | While the profile is `pending`, its `retry_after_seconds`; else `null` |
| `stop_automation` | `stop_declared_block` | `null` | `null` |
| `proceed` | `proceed` | `null` (D65; D63 had given the customer page here); the customer page stays in `customer_url` when `official_paths.consumer` is curated | `null` |
| `retry_lookup_once` | `unknown` with `profile_pending` (first read queued) | `null` | `access_profile.retry_after_seconds` |
| `stop_if_listed` | `unknown` with `robots_blocks_some_agents` | `null` | `null` |
| `lookup_apex_host` | `unknown` with `profile_not_read` | `null` | `null` |
| `no_clear_action` | Any other `unknown`, including a `pending` profile whose earlier read failed | `null` | `access_profile.retry_after_seconds` when a read is queued, else `null` |

- `retry_after_seconds` is when to repeat the same lookup **once**. It is not a polling interval. If a repeated lookup answers `retry_lookup_once` again, read it as `no_clear_action`.
- `stop_if_you_are` is present only when `recommendation.reasons` contains `robots_blocks_some_agents`: the agent tokens from this service's token table whose vendor is explicitly disallowed at the site root. If your requests identify as one of them, treat it as a declared block and stop retrying pages. Send `agent_vendor` for an answer for your own agent.
- `lookup_host` is present only with `lookup_apex_host`: the site's main domain, whose declared policy covers the site. Look it up once, with the same fields you sent (`error_class`, `failure_stage`, `task_step`, `agent_vendor`), so the second answer is judged for the same failure and step.
- `customer_url` is present with `use_official_path`, with `proceed` and with the D85 and D98 `hand_off_to_human` (`edge_refusal_confirmed`, `edge_refusal_robots`), with the D101 `hand_off_to_human` (`no_path_after_failure`, `url` null), and with `no_clear_action` on rows U6, U7 and U9 (D97; `url` stays null), when `official_paths.consumer` is curated (D61): the site's own customer page (the first `customer_help`, else the first `entry_link`, else the first `official_app`), for a task in the user's own account, which a developer API may not reach. On the `use_official_path` rows that do not block pages (pending profile, or an official path with no robots block), `next_action.url` is the customer page too and the summary line names it first; a developer API is then mentioned as also listed. Where robots.txt or a refused read blocks pages (rows O2-O6), `url` stays the developer path and the summary hands `customer_url` to the user (D61), a page to hand over, not one to automate. If `customer_url` is absent, the host may simply not be curated; absence is not the same as "the site has no customer page".
- `url` is taken only from the curated official paths and verified status sources described above, and must be an `https` URL of at most 200 characters; otherwise it is `null`.
- `status_url` (D69) is optional and present only when a status page is known: `provider_status.source_url`, else `official_status_page.source_url`, as an `https` URL of at most 200 characters. For a lookup with `task_step=status_check` and no failure signal, `summary_line` is one of the status sentences (T1: the provider feed reports no active issue; T2: a feed is listed but gives no clear current state; T5: the feed could not be read just now (D76); T3: no feed is read, only an official status page is known (T3-S, D72: that page needs the user's sign-in, so hand `status_url` to the user; D77: `url` is never replaced by such a page); T4: no status page is known) unless `do` is `wait_for_provider`, `hand_off_to_human` or `stop_automation`, or the reasons include a robots block (`robots_blocks_agents`, `robots_fetch_refused`, `robots_wildcard_disallow`, `robots_names_vendor_alias`, `robots_blocks_some_agents`), whose sentences stay (D76: `use_official_path` rows take the exception below), as does a row waiting for a re-lookup (`profile_pending`); a subdomain lookup with no known status page also keeps the `lookup_apex_host` sentence, because the site-wide lookup may carry the provider status. `do`, `url`, `retry_after_seconds` and `recommendation` are the same as for any other lookup; `status_url` is added next to them (the D76 `url` exception below is the only difference). The status sentences name no host or URL.
- **Unreadable feed (D76).** When `provider_status.freshness` is `stale` (the last success is older than 2 hours, only failures were ever recorded, or a discovered source no longer verifies), `indicator` is shown as `unknown`, never `none`. One failed read after a recent success stays `fresh` with the indicator as read (D46). `fetched_at` stays the last success and an active indicator is left as it is. The `summary_line` of a status-check lookup is then the sentence saying the provider's status feed could not be read just now (T5; T5-N when no status page is known).
- `status_url_covers` (D102) is optional: `"api"` when `status_url` is the `official_status_page` and that page covers only the provider's API or developer services (`official_status_page.covers: "api"`, D80), so an agent does not take it for the status of the whole site. It is left out in every other case (never `null`), and the status-check sentences are as before.
- **Status checks on `use_official_path` rows (D76).** For a status-check lookup (no failure signal) whose `recommendation.action` is `use_official_path`, which is not waiting for a re-lookup (`profile_pending`), when a status page is known, `summary_line` is a T sentence and `next_action.url` is the status page. This is the only exception to `url` being unchanged by D69; `do` stays a function of `recommendation.action`. When a robots block is among the reasons and the status page is on the looked-up site's own registrable domain, nothing is overridden: the robots sentence and the original `url` stay. Other robots-block rows and `profile_pending` and `unknown` rows keep their sentence, `do` and `url`; only `status_url` is added.
- **Status wording (D81, amends D79).** Wording only, and only in a `task_step=status_check` lookup without a failure signal; `recommendation`, `next_action`, `links` and every other lookup are byte-for-byte as before. (1) In a robots-based row that names the developer path (`robots_blocks_agents`, `robots_blocks_some_agents`, `robots_names_vendor_alias`, `robots_fetch_refused`, `robots_wildcard_disallow`), the robots sentence after the status sentence ends "for anything beyond the status question, use the listed official developer path.": the developer path is not a way to check whether the site is up (a row with a curated customer page keeps its sentence). (2) When `official_status_page.covers` is `api`, the status sentence says so: `AHN reads no status feed for this site, so it cannot say whether it is up. Its status page, next_action.status_url, covers only the provider's API, not the whole site; check it there for API status.` (and, where the page is not pointed at, `AHN reads no status feed for this site, so it cannot say whether it is up; the status page it knows covers only the provider's API. Tell your user the site's status is unverified.`). (3) For a name that RFC 2606 or RFC 6761 reserves for documentation and tests (`example.com`, `example.net`, `example.org` and their subdomains; the top-level names `.example`, `.test`, `.invalid` and `.localhost`) the status sentence is `This is a reserved example domain (RFC 2606) for documentation; it runs no service with a status to check.` Each sentence stays within 200 characters and the merged line within 401 (`ahn-client` 0.6.6 accepts that).
- **Status first (D79, amends D76 and D77).** In a `task_step=status_check` lookup without a failure signal the first sentence of `summary_line` answers the status question: the provider's state when AHN has one, else the T sentence that fits (status page known but no feed, status page unknown, sign-in needed). A row that rests on a robots block (`robots_blocks_agents`, `robots_blocks_some_agents`, `robots_names_vendor_alias`, `robots_wildcard_disallow`, `robots_fetch_refused`) keeps its robots sentence unchanged, after the status sentence. Rows that wait for a re-lookup, wait for the provider, hand off to the user, or answer a subdomain with no status page keep their sentence as before. `do`, `url`, `status_url`, `retry_after_seconds`, `stop_if_you_are` and `recommendation` are unchanged. In front of a robots sentence the status sentence is a variant without "Check the site itself" (the robots sentence that follows says to stop or that pages refuse): `AHN knows no official status page for this site, so it cannot say whether it is up; tell your user its status is unverified.` when no status page is known, and `AHN reads no status feed for this site, so it cannot say whether it is up; tell your user its status is unverified.` when the page is on the looked-up site's own registrable domain (D76: that page is not pointed at). A status page on another domain keeps the T3 sentence. `proceed` rows get no prefix. The combined line is two sentences of at most 200 characters each, so it can be longer than 200 characters but not than 401; `ahn-client` accepts a server line up to 401 characters (0.6.6). The robots sentences no longer predict the outcome of page automation: "Page automation may be refused too".
- **Sign-in status pages and the P2 sentence (D77).** A status page with `requires_sign_in` is only ever `status_url`: on a `use_official_path` status check the T3-S sentence applies and `next_action.url` keeps the row's own value (the sentence says `do` and `url` are for any other step on the site); when a robots block is among the reasons, the robots sentence stays and only `status_url` is added. A `proceed` row decided by `robots_blocks_not_your_agent` without `agent_vendor` keeps its own sentence under a status check, because it ends in a condition (stop if your token is in `access_profile.robots.agents_blocked`); `status_url` is still added. For an alias group of sites mapped to one status feed, a lookup of that feed's own host shows the reading of the member with the most recent `fetched_at` (the smallest `site_host` among equals).
- **`status_url` on every lookup (D76).** Whatever the `task_step` or failure signal, `next_action.status_url` is present when a status page is known. It is informational and may be on a path robots.txt disallows; it is not an instruction to automate that page. No other field changes.
- If the three keys cannot be produced, they are left out and the rest of the answer is unchanged. The OpenAPI schema always lists `summary_line`, `next_action` and `links` as optional properties, whether or not they are present.
- **One status action (D96).** A `task_step=status_check` lookup asks "is it up", so its `next_action` is the status page, one action. When a status page is known and the row does not wait for the provider (`wait_for_provider`), hand off (`hand_off_to_human`), stop (`stop_automation`), wait for a re-lookup (`profile_pending`), rest on a robots block, or point at a page that needs the user's sign-in (T3-S), `next_action.do` is `use_official_path` and `url` is the status page, whether the row would have been `proceed`, `unknown` or `use_official_path` (D76 covered only the last); `summary_line` is the T sentence and `lookup_host` is left out. A failure signal (`error_class` or `failure_stage`) no longer turns the status answer off, except `error_class` `human_verification` or `login_auth`, which are handed to the user as before. A lookup that reports a failure keeps its D87 sentence wherever no status sentence applies, and on a robots block unless the status page is on another site. When the lookup reports a failure and the status page is on the looked-up host itself (the page that failed), `do` is `hand_off_to_human`, `url` is `null`, `status_url` stays, and `summary_line` is one of: `T1-F` "The provider's status feed reports no active issue (provider_status, see its fetched_at). That status page did not open for you; give your user this reading, not a guess."; `T2-F` "A provider status feed is listed (provider_status), but it gives no clear current state, and the status page did not open for you. Tell your user the status is unverified."; `T3-F` "AHN reads no status feed for this site, and its status page did not open for you, so AHN cannot say whether it is up. Tell your user the status is unverified."; `T5-F` "AHN could not read this provider's status feed just now, and the status page did not open for you. Tell your user the status is unverified.". A developer document (`api_docs`, `developer_portal`) is never the `url` of these answers; it stays in `official_paths` and `next_checks`. When no status page is known and the row's `url` would be a developer path, `url` is null and `do` is `hand_off_to_human` if a failure was reported (the sentence says the status is unverified) and `no_clear_action` if not. A lookup that reports a failure is never told to check the site itself. `recommendation`, `ahn_check`, `next_checks` and `feedback_token` are unchanged, and a lookup without `task_step=status_check` is answered as before. Where D95 and D96 both apply (a `service_error` status check), D96 decides `do`, `url` and `summary_line` and D95 still decides `recommendation`. `AHN_D96_STATUS_CHECK_ONE_ACTION=0` (on by default; an unknown value counts as `0`) gives the answer from before D96.
- **Unresolved incidents on an incident.io page (D100).** An incident.io status page can keep its overall `indicator` at `none` while an incident that names no component is open. When a Statuspage-format `status.json` body has the incident.io shape (a 26-character upper-case `page.id` and no `time_zone`), the scheduled reader, and the background refresh a lookup starts, also read that page's `/api/v2/summary.json` (same robots.txt decision, 32 KiB cap, no redirect, one request per second per host, at most 40 such reads per cron run; a lookup's background refresh has no per-run count) when the indicator reads `none`, and fills `active_incidents`, `max_incident_impact`, `incident_updated_at`, `affected` and (when the body lists them) `active_maintenances` from the incidents whose status is not `resolved` or `postmortem`. A Statuspage (Atlassian) page keeps its earlier behavior (no list is read while the indicator is `none`), and an incident.io page whose indicator is `minor` or above is read and answered as before D100 (no summary.json read). While such a page lists an unresolved incident it is read again every 15 minutes, like an active indicator. In a `task_step=status_check` lookup the status sentence follows: `T6` "The provider's status page lists an unresolved incident (provider_status.active_incidents), though its overall indicator reads operational. Check next_action.status_url; it may be partly affected." for a fresh `none` reading with `active_incidents` of 1 or more; `T1-U` "The provider's status feed's overall indicator reads operational, but AHN did not read its incident list. Check next_action.status_url before telling your user it is up." for an incident.io-shaped page whose list was not read (robots.txt, budget, failure); `T6-F` (T6 when the status page itself did not open for the caller) "The provider's status page lists an unresolved incident (provider_status.active_incidents), and that page did not open for you. Tell your user the service may be partly affected."; a `T1-U` page that did not open takes `T2-F`. `T1` ("reports no active issue") is kept for a page whose list was read and is empty, and for every Statuspage page. In any other lookup the same reading gets the `provider_scope` next check in place of `provider_clear`. `do`, `url`, `recommendation` (including the D45 wait) and the `summary_line` of a lookup that is not a status check are unchanged; only these sentences and the next check move. The stored marker is `status_cache.feed_platform` (`incident_io`, migration 038). `AHN_D100_INCIDENTIO_INCIDENTS=0` (on by default; an unknown value counts as `0`) stops the summary.json read and gives the answer from before D100.
- **Failure lines for a host with no listed path (D97).** With the D87 switch on, a lookup whose row is `U6` (the site refused AHN's plain robots.txt read), `U7` (robots.txt unread) or `U9` (no policy read for the host), none with a developer path listed (a customer path may be), that reports `error_class=service_error` takes a sentence that says what the failure is and what to do. After no response (`failure_stage=before_target_response`) `U7` says "No response came (timeout or connection), and AHN could not read the site's robots.txt either. Check your tool and path; retry once later; then tell your user." (`U9`: "...and AHN has no declared policy for this host..."; `U6`: "...and the site refused AHN's plain robots.txt read too..."; `NO_PATH_NO_RESPONSE_ROWS` in `ahn/response_guide.py`); after any other 5xx or no stage it says "AHN cannot judge a single page's 5xx, and could not read the site's robots.txt. Retry once later; if it persists, tell your user." (`NO_PATH_SERVICE_ERROR_ROWS`). Where a customer path is curated, `next_action.customer_url` is present on these rows and the sentences end by handing it to the user ("Check your tool; retry once later, then hand your user next_action.customer_url.", `NO_PATH_NO_RESPONSE_CONSUMER_ROWS`; "Retry once later; if it persists, tell your user and hand them next_action.customer_url.", `NO_PATH_SERVICE_ERROR_CONSUMER_ROWS`); a row with a curated customer path and no failure signal says "A customer page is listed (next_action.customer_url) for tasks a person does on the site." in place of "no official path is listed" (`NO_PATH_CONSUMER_ROWS`). `url` stays `null` and `do` stays `no_clear_action`. A failure of another kind, a `task_step=status_check` answer and a host with a developer path (`U7-O`, `U9-O`, D95) are unchanged. Only the `summary_line` changes, and `customer_url` is added on the `U6`/`U7`/`U9` rows when a customer path is curated; `recommendation`, `next_checks`, `cause`, `ahn_check`, `links` and `feedback_token` are those of the row. No new switch: `AHN_FAILURE_KIND_LINES=0` gives the answer from before D97. Every sentence is at most 200 characters.
- `do` never says more or less than `recommendation.action` (a status-check row is the exception: D76 makes `url` the status page; D96 makes `do` `use_official_path`, or `hand_off_to_human` when the status page itself failed). The four values that split `unknown` all mean that no verdict exists; they only say what can be done now.

### Failure cause (`cause`, D73)

A lookup that reports a failure (`error_class` or `failure_stage`) may carry an optional `cause`: why the step failed, as far as AHN's own stored host-level measurements say. It is information only. It is added after the recommendation is final, so `recommendation` and `next_action.do` are the same with it on or off. The field is left out (never `null`) when there is nothing to say, and for a lookup without a failure signal.

- `branch`: `policy_closed` (the host refuses automated readers), `transient` (a temporary problem), or `undetermined`.
- `hint`: `home_now_gated`, `persistent_refusal`, `robots_now_disallows` and `new_bot_defense` (policy_closed); `provider_incident`, `site_errors`, `recovered`, `rate_limited`, `others_failing_same_hour` (transient); `your_side_likely`, `no_measurement`, `home_gate_unconfirmed`, `terms_signal_changed` (undetermined).
- `confidence` (`high`, `medium`, `low`), `basis` (the stored sources used: `provider_status_events`, `outage_episodes`, `site_probe`, `site_probe_daily`, `lookup_signals_hourly`, `host_access_changes`), optional `window` (`from`, and `to` while still going on, UTC), optional `recheck_after` (only when a stored next measurement time exists: AHN's own next home-page check, not something the caller is asked to do, and left out when AHN does not measure the host: its `robots.txt` disallows AHN or refused the request for it, or the host is not eligible for a check), `line`: a fixed English sentence of at most 200 printable ASCII characters, filled with times only (no site text and no hostname reaches it), and `note`: the fixed sentence `Information only; follow next_action.`, present on every `cause` (D78). `note` and the wording of `line` carry no judgment: `branch`, `hint`, `confidence`, `basis`, `recommendation` and `next_action` do not depend on them.
- A refusal AHN measured (bot challenge, 403, login wall, rate limit on the home page) is never read as a temporary problem (D68). One refusal gives `undetermined` (`home_gate_unconfirmed`); `policy_closed` needs the next measurement to agree or at least two refusals in a row. A login wall does not raise the stored count of refusals in a row, so two login walls in a row are read from the daily totals of AHN's home-page checks instead (D84): the last two stored checks were both a login wall, with no other outcome between them (D84 takes every outcome that is not a login wall as the end of the run: a bot challenge, 403, 429, an unreachable answer, a `not_measured` row or a normal answer), and a day that holds a login wall and another outcome is not counted. This applies only to a lookup that names an `error_class` other than `login_auth`: for a step that failed on a sign-in the site is expected to ask for one, and a lookup with no `error_class` (only a `failure_stage`) is answered as before. Then `cause` is `policy_closed` / `home_now_gated` / `medium` with `basis` `["site_probe", "site_probe_daily"]` and the `line` `Likely a sign-in requirement: the site's home page showed a sign-in wall on AHN's last two checks.` It ranks where the unconfirmed sentence ranked: `persistent_refusal` and `others_failing_same_hour` still come first. When the stored count is already 2 or more and the latest check is a login wall, the `line` is `Likely a policy block: the site refused AHN's home-page checks at least twice in a row; the latest showed a sign-in wall.` Only `cause` changes; `recommendation`, `next_action` and `summary_line` do not. The `line` of `home_gate_unconfirmed` names whose check it was and the kind of the last refusal (`bot-challenge`, `HTTP` or `login-wall`; no count) and says that the next check is AHN's (`recheck_after` when that field is present); it is not an instruction to the caller. Since D82 it also tells how old that check is, with the same age as `ahn_check.age_seconds`, in the same words as the first line of the MCP answer (cut down, not rounded: "just now" under 5 minutes, minutes under an hour, hours under 24 hours, then days), and names the bot-defense provider (for example `DataDome` or `Cloudflare`) when the stored check has one; a provider code that names none is left out and nothing is guessed. Example: `Not determined: AHN's check 19 h ago saw a DataDome bot-challenge refusal; recheck_after is AHN's next check, not an instruction.` The `line` of `site_errors` and `recovered` (from AHN's own outage periods) says that AHN's own checks did not reach the site and that this can be AHN's network path alone, so it does not tell whether the caller's tool can reach the site; it gives no instruction such as "retry later" (D82). Example: `AHN's own checks have not reached the site (since 10-22 00:21 UTC); that can be AHN's network path alone, so it does not tell whether your tool can reach the site.` For these two hints `confidence` is `high` only when the period is confirmed and something other than AHN's own measurement saw the host failing between its start and its end (or now): a published observation with outcome `error` on a service-error incident, or at least three separate clients' lookups with a service error within one and the same hour of that period (clients are counted per hour and a client that looks again in a later hour counts again there, so hours are never added up); a report filed under the `www.` name of the host counts too. With only AHN's own measurement behind it, `confidence` is `medium`. `branch`, `hint` and `basis` are the same either way. The general `no_measurement` `line` says AHN has no usable home-page check of the site near the failure time (a check counts when the latest stored one is within 12 hours of it, or a daily total of that UTC day has one). When the stored reason AHN has no measurement is that the host's `robots.txt` disallows AHN (`robots_disallowed`) or refused AHN's request for it (`robots_refused`), `recheck_after` is never given (nor when the stored reason is `not_eligible`, a host that is not eligible for a check, which keeps the general sentence), and while that stored row is at most 24 hours old `line` says so; `basis` stays `["site_probe"]` (the stored row that gives the reason).
- A home-page check that ended at a redirect between the host's two names (`www.<host>` and `<host>`) that AHN did not follow (`ahn_check.outcome` `redirected_same_host` with `redirect.to_relation` `www_alias` and `redirect.followed_www` false) is not a normal check: the other name's own answer is unknown (D88). `cause` treats it as no measurement (`no_measurement`, or `terms_signal_changed` when a terms signal exists), never `your_side_likely`, and leaves out `recheck_after`: the next check may end at the same redirect (the other name's `robots.txt` can disallow it), so a home-page measurement is not promised. When `cause` falls back to the day's counts for an older `failed_at` (D91), the day's `redirected_same_host` count is never read as a normal check, whatever the stored check is now (the daily totals keep no redirect record, so a count may be such a redirect; a path or locale move on a site that has no other normal check that day loses that evidence, on purpose: no wrong "your side" hint is the priority); the day's other outcomes still are, so a `failed_at` on a day that also holds a real normal check can still give `your_side_likely`. The two-login-walls confirmation (D84) also reads a day of `redirected_same_host` as ending the run, for the same reason: it stays undetermined until the next check. This reaches lookups that named `site_access` or `service_error` without `failure_stage` `before_target_response`, which with a normal check used to get no `cause`: they now carry `no_measurement` (or `terms_signal_changed`). A followed www answer, a same-host redirect to another path or locale, and a check stored without a redirect record are unchanged. Only `cause` (and the MCP first line, which says "redirected to the host's other name (www/apex), not followed") changes; `recommendation`, `next_action` and `summary_line` do not. The Python client's local memory counts `your_side_likely` rows when it suggests changes, so it suggests less for such a host. The check schedule (D88): such a check keeps `consecutive_refusals` and `consecutive_failures` as the previous check left them and waits the same time a normal check does, so a refusal followed by an unfollowed redirect still counts toward two in a row, but only while that refusal is at most 7 days old (D91; a later refusal after older redirects counts as a first one and is checked again after 24 hours); this adds no requests.
- `failed_at` (optional, ISO 8601, with or without a UTC offset) names the time of the failure; without it the failure is taken to be now. It is received but not stored or counted. Raw measurements are kept 14 days, so a `failed_at` older than that is answered from the provider's status history alone. A value that cannot be used (bad format, or more than five minutes in the future) gives no `cause`, never a cause for a different time.
- `cause` never changes `summary_line` or `next_action` (D51); with it on or off they are the same.
- The caller's own codes (`http_status`, `retry_after`, `challenge`, `via`) are never read for `cause` (D47). Hourly counts of other lookups (`rate_limited`, `others_failing_same_hour`, `persistent_refusal`) are used only when at least three separate clients contributed.
- Hints from the history of changes in a host's declared access policy (D75). When AHN re-reads a host's `robots.txt`, `llms.txt` and standard files, or checks its home page, a field that differs from the value stored just before is kept as one row of short codes (host, time, field, old and new code), for 90 days; the first reading of a host writes nothing, and no file text, path or header value is stored. A hint looks at changes recorded from 14 days before `failed_at` to 24 hours after it, and only while the field still has the changed value. `robots_now_disallows` (`high`; one change is enough): the caller's vendor tokens (`agent_vendor`), or AHN's own token when no vendor is given, went from allowed to disallowed for the site root. `new_bot_defense` (`medium`): the home page refused AHN's last two checks (as for `home_now_gated`) with a bot-defense provider that the daily counts did not show in the 14 days before; one refusal stays `home_gate_unconfirmed`. `terms_signal_changed` (`medium`, `undetermined`, information only): `llms.txt` was removed, or a data-mining reservation was added. It is given only where the answer would otherwise be `no_measurement` or no `cause`, and its `line` says it is not an access block. None of the three is given to a caller that reported `error_class=service_error`.

Setting `AHN_CAUSE_HINT=0` (D73) leaves `cause` out and makes the answer equal to the one before it. On by default.

### Links

`links` gives the service's public feedback places: `feedback` (the "Field reports" category of the repository's GitHub Discussions: tell us when an answer was wrong or did not fit your next step) and `changelog` (`docs/feedback-changelog.md`: what we changed after feedback). The values are the same for every lookup and may change. A link that is not set is left out, never `null`; with none set, `links` is left out. `feedback` and `changelog` are the same for every lookup; `links.why` (below) is built from what the caller itself sent (the hostname, the failure codes, `via`, `agent_vendor`, `task_step` and the test mark) and from nothing else.

`links.why` (D109) is the address of `GET /v1/why` for the same lookup: the hostname plus the failure codes (`error_class`, `failure_stage`, `http_status`, `challenge`, `retry_after`) and the `task_step`, `via`, `agent_vendor` and test mark the lookup itself carried (`task_step` since D110), in the same form as the extra line of a failed `check_incident` result. It is present only on a lookup that sent at least one failure code (never on a plain "is it down" lookup without one). It is built from the codes you sent, reads nothing from the answer, and does not change the recommendation, `next_action` or any other field.

### `next_checks`

`next_checks` is an ordered list of `{code, text}` items with English `text`; the human website shows the same codes in Korean. The checks come from human verification and sign-in, the optional failure stage, the declared and official layers, a fresh provider statement, and whether reports exist. They never infer the actual result or cause of a task, never grant permission to bypass a site, and are not an automatic outage verdict. Order:

1. `failure_stage` value if given and not `unknown` (`before_target_response`, `response_observed`, `access_denial_observed`); otherwise `locate_failure_stage`, only when a failure signal was sent (`error_class` or `failure_stage`, D63) and `error_class` is not `human_verification` or `login_auth`.
2. `edge_refusal_confirmed` or `edge_refusal_robots` when `recommendation.reasons` starts with it (D85, D98); `no_path_after_failure` when `recommendation.reasons` ends with it (D101, `error_class=service_error`); `human_handoff` (`error_class=human_verification`) or `account_handoff` (`error_class=login_auth`).
3. Declared profile. When no profile was read because the hostname is a subdomain or tenant host (not a `www.<apex>` name, which gets the apex's profile), `profile_not_read` says so and points at the apex host. When the profile is `pending` with `retry_after_seconds`, `profile_pending`. Otherwise, when an access profile exists: the robots codes below are left out when `error_class` is `human_verification` or `login_auth` (D63; `access_profile` itself stays in the answer); else `robots_fetch_refused` (`robots_status` is `refused`), `robots_allows_agents` (`robots_status` is `absent`, D63), `robots_unknown` (any other non-`ok` status), or the robots codes of the [recommendation](#recommendation) (one of `robots_blocks_agents`, `robots_blocks_some_agents`, `robots_names_vendor_alias`, `robots_wildcard_disallow`, `robots_blocks_not_your_agent`, `robots_allows_agents`; two only for `robots_blocks_some_agents` or `robots_names_vendor_alias` followed by `robots_wildcard_disallow`); then `robots_grouping_differs_by_parser` when `robots.grouping_differs_by_parser` is not empty; then `llms_txt_present` when `llms_txt_status` is `present`, then `content_use_ai_input_declared_no` when a user-directed agent token's effective preference is `ai-input=no` or `ai-use=n` (see [Content-use preferences](#content-use-preferences-content_use)).
4. `official_path_available` when an official path with `api_docs` or `developer_portal` is listed. Registry facts follow it, only when `host_facts` is present: `government_registry_listed`, `government_list_version_missing` or `government_suffix_restricted` (informational; they never change `recommendation`).
5. `provider_scope` (fresh active issue), `provider_components_only` (fresh active indicator with `basis: components_only`) or `provider_incident_stale` (stale incidents, or a minor page with no incident list from a `source_time: active_items` feed whose active items were not updated for more than 7 days, D54; see [Recommendation](#recommendation)), then `provider_scope_partial` when it applies (below), then `provider_update_time_unknown` for a minor page with no incident list and no usable update time (D54), then `provider_maintenance_only` when the active status rests only on maintenance in progress with no incident (`basis` is `maintenance` and `active_incidents` is `0`, D55); or `provider_scope` then `provider_history_incident` for an Atom-history reading that makes the answer wait (D57, nothing else from this step); or `provider_clear` (fresh `indicator: none`); or `provider_unknown` (no fresh feed, or another indicator). `provider_scope_partial` follows any of these active codes when every component named by the unresolved incidents and maintenances sits in a region or point-of-presence component group of that page (a fixed table in `ahn/status_scope.py`, `REGIONAL_GROUPS`, from the providers' own component lists; a group not in the table never counts), or when there is at least one unresolved incident and `max_incident_impact` is lower than a `minor`, `major` or `critical` `indicator`. It never decides whether to wait. Only the first condition (every affected component regional) lowers a wait to `low` confidence; the second (worst incident below the page) is information only (D45).
6. `reports_unknown` (`no_reports`), `reports_stale` (`stale_reports`), or `reports_unverified` (any other evidence level).

### Agent vendor (`agent_vendor`, D48)

`GET /v1/incidents/check` and the MCP `check_incident` tool accept an optional `agent_vendor`: the vendor whose documented `robots.txt` token your own web requests send. Values: `openai`, `anthropic`, `google`, `perplexity`, `meta`, `mistral`, `amazon`, `microsoft`, `apple`, `duckduckgo`, `diffbot`, `exa`, or `other` (your requests identify as none of these vendors' tokens). It is the vendor of the fetcher, not of the model: a Claude model that fetches through a generic HTTP library is `other` or should leave the parameter out, while Claude's built-in web fetch identifies as `Claude-User` and is `anthropic`. Send it only when you know it; leave it out when unsure. A value outside the list (including a different case or extra spaces) is treated as not sent, never as an error. When it was accepted, `recommendation.agent_vendor` echoes it; otherwise the field is left out. It is used only to choose the recommendation and the robots check in `next_checks`: it is not counted with the lookup signal codes and not stored. The rest of the answer, including `access_profile`, is the same with or without it. The service cannot verify the value; a wrong one gets the answer for that vendor's tokens, and declared policy is no access guarantee either way.

**Governing tokens.** Each agent token in `AGENT_USER_AGENTS` belongs to one vendor (`AGENT_VENDOR` in `ahn/access_profile.py`). A vendor's governing tokens (`GOVERNING_TOKENS`) are its `user_agent` tokens, or its `search_crawler` tokens when it has no `user_agent` token (today `microsoft`: `Bingbot`, `apple`: `Applebot`, `exa`: `ExaSearchBot`). `training_crawler` tokens never govern, and vendors that run only training crawlers (Common Crawl, ByteDance, Cohere) are not in the list. A vendor's own search crawler does not govern when it has a user-directed token: each vendor documents the two as separate controls. For a vendor V the state is:

- `explicit`: a governing token has an explicit group that disallows the root (prefix matching included: a `Diffbot` group names `Diffbot-User`, a `Google` group names `Google-Agent`);
- `alias`: otherwise, when no group names any of V's governing tokens (a group that names and allows one decides for V), a group that disallows the root names V under a name listed for V in `VENDOR_ALIASES` (`robots.vendor_aliases_blocked`, for example `claude-web`);
- `wildcard`: otherwise, a governing token is named by no group and inherits a `*` group that disallows the root;
- `allowed`: otherwise.

For `other` the state is `wildcard` when the `*` group disallows the root, else `allowed`: a token outside the table cannot be named by a group the service reads. How the states make the answer is in [Recommendation](#recommendation).

**Limits.** The answer depends on the token table and the alias table: a new, unlisted name for a vendor's agent is still missed, and you can check your own token in the host's `robots.txt`. Alias names cover only user-directed or agentic fetchers, never ad or enterprise crawlers (`mediapartners-google`, `oai-adsbot`, `amazon-kendra`, `googleother`, `facebookexternalhit`, ...). Whether a vendor's fetcher honours `robots.txt` is that vendor's policy.

**Switch.** `AHN_VENDOR_AWARE_BLOCK=0` turns the vendor-aware rule off: `agent_vendor` is still accepted and ignored, nothing is echoed, and `recommendation` and `next_checks` are those of the rule before D48, wording included. `access_profile.robots` keeps `vendor_aliases_blocked` and the dash folding either way.

### `failure_stage`

The optional `failure_stage` (`before_target_response`, `response_observed`, `access_denial_observed`, `unknown`) is **what the caller observed**, and only shapes the checks. The service does not verify where a response came from or why access was denied. The value is echoed back in the response. It is never evidence for reports, provider status, or the `recommendation`; it is only counted in the hourly lookup signal counts described in the next section. An invalid `error_class` or `failure_stage` on the REST lookup returns `400` with only `{"error": "invalid_request", "field": ..., "allowed_values": [...]}` and never reflects the input. The MCP tool accepts the same optional values.

### Lookup signal codes

Four more optional codes describe the failed step as the caller saw it. Each comes from a fixed list; send only what you already know and leave the rest out. They are accepted on `GET /v1/incidents/check` and on the MCP `check_incident` tool under the same names (the tool takes `http_status` as an integer).

| Parameter | Values | Meaning |
|---|---|---|
| `http_status` | `401`, `402`, `403`, `407`, `408`, `429`, `451`, or any `500`-`599` | The HTTP status the target returned. Other statuses (404, 422, ...) are not access problems and are ignored (counted as not sent). Take it from the response itself, not from a guess in an error message. |
| `challenge` | `header`, `none` | `header` when the target's response carried a bot-challenge header such as `cf-mitigated: challenge`; `none` when it did not. Never decided from the page body. |
| `retry_after` | `none`, `lt_60`, `60_3600`, `gt_3600` | The `Retry-After` value of a 429 or 503 in seconds: under 60, 60 to 3600, over 3600. `none` when the header is absent or is a date. |
| `via` | `http_fetch`, `browser`, `unknown` | What made the failed request: a plain HTTP fetch or a browser. `unknown` is accepted but stored as not sent. |

A value outside its list is **ignored, not refused**: the lookup is answered normally and counted as if that code had not been sent, because a typo in an optional signal should not cost the caller its answer. (`error_class` and `failure_stage` keep their `400`.) A code that is left out is counted as unknown (`unspecified`), never as `none`: send `challenge=none` or `retry_after=none` only when you looked at the response headers and saw no such header.

**What the service does with them (D47, shadow mode).** A lookup is counted per public hostname and UTC hour together with `error_class`, `failure_stage`, these codes (`http_status` folded to its class, all `5xx` as `5xx`), the kind of client software (`plugin`, `ahn_client`, `mcp`, `web`, `rest_other`, from the User-Agent and the MCP hop, so only a hint), and the `recommendation.action` the lookup was answered with. Counts are kept 35 days. To count separate clients without keeping an address, a keyed digest of the IP address that is specific to the hostname and the UTC day is kept 2 days with the time of the client's last lookup, the coarse kind of blocked lookup (`outage`, `block`, `rate`, `login`) and its recommendation (the time is kept to the minute for about an hour, until the next cleanup after it is 61 minutes old, then cut to the hour; the cleanup runs every 15 minutes); a lookup of the same host 10 to 60 minutes after an earlier one (both inclusive, both lookups blocked ones) is counted as a re-lookup after that recommendation. No digest or exact count is ever returned. Lookups from the operator's own network, lookups marked `X-AHN-Test: 1` or `ahn_test=1`, documentation example hosts, and hosts that are not eligible apex hosts are not counted. In public mode a host is counted only while it is in the lookup register (the same condition as the daily lookup counts). The tables are size-bounded: at most 32 code combinations per host and hour and 200 per hour in all, the rest fold into `overflow` rows. The caps are approximate under concurrent writes. For an MCP call, the adapter passes the caller's address and test mark on its authenticated loopback hop for this count only.

**Nothing here changes an answer.** `recommendation`, `next_checks`, `evidence_level`, `observations` and every other field are the same with or without these codes. The codes are not reports and are never merged into `observations` or `evidence_level` (D11). The one response field that reads their hourly counts is the optional `cause` (D73), and only when at least three separate clients contributed; the caller's own codes never change its own answer. Any other field added later will be an optional layer with coarse bands, under the same three-client rule.

### Lookup feedback (`feedback_token`, `POST /v1/feedback`, MCP `rate_last_lookup`, D58)

An answer to a blocked lookup (one that sent `error_class`) ends with a `feedback_token` object when the service counts lookups of that host (an eligible apex host that is not a documentation example host, inside the lookup register in public mode, with lookup metrics on). Only this lookup (and MCP `check_incident`, which calls it) can carry one: an incident detail (`GET /v1/incidents/{id}`) and the site's own pages never do. (The name differs from `links.feedback`, the public discussion link.) The token is issued only when `error_class` was sent: a lookup with only `failure_stage`, or with no failure signal (a D63 `proceed`), carries none.

```json
"feedback_token": {
  "token": "<opaque>",
  "expires_in_seconds": 3600,
  "outcomes": ["succeeded", "still_blocked", "handed_off", "gave_up"],
  "paths": ["official_path", "same_site", "unknown"]
}
```

Otherwise the key is left out, never `null`. It is added after the answer is decided: `recommendation`, `next_checks` and every other key, and their order, are the same with or without it. A response that carries it is sent with `Cache-Control: no-store`. Setting `AHN_LOOKUP_FEEDBACK=0` leaves it out of every answer and leaves `rate_last_lookup` out of the MCP tool list; tokens issued earlier can still be sent back until they expire.

After trying the step again, the caller may send the token back once with what happened:

`POST /v1/feedback` with the JSON body `{"token": "<token>", "outcome": "succeeded", "path": "official_path"}` returns `200 {"accepted": true}`. The body takes these three keys only; `path` is optional (default `unknown`). There is no hostname: the token says which lookup it answers.

| Field | Values | Meaning |
|---|---|---|
| `outcome` | `succeeded`, `still_blocked`, `handed_off`, `gave_up` | The next attempt worked; it was still blocked; the step was handed to the user; the caller gave up. "Not tried" is never sent: no feedback is that. |
| `path` | `official_path`, `same_site`, `unknown` | The attempt used the official path the answer pointed to; it retried the same site; not said. |

Errors: `400 invalid_request` with `field` and `allowed_values` for an `outcome` or `path` outside its list; `400 invalid_request` for any other body problem (a missing token, an unknown key such as `site_host`); `400 invalid_feedback_token` for a value this service did not issue (malformed, altered, signed with another key, or not in the exact spelling it was issued in); `410 feedback_token_expired` 3600 seconds or more after the lookup; `409 feedback_token_used` when the token was already used (sending the same feedback again changes nothing); `503 service_unavailable`.

The token is opaque to the caller. It is a signed value (HMAC-SHA256 under a key derived from the service secret) that carries the apex hostname the lookup was counted under, the `recommendation.action`, the client kind (as for [lookup signal codes](#lookup-signal-codes)), the issue time, whether the lookup was counted, and a random nonce. **Nothing is stored when a token is issued.** When it is used, a SHA-256 fingerprint of its signed content (which includes the nonce) is kept with its expiry time, with no hostname, so it cannot be used twice; fingerprints are deleted five minutes after the token expires (a margin for clock differences between instances), by the next feedback and by the cleanup that runs every 15 minutes. The outcome is counted once per issue hour of the lookup, hostname, action, client kind, outcome and path (a count that would wait more than 200 ms on a lock is skipped; the feedback is still accepted); counts are kept 35 days, with at most 200 combinations per hour (the rest fold into an `(overflow)` row with no hostname). A lookup that is not counted (the operator's own network, `X-AHN-Test: 1`, `ahn_test=1`) still gets a token so that the flow can be tried end to end; its feedback is accepted and not counted.

**Feedback changes no answer.** It is not a report, is never merged into `observations` or `evidence_level` (D11), and the counts are not shown publicly or in any response.

MCP `rate_last_lookup(token, outcome, path="unknown")` sends the same request and returns `{"accepted": true}`; the error codes above come back as tool errors. It is annotated `readOnlyHint=false`, `destructiveHint=false` (it only adds to a count), `idempotentHint=true` (a repeated call has no further effect) and `openWorldHint=false`, and is listed in every mode while `AHN_LOOKUP_FEEDBACK` is not `0`. Its `token` input schema has the same pattern and length limit as the REST body.

**Additive fields may appear.** The `outputSchema` that MCP `tools/list` advertises for each tool (`check_incident`, `rate_last_lookup` and the others) allows additional properties on every object (`additionalProperties: true`), so a client that cached the tool list keeps accepting answers after an optional key is added. The service itself still checks its answers against the closed models.

## `POST /v1/observations`

In local synthetic testing, `X-API-Key` is required. The submitting agent follows its own user and platform authority rules. The body below is entirely synthetic.

```json
{
  "schema_version": 1,
  "site_host": "example.test",
  "task_step": "login_verification",
  "error_class": "human_verification",
  "observed_at": "2026-10-03T03:55:00Z",
  "agent_family": "muse",
  "attempt_actor": "human",
  "attempt_env": "human_in_agent_browser",
  "outcome": "blocked",
  "challenge_vendor": "unknown",
  "challenge_kind": "loop",
  "synthetic": true,
  "idempotency_key": "0a915e22-0a8d-4be0-84a3-4061ade4adab",
  "consent_confirmed": true
}
```

Success returns `201` with `{ "observation_id": "uuid", "incident_id": "uuid", "review_state": "pending", "synthetic": true }`. Resending the same `idempotency_key` from the same reporter returns `200` with the existing IDs; the same key with a different body is `409 idempotency_conflict`. The server identifies the reporter from the key and rejects a `reporter_id` in the body. `consent_confirmed` is still accepted from older clients, but the server never treats it as evidence of authority or uses it to decide approval. Local test mode accepts only `synthetic: true` submissions for `.test` hosts.

Enum values: `attempt_actor` `agent`, `human`; `attempt_env` `agent_cloud_browser`, `human_in_agent_browser`, `human_own_browser`, `unknown`; `agent_family` `dots`, `muse`, `other`; `challenge_vendor` `cloudflare`, `recaptcha`, `hcaptcha`, `unknown`, `none`; `challenge_kind` `interactive_check`, `loop`, `block_page`, `unknown`, `none`.

Optional `cause` and `cause_basis` (D109) say what the reporting agent established about why the step failed, and what it established that from. Send both or neither. Send them only when you established the cause from one of the four bases, never as a guess; otherwise leave both out (there is no `unknown` value, and leaving the fields out means the same). They are accepted only with `outcome` `blocked` or `error`, and only in these combinations:

| `cause` | Points at | Allowed `cause_basis` | Allowed `error_class` |
|---|---|---|---|
| `site_said_no_agents` | the site | `site_message` | any |
| `site_bot_check` | the site | `site_message` | `human_verification` |
| `site_unavailable` | the site | `site_message`, `person_confirmed` | `service_error` |
| `platform_refused` | the agent's own product | `own_platform_message` | any |
| `platform_needs_person` | the agent's own product | `own_platform_message` | any |
| `verification_on_person_device` | the account | `site_message`, `person_confirmed` | `login_auth` |
| `verification_not_received` | the account | `person_confirmed`, `compared_with_own_browser` | `login_auth` |
| `signed_out` | the account | `site_message`, `person_confirmed` | `login_auth` |
| `agent_browser_differs` | the agent's browser | `compared_with_own_browser` | any |

`cause_basis` is `own_platform_message` (your own product said so), `site_message` (the site's screen or response), `person_confirmed` (a person confirmed it) or `compared_with_own_browser` (the same step was compared with the person's own browser or app). A value outside its list, `cause_basis` without `cause`, a missing or disallowed basis, an `error_class` that does not fit, or any other `outcome` is `422 {"error": "invalid_cause"}`. No agent product name is accepted in a report.

The automatic review never publishes a report whose `cause` is `site_said_no_agents`, `platform_refused`, `platform_needs_person` or `agent_browser_differs` (they name a site's policy or a product): it is held for the operator with `review_reason` `cause_review`. The other five follow the ordinary automatic review. A published cause is shown, always as the reporting agent's statement ("reported by the submitting agent, not verified by AHN"), in `observations[].cause` and `cause_basis` of the lookup answer, in `others_saw.reports[]` of `GET /v1/why` and on the incident page. It never enters `recommendation`, `next_action`, the `cause` hint, `failure_stage`, `next_checks`, `evidence_level`, the counts or `lookup_activity`; sending a cause again and again changes none of them. The idempotency check covers both fields.

## `POST /v1/observations/{id}/outcomes`

Disabled in public operation (see the public intake contract below). Requires the same reporter's key, authorization for the new submission, and a new idempotency key. It reuses the original incident's `site_host`, `task_step`, and `error_class`; the body accepts only `schema_version`, `observed_at`, `attempt_actor`, `attempt_env`, `outcome`, `challenge_vendor`, `challenge_kind`, `agent_family`, `synthetic`, `idempotency_key`, and `consent_confirmed`. The new observation row references the earlier one through `supersedes_id`, so an older failure and a newer success of the same incident are both recorded. Another reporter's ID is not accessible.

## `DELETE /v1/observations/{id}`

In local test mode, requires the same reporter's key (public mode uses a withdrawal token; see below). A withdrawn observation is excluded from lookups and leaves only a minimal audit event. Repeating the request returns success (idempotent). Retention is set by the operator and stated on the privacy policy page: reports have no automatic deletion date unless `AHN_REPORT_RETENTION_DAYS` (30–3650) is set, in which case the periodic cleanup (every 15 minutes) deletes reports older than that period and withdrawn reports 30 days after withdrawal. A report can also be deleted sooner on request (see the support address on the policy page).

## Incident list and detail

`GET /v1/incidents?site_host=&error_class=&limit=` lists at most 50 published incidents from the last 7 days. `GET /v1/incidents/{id}` returns one incident's public summary with a limited list of observations. Unpublished, hidden, and synthetic incidents are `404` on the public list and detail. Local test lookup paths are kept separate from the public web paths.

## OpenAPI and MCP

`/openapi.json` describes the REST contract of the running mode. In local synthetic testing, the `X-API-Key` security scheme applies to writes. Public beta report submission needs no key, and MCP exposes only `check_incident`, `rate_last_lookup` ([lookup feedback](#lookup-feedback-feedback_token-post-v1feedback-mcp-rate_last_lookup-d58)) and `report_observation`.

`check_incident` is read-only for the caller: it creates no report and never changes the target site or the caller's data. Each lookup is counted anonymously (host registration and a daily per-host count, written in the lookup's own short transaction; plus, in shadow mode, an hourly per-host count of its optional lookup signal codes, see [Lookup signal codes](#lookup-signal-codes)), and the service may fetch the host's public `robots.txt`, `llms.txt` and provider status feed to fill its cache; those reads happen in the background, never while the lookup waits. It is annotated `readOnlyHint=true`, `idempotentHint=true` and `openWorldHint=true` (it describes the public web). MCP annotations are UI hints only; the server cannot verify under what authority an agent submits. Never pass secrets, raw conversation, or target-site page content through MCP. Whether apps call the tool at the right moment without approval friction is to be measured in a real pilot. The central API counts successful MCP tool executions in a separate daily category, distinct from `/mcp` HTTP connections and REST GETs; it cannot tell failed executions, independent agents, or task results.

MCP `check_incident` returns two text blocks: first `summary_line` (and, when `next_action.url` is set, a second line `URL: <url>`; when `next_action.customer_url` is set and differs from `url`, a further line `Customer path: <url>`, D61), then the full answer as JSON, the same as the structured content and the REST answer. If you parse the text, read the last block: it is the JSON. When the call carried a failure code (`error_class`, `failure_stage`, `http_status`, `challenge` or `retry_after`), the first block ends with one more line, `Why it stopped and whether a person must act: https://agenthelpnetwork.com/v1/why?site_host=<host>&...`, built only from the hostname and the codes the caller sent, plus `task_step`, `via`, `agent_vendor` and the test mark when they were sent (D108, D110; see [Explain a blocked step](#explain-a-blocked-step-get-v1why)). `/v1/why` does not take `failed_at`, so the answer behind that link is calculated without it. The JSON block and `structuredContent` are byte for byte unchanged, and the tool definition is unchanged; only the first block gains that one line, and only for a lookup with a failure code. When `next_action.do` is `proceed`, the first block ends with one more free-text line saying that proceed means no block is declared, not that nothing blocked the caller (outside every schema).

Setting `AHN_RESPONSE_GUIDE=0` removes `summary_line`, `next_action`, `links` and the first MCP block, so the answer is the same as before D51.

Setting `AHN_STATUS_CHECK_GUIDE=0` (D69) gives a `task_step=status_check` lookup the same `summary_line` as any other lookup and leaves `next_action.status_url` out (it also turns off the D76 always-on `status_url` and the status-page `url`). On by default.
Setting `AHN_STATUS_CHECK_COMPACT=0` keeps `access_profile.robots.rules` in `task_step=status_check` answers (D71); it is on by default.
Setting `AHN_FAILURE_KIND_LINES=0` (D87) gives the `summary_line` of every answer exactly as it was before D87. On by default; an unknown value counts as `0`. Only the sentence of those two kinds of row differs; nothing else in the answer is touched.
Setting `AHN_D99_UNREADABLE_NOT_PENDING=0` (D99) shows `ahn_check` as `pending` with `retry_after_seconds` again for a host whose `robots.txt` could not be read and has no read queued. On by default; an unknown value counts as `0`. Only `ahn_check` differs.
Setting `AHN_D104_BETTERSTACK_UPDATED_AT=0` (D104) reads a Better Stack feed's page-level `updated_at` as `source_updated_at` again and leaves `provider_status.affected` out for it. On by default; an unknown value counts as `0`. The recommendation is the same either way; the public board differs in one case: a wait whose open report was last updated more than seven days ago leaves the board as `stale_update` with the switch on.
Setting `AHN_D100_INCIDENTIO_INCIDENTS=0` (D100) stops the `summary.json` read of incident.io-shaped status pages and restores the status-check sentences and the `provider_clear` next check from before D100. On by default; an unknown value counts as `0`.

## Background reads (stale-while-revalidate)

A lookup almost never waits on a third-party host. `GET /v1/incidents/check` and MCP `check_incident` answer from the database over one connection: the bookkeeping writes (host registration, the per-host count) are committed first, then the reads the answer needs, then the queue inserts. The one exception is the home-page check (`ahn_check`, D67): while the operator sets `AHN_SITE_PROBE=1` and unless the host's `robots.txt` disallows it, the lookup waits **at most 3 seconds** for our server's request of the home page (holding no database transaction; a lookup that finds another lookup's request for the same host running does not wait and shows `pending`). Every other read of a target host or a status provider happens behind the lookup.

- **What is queued.** One row per kind and host in `background_reads`, so repeated lookups collapse into one read: the `robots.txt`/`llms.txt` profile of an eligible host inside the bounded lookup register (`QUERIED_HOST_CAP`) with no cached read or one outside its cache window (24 hours, or one hour after a transport failure); the once-a-day Statuspage discovery for a host without a feed; and a refresh of a connected feed once its statement would read as `stale` by age (2 hours; 15 minutes while the cached `indicator` is active) or was never read, not again within 15 minutes of the last attempt. The queue holds at most 2,000 rows; when it is full, nothing new is queued. If the queue cannot be written, the lookup still answers.
- **Who reads.** A small worker inside the web process (two threads, each claiming one job at a time, woken by the lookup that queued the row and polling every 30 seconds) and the 5-minute review cron (`python -m ahn.auto_review`, claiming five at a time, processing the queue first and the seed list after it within one 120-second budget; when the budget is spent it returns even if a read is still running). Jobs run in the order profile, discovery, feed, oldest first. A claim uses `SELECT ... FOR UPDATE SKIP LOCKED`, counts the attempt and sets a five-minute lease, and the lease is checked again just before the job starts, so no two processes or threads read the same row. `AHN_BACKGROUND_READS=0` turns the in-process worker off; the cron still processes the queue. External reads are paced to at most two per second per process.
- **The read rules are unchanged** (decisions D27-D29): the same `robots.txt`/`llms.txt` reader, caps, redirect rule, per-host locks, 24-hour cache, and one-hour retry after a transport failure; the same feed reader and Statuspage discovery. Every body read (a `robots.txt`, an `llms.txt`, a feed, a discovered status page) also has a whole-body time limit of 10 seconds, so a host that sends one byte at a time ends as `read_timeout` (feeds: `timeout`) instead of holding a reader.
- **Outcomes.** A read that ends in any result, including a transport failure, is finished: the cache records it and the row is deleted. A job whose processing raises, or whose processor stopped mid-job, is retried after 2, 4, 8 and 16 minutes (2^attempts minutes, at most 60) and dropped after five attempts.
- **What the caller sees.** The first lookup of a new eligible host returns `access_profile` with `robots_status: pending`, `llms_txt_status: pending`, `freshness: pending` and `fetched_at: null`. When its read is in the queue, the profile also carries `retry_after_seconds`: an estimate from the job's place in the queue and its earliest start, between 5 and 300 (300 while only the cron processes the queue); `recommendation` and `next_checks` then carry `profile_pending`. Ask once more after that many seconds; do not poll. When nothing could be queued (a full queue, a host outside the register, a database error), the field is absent and the profile reads as unknown. An expired profile is returned as cached with `freshness: stale` and read again behind the lookup; a failed feed keeps its last statement (`fresh` with `error_detail` while at most 2 hours old, then `stale`), and an old one reads as `stale`. A mapped feed with no read yet is `provider_status.freshness: pending` with `indicator: null`. A first discovery shows `not_verified_by_current_methods`; `provider_discovery_attempted_at` is set when the discovery actually runs, and a verified source appears from a later lookup. No `Retry-After` header is sent: the response is a 200 and only the body field applies.
- **Home-page check (D67).** A fourth kind, `site_probe`, has the lowest priority and no delay: a request for a host's home page, unless the stored `home_gate` disallows it (see `ahn_check`). It waits (without using up an attempt) for a fresh profile and is dropped after one hour without one; a lookup first tries the same check synchronously for at most 3 seconds and queues the row only if that does not finish.

## Public intake contract

- `POST /v1/observations` needs no account or API key. **Three fields are required: `site_host`, `error_class`, `outcome`.** `error_class` is one of `site_access`, `login_auth`, `human_verification`, `service_error`; `outcome` is one of `passed`, `blocked`, `error`, `abandoned`. Omitted fields default to: `observed_at` = server receive time, `task_step` = `other`, `attempt_actor` = `agent`, `attempt_env` = `unknown`, `agent_family` = `other`, `synthetic` = `false`. State the real time, step, and environment when known. Allowed `task_step` values are `site_open`, `login`, `human_verification`, `service_use`, `other`. The body is JSON of at most 4096 bytes, and undefined fields are rejected. Never send a real report as an example or test. `cause` and `cause_basis` are optional and follow the rules above (`422 invalid_cause` otherwise).
- **Automatic sharing:** if the agent's own user and platform authority rules permit it, it may send a de-identified firsthand observation without additional per-submission approval. This document grants no authority and does not impose an approval procedure on other agents. A public hostname can itself identify a person or organization, so do not send sensitive hostnames. `consent_confirmed` is accepted for older clients but is not used as proof of authority or as an approval gate.
- If `idempotency_key` is omitted, the server creates a new UUID. **To avoid duplicates when retrying, the client should generate a UUID, keep it, and reuse it with the same body.** Resending a request without a key can create a separate report.
- `201`, or `200` for the same idempotent request, includes `review_state: pending`, `observation_id`, `incident_id`, `synthetic: false`, and `withdrawal_token`. Do not share this token or put it in a URL. New reports start private. A separate Render cron job runs every 5 minutes, reviews reports older than 10 minutes by rule, and publishes only qualifying single structured observations with `review_reason: auto_unverified`. This does not verify the site's status or the report's truth. Other reports are held, and the operator can hide or publish them manually.
- `DELETE /v1/observations/{id}` uses the `X-Withdrawal-Token` header. A mismatched ID or token is `404`; a withdrawn observation is excluded from public lookups. The human pages `/en/report` and `/ko/report` also have a withdrawal form.
- In public operation, `POST /v1/observations/{id}/outcomes` is disabled and does not appear in OpenAPI or MCP. A new result is a new submission under the submitting agent's own authority rules.
- All anonymous submissions count as one unverified source. More than 5 per host per day (a `www.<apex>` name counts toward its apex), 100 in total per day, or, per app instance, 3 per client per minute or 20 in total per minute returns `429`. The operator can pause intake with a database flag, which returns `503 reporting_paused`.

## Export v1 (operator CLI)

Stored facts can be written out as JSON Lines, one envelope per line, by the operator: `python -m ahn.cli export --kind access_profile|status|observation [--since ISO | --all] [--out FILE]`. This CLI is not a public endpoint. The public dataset is the [offline bundle](#offline-bundle), a separate file served only while the operator's switch is on.

```json
{"schema_version": 1, "kind": "access_profile", "record_id": "ahn:agenthelpnetwork.com:access_profile:example.org:2026-10-19T04:05:06.789000Z",
 "origin_operator": "agenthelpnetwork.com", "vantage": {"kind": "datacenter", "region": "US", "asn": null, "declared": true},
 "reader_version": "AgentHelpNetwork/0.2 (+https://agenthelpnetwork.com/en/policy)", "observed_at": "2026-10-19T04:05:06.789000Z",
 "received_at": "2026-10-19T04:05:06.789000Z", "expires_at": "2026-10-20T04:05:06.789000Z", "source_url": "https://example.org/robots.txt",
 "content_sha256": "<64 hex>", "payload": {"site_host": "example.org", "robots_status": "ok", "robots": {"...": "..."}, "llms_sha256": null},
 "signature": {"alg": "ed25519", "key_id": "agenthelpnetwork.com:2026-10", "sig": "<base64url>"}}
```

- `record_id` is `ahn:<operator>:<kind>:<host>:<observed_at>`; observation records add a short digest of the operator's own observation id, which itself is never exported. `expires_at` is `observed_at` plus 24 hours (`access_profile`) or 7 days (`status`, `observation`).
- `access_profile` and `status` records come from definitive reads only (`fetched_at` set). A row whose latest attempt failed after that read is left out, because it would mix the read with the failure's label; it is exported again after the next successful read. `content_sha256` is the SHA-256 of the `robots.txt` or feed bytes as received; the files themselves are never stored. Provenance columns (`origin_operator`, `vantage`, `reader_version`, the hashes) were added by migration 020 and are `null` for rows read before it; they are not backfilled. Rows without a recorded operator are this operator's own reads. The `access_profile` payload also carries `content_use` as stored: the parsed preferences (the declared shape's fields without `status`, `scope`, `note`, and the read fields) plus `vocab` (the parser version) and the `robots_sha256` of the file it was parsed from; `null` when the read had no `robots.txt` body or predates migration 021.
- `observation` records follow the public answer's rules: published, non-synthetic, unwithdrawn reports on a published incident from the last 7 days (`--all` exports every stored one), `observed_at` and `received_at` cut to the hour, and no reporter identity. The payload holds only the public answer's fields: `site_host`, `observed_at`, `task_step`, `error_class`, `attempt_actor`, `attempt_env`, `outcome`.
- **Signing.** Only when `AHN_EXPORT_SIGNING_KEY` names an Ed25519 private key file (PEM, PKCS#8): the signature covers the RFC 8785 (JCS) canonical form of the envelope without its `signature` member, and is `{"alg": "ed25519", "key_id": "<operator>:<YYYY-MM>", "sig": base64url without padding}`. `AHN_EXPORT_KEY_ID` sets the key id (default: the operator and the current UTC month). Without a key, `signature` is `null`.
- The operator id is `AHN_OPERATOR_ID` (default `agenthelpnetwork.com`) and the declared vantage is `AHN_VANTAGE` (JSON, default `{"kind":"datacenter","region":"US","asn":null,"declared":true}`).
- Planned, not published yet: verification keys at `/.well-known/ahn-operator.json` as `{"operator": "<operator>", "keys": [{"key_id": "<operator>:<YYYY-MM>", "alg": "ed25519", "public_key": "<base64url raw 32 bytes>", "not_before": "<ISO>", "not_after": "<ISO or null>"}]}`. Until it exists, signatures can be checked only with a key the operator hands over directly.
- **Reading Export v1.** Consumers must ignore kinds and fields they do not know; new kinds and fields are added without a new `schema_version`. Besides the CLI's `access_profile`, `status` and `observation`, the [offline bundle](#offline-bundle) writes `bundle_meta`, `official_path` and `status_source`. Those three describe curated tables and the file itself, not a read: their `received_at` is `null` (nothing was received), and their `observed_at` (and so `record_id` and `expires_at`) is the build time of the file, so the same entry gets a new `record_id` in every build.

## Offline bundle

**Served only while the operator's switch is on.** `AHN_PUBLIC_BUNDLE=1` on the web service and on the review cron turns it on (the web service also needs `AHN_PUBLIC_BUNDLE_SINCE`, the date the privacy policy then shows as last updated); it is off by default. While it is off nothing is built, the cron deletes any stored file, and both paths below answer `404` like any unknown path. Until the switch is on at agenthelpnetwork.com, this section describes a prepared format, not an available download.

The bundle is one gzip JSON Lines file for agents and frameworks that want this data without a network lookup (no hostname leaves the agent, no wait) and for operators who mirror it.

- `GET /v1/bundle/latest.jsonl.gz` returns the file (`Content-Type: application/gzip`, no `Content-Encoding`: save the bytes as they are). `GET /v1/bundle/latest.jsonl.gz.sha256` returns its SHA-256 in `sha256sum` format (`<hex>  ahn-bundle-<UTC time>.jsonl.gz`). Both accept `HEAD`. The file response also carries `ETag: "<sha256>"`, `Repr-Digest: sha-256=:<base64>:`, `Last-Modified`, `Cache-Control: public, max-age=3600` and `Accept-Ranges: none`; send `If-None-Match` with the ETag and an unchanged file answers `304` without a body. A `Range` request gets the whole file with `200` and counts as a full download.
- The review cron rebuilds the file about once a day (when the stored one is 23 hours old); the web service serves the latest stored file. Pull it at most daily. Before the first build the paths answer `503 {"error": "bundle_not_ready"}`, and a stored file more than 48 hours old is not served: `503 {"error": "bundle_stale"}` (both with `Retry-After: 300`).
- Download limits: each client (counted in memory only, by a keyed daily digest of its IP address) gets 3 full downloads per UTC day, then `429 {"error": "bundle_client_limit"}`; all full downloads together share 25 MiB per UTC day, counted in the database so a restart does not reset it, then `429 {"error": "bundle_daily_limit"}`. Both carry `Retry-After` until the next UTC day. `304` and `HEAD` answers are not counted.
- Limits of the file: at most 20,000 records, 8 MiB compressed and 128 MiB uncompressed; a build over any limit fails and the previous file stays. Measured with every curated seed host and deliberately heavy synthetic `robots.txt` summaries, the file is about 0.84 MB compressed (1.1 MB with signatures) for about 3,600 records.

**Format.** Every line is an Export v1 envelope (`schema_version` 1, the same fields as [Export v1](#export-v1-operator-cli); ignore kinds and fields you do not know). The first line is the head record, `kind: "bundle_meta"`, whose payload holds `title`, `creator` (the operator's display name, the licensor), `generated_at`, `valid_until`, `record_count` (records after the head), `counts` per kind, `license: "CC-BY-4.0"`, `license_url`, `notice`, `attribution`, `third_party_quotes`, `status_source_note`, `schema_url` (this section), `contribute_url` (the page on how to send corrections and additions back; added later, so older files lack it), `includes` and `excludes`. The other records follow sorted by kind, then hostname:

| kind | What it is | Where it comes from |
|---|---|---|
| `access_profile` | The latest definitive `robots.txt`/`llms.txt` read: the operator export's record, with the read time cut to the UTC day (`observed_at`, `received_at` and `record_id` say `T00:00:00Z`). Optional `payload.host_change` (D75, left out when there was none): the changes of this host's declared access policy over the last 30 days, newest 40 at most, oldest first, each `{field, from, to, day}` with short codes and the UTC day (`field` is `robots_status`, `robots_verdict:<agent token>`, `llms_presence`, `tdm_root`, `site_declared_api`, `site_declared_reservation`, `home_outcome` or `bot_vendor`; `allow`/`block` for a verdict). Readers that do not know the field ignore it | Hosts on the curated part of the public seed list ([`ahn/seed_hosts.txt`](../ahn/seed_hosts.txt), above the `# Hosts chosen from the Tranco top 1,000` comment that opens its Tranco block) only |
| `official_path` | `name`, `api_docs`, `developer_portal`, `note`, and `access` (auth, key sign-up, limits, sandbox, OpenAPI, MCP, terms) only while that bundle is current under the API's 90-day rule for the whole validity of the file | The curated table [`ahn/official_paths.py`](../ahn/official_paths.py) |
| `status_source` | `source_name`, `status_page_url`, `api_url` and `feed_kind` (both `null` for a link-only page) | The curated `SOURCES` and `OFFICIAL_STATUS_PAGES` in [`ahn/status_refresh.py`](../ahn/status_refresh.py). Many of these hosts were found by scanning bands of the Tranco ranking; each mapping was checked on that host's own status page, and no rank is included |

**Freshness.** Judge the bundle's records by the head record's `valid_until` (build time + 8 days: the seed list is re-read about weekly). Each record's `expires_at` is the online API's cache rule (24 hours for a read, 7 days for the curated tables) and is kept so the envelope stays Export v1; offline, `valid_until` is the rule. After `valid_until`, get a newer file, read the host's own file, or call the API.

**A missing record is not a missing declaration.** A host without an `access_profile` record was not read definitively for this file (it is not on the curated seed list, or its last read failed); it may well have a `robots.txt`. A host without `official_path` or `status_source` is simply not curated. Government registry facts (`host_facts`) are not in the bundle either: they come from two public whole-file lists (the U.S. .gov registry, CC0, and the UK .gov.uk list, Open Government Licence v3.0) that are best read from their publishers, who update them more often than this file.

**Never in the bundle**, enforced by a field allowlist (envelope, payloads, robots summary and rules, `content_use`, `access`), a forbidden-field scan and a host check on every record (a build that breaks any of them fails): reports or anything about them; hostnames people looked up that are not on the seed list, including their reads, discovered status pages and lookup counts (a looked-up host in a public file would tell what someone looked up); lookup counts; request logs; IP digests; reporter keys; a status feed's current value (read the feed itself; the bundle carries only where it is); the seed hosts taken only from the Tranco ranking (the block at the end of the seed list, left out until that list's terms are settled; a comment naming Tranco above that block also fails the build); and the seed list's order or rank (records are sorted by hostname and no rank is written). Status mappings come from the code, not from the `status_sources` table, whose rows exist only after a lookup.

**Using it.** Every record says where to check it: `source_url` and, for reads, `content_sha256`. An `access_profile` is the host's declared policy at read time, never an access guarantee. Records are signed exactly as the operator CLI signs them, only when `AHN_EXPORT_SIGNING_KEY` is set and the key can be read; otherwise (not set, or the file is missing, not an Ed25519 key, or password-protected on the service that builds the file) `signature` is `null`, and the SHA-256 file over HTTPS is the integrity check. Check a download with `sha256sum -c ahn-bundle-<time>.jsonl.gz.sha256` and read it with `gzip -dc`.

**License.** The bundle is licensed under [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/) by the operator named in `creator` (`AHN_OPERATOR_NAME`); the code stays Apache-2.0. The head record's `notice` is the marking (`Agent Help Network offline bundle © <year> by <creator> is licensed under CC BY 4.0. To view a copy of this license, visit https://creativecommons.org/licenses/by/4.0/`) and `attribution` is a ready credit line with the generation time. When you reuse or mirror it, credit the creator and Agent Help Network, link the license, and say if you changed the data. **Quoted publisher text is not covered:** `official_path` `access.free_tier.quote` and `access.terms.quote` are short verbatim quotes from the publishers' own pages, third-party material that this license does not grant (`third_party_quotes` says so in the file). The license covers the dataset as compiled here; each record points to the public source it was read from, and the sites' own files are not included.

**Sending data back.** If you have a corrected or missing official developer path, status-page mapping or access bundle, [`/en/contribute`](https://agenthelpnetwork.com/en/contribute) explains how to send it (an issue form, or a pull request with a JSON Lines file under [`contrib/`](../contrib/README.md) in the same record shape; `scripts/check_contrib.py` checks the shape and makes no request). Nothing is expected of anyone who uses the file, and the license above does not change. We re-read the public source ourselves before anything is applied.

**Thin shards, manifest and changes file.** Beside the full file, the same stored bundle is cut into small JSON files, for an agent that wants to compare a few hosts and for agents that cannot run a script over a file this size. They are served whenever the bundle is served; `AHN_BUNDLE_SHARDS=0` on the web service takes the three paths below out (`404`, the full file is unaffected). They need no new storage: the web service derives them in memory from the stored file.

- `GET /v1/bundle/shards/<xx>.json`: 256 shards. `xx` is the first byte of the SHA-256 of the lowercase hostname without a trailing dot, as two lowercase hex digits (Python: `hashlib.sha256(host.encode()).hexdigest()[:2]`). Every shard exists, empty or not. The client picks the shard of its own host, so the server never receives a hostname and cannot tell which host a shard was fetched for; it sees a one-in-256 prefix. Several shards fetched together by one address are a combination, so a client that wants to blur its list can always fetch a fixed number of shards and fill the rest with random ones. Body: `{"schema": "ahn-shard/1", "shard", "generated_at", "valid_until", "hosts": {"<host>": {"access", "official", "status"}}}`, each section present only when the full bundle has that record. `access` is the thin form of `access_profile` (`robots` and `llms_txt` statuses, `root_allowed`, `crawl_delay`, `agents_blocked`, `content_signals`, `ai_input_declared_no`, `read_host` when it differs, `read_on`, the UTC day of the read); `official` of `official_path` (`name`, `api_docs`, `developer_portal`, and from its access bundle `auth` methods, `key_signup_url`, `openapi_url`, `rate_limits_url`, `sandbox_url`, `official_mcp` endpoints, `terms_url`); `status` of `status_source` (`name`, `page`, `api`, `feed`). Fields without a value are left out. Robots rule lists, quoted publisher text and signatures stay in the full file. Judge freshness by `valid_until`, as for the full file.
- `GET /v1/bundle/shards/manifest.json`: `shards` lists, for each of the 256 shards, `id`, `sha256` and `bytes` (of the JSON as the client sees it), `gzip_bytes`, `built_at` and `hosts`; `bundle_sha256` is the full file's SHA-256 these were cut from, `changes` describes the changes file the same way. Compare a shard's `sha256` with the SHA-256 of what you received. When `AHN_EXPORT_SIGNING_KEY` is readable by the web service the manifest carries a `signature` made the way records are signed (Ed25519 over the canonical form of the document without `signature`); otherwise it is a hash manifest only, and HTTPS is the integrity check for the manifest itself.
- `GET /v1/bundle/changes.json`: the host sections that changed during the last 7 days, `{"schema": "ahn-changes/1", "generated_at", "window_days": 7, "covers_since", "changes": [{"host", "section", "changed_on", "record" | "removed": true}]}`. A re-read that changes nothing but the read day is not a change. There is no history table behind it: the web service compares each stored file it serves with the previous one it served, and a restart starts a new baseline, so `covers_since` says from when changes could be seen (never earlier than 7 days ago). Before that time, use the shards.
- All three are sent gzip-encoded (`Content-Encoding: gzip`, `Content-Type: application/json`), so an HTTP library or browser hands you plain JSON; with `curl` add `--compressed`. `ETag` is the SHA-256 of the JSON (strong); send it as `If-None-Match` and an unchanged file answers `304` without a body. `HEAD` is accepted. `Cache-Control: public, max-age=3600`. A missing or stale stored bundle answers `503` as above.
- Budget: the three files share 50 MiB of transfer per UTC day, separate from the full file's 25 MiB, which they do not touch and which does not touch theirs. This counter is kept in memory and counts within one process lifetime only: every deploy or restart resets it, so the real daily total can exceed 50 MiB on a day with a deploy. The 7-day window of the changes file is measured from the stored bundle's `generated_at`, not from the request time, so one stored bundle always yields the same changes and manifest bytes (and ETags). Over it, `429 {"error": "bundle_shard_daily_limit"}` with `Retry-After` until the next UTC day (the same form as `bundle_daily_limit`). `304` and `HEAD` answers are not counted. Fetch the manifest and the changes file at most daily, and a shard only when the manifest's `sha256` for it differs from the copy you hold.

**Operators.** `python -m ahn.cli bundle --out FILE` writes a bundle from the database to inspect it without publishing anything; `--store` replaces the stored file the web service serves, under the same database lock as the cron. Both need `AHN_OPERATOR_NAME`.

## Site problems right now (served only once the operator turns it on)

`GET /v1/now` (JSON, schema `ahn-now/1`) and the human pages `/en/now` and `/ko/now` exist only while the operator sets `AHN_PUBLIC_BOARD=1` (and the public lookup is on); today they are off and answer 404. The list is read from the database only (no request to any site), at most once a minute per web process, and is sent with `Cache-Control: public, max-age=60` and an `ETag` (`If-None-Match` gets 304). Do not fetch it more often than `next_update_after`.

- `problems[]` and `maintenance[]` (at most 100 each, `truncated` says when more exist; lines are ordered by the provider's `updated_at`, newest first, whatever the grade; a line without one sorts last, and equal times by host name; the grade does not rank): `site_host` and `provider` (`indicator` as the provider publishes it: `critical`, `major`, `minor` or `maintenance`; `basis` when read, as in the lookup answer; `updated_at`, the latest provider time the line was judged on (page or incident); `source_name`, `source_url`, `source_updated_at`, `fetched_at`). A page whose indicator is raised by maintenance only (`basis: maintenance`) is listed under `maintenance`. A host is listed only while its provider statement would make a lookup answer wait (the same rule as `recommendation`) and the provider updated that statement within the last 7 days. A statement with no update time (a time more than an hour in the future counts as none), or whose open incidents all stopped updating more than 7 days ago, is left out. A line read from a page's public incident history (D57; the page's `robots.txt` disallows its status API and allows `/history.atom`) has `provider.indicator: null` (said, never made up: that feed has no level), `source_kind: history_atom` and `active_incidents`, no `basis` or `source_updated_at`, and `updated_at` is the latest `<updated>` of its open incidents. It is listed exactly when the lookup waits on it (the D57 row of the recommendation); with open incidents but a blind window, no usable time, or a time older than 7 days it is left out (`window_blind`, `no_update_time`, `stale_incidents`). A history that lists no open incident is not a statement and is neither listed nor counted. The same page mapped to several hosts gives one line per host, as for any feed.
- `ahn_check` (on a line) and `coverage.ahn_check_vantage`, `checks_paused` and the `a_*` numbers in `stats_7d` appear only when the operator also sets `AHN_PUBLIC_BOARD_AHN_CHECK=1` (off by default): AHN's own robots.txt reads from one datacenter location, `result` one of the failure kinds, never a refused read.
- `coverage`: `provider_feeds_read`, `feed_scope` (`looked_up_hosts_only`), `curated_hosts`.
- Since D68 the board's AHN check also counts list-driven home-page checks (see `ahn_check`): a line's `ahn_check.checked` lists which of them failed in the current period, `robots_txt`, `home_page` or both. It states that AHN could not connect from this one point, not that the site is down; refused answers are never listed.
- `stats_7d`: `days`, `provider_periods` (provider problem periods in the last 7 days, no host named; incidents read from an incident history, D57, are not counted there yet) and `provider_left_out_now` (fresh provider problem statements left off the list right now, by reason: `stale_incidents`, `stale_update`, `no_update_time`, `not_a_wait`, `feed_not_shown`, `window_blind`).
- `legend`, `note`: fixed text. A host missing from the list is not known to be working.
- Never in this file: refused reads (401, 403, 429, 503), agent reports, lookup counts or who looked a host up.

## Agent platform policies (`GET /v1/platforms`)

`GET /v1/platforms` (JSON, `schema_version` `ahn-platforms/1`) and the pages `/en/platforms`, `/ko/platforms` show what each agent product's own vendor writes on its public help pages about the sites the product limits, the steps it asks a person to approve, and how it identifies itself (D107). It takes no parameters, reads nothing from the request, and makes no outside request.

- `notice`: fixed text. These are the vendors' words; AHN does not judge whether a site falls under any description, does not know unpublished lists, and has not tested the products.
- `platforms[]`: `platform` (`claude_in_chrome`, `claude_desktop_browser`, `chatgpt_agent`, `gemini`, `meta_muse`, `perplexity_comet`), `display_name`, `vendor`, `coverage` (`documented` when at least one page was read, else `unread`), `docs[]`, and `no_official_documentation_found[]` (topics the vendor has published nothing on, e.g. which sites Muse limits).
- `docs[]`: `surface`, `url` (an https page on the vendor's own domain), `title`, `status`. `read`: `verified_at` (the day AHN read it) and `quotes[]` of `{tag, text}` (verbatim, at most 200 characters; tags `blocked_category`, `site_side` (a restriction the vendor says the website sets, not the product), `confirm_required`, `admin_policy`, `banner_text`, `remedy`, `list_incomplete` (the vendor's notice that its list may be incomplete), `identity`, `prohibited_action`, `capability_note`, `change_note`). `unread`: `unread_reason` (`http_403`, `challenge_page`, `script_rendered`, `not_read_this_round`) and `last_attempt_at`, no quotes; AHN does not retry such a page another way. Optional: `conflict` with `conflict_peer_url` (two official pages of one product that differ; both are shown), `admin_deployment_doc` (written for managed deployments), `note_code` and `note`.
- A page last read more than 90 days ago is listed as `unread` with `not_read_this_round` and without quotes. Absent fields are left out, never null.
- Nothing here changes `recommendation`, `next_checks`, `next_action` or `summary_line` of a lookup, and the MCP tools are unchanged.

## Explain a blocked step (`GET /v1/why`)

`GET /v1/why` (JSON, `schema_version` `ahn-why/1`) answers one question for an agent whose authorized step is blocked: which layer to look at first, whether a person has to act, and what other agents saw (D108). It runs one lookup (the same code path as `GET /v1/incidents/check`, window 168 hours, no result token; the `server` field is the same as a `GET /v1/incidents/check` request with `window_hours=168` and the same codes) and adds fixed sentences chosen from your codes and from records AHN already holds. It does not judge any site, does not tell anyone how to get past a block, and makes no outside request while it answers. `HEAD` is not answered, as for the lookup.

Parameters. Only `site_host` can make a request fail (400 `invalid_site_host`); a pasted address is cut to its host (`host_normalized` `path_dropped`), a subdomain is answered from its registered domain (`apex`). Every other value that is not on its list is ignored and never repeated.

- `site_host`, `lang` (`en`, `ko`; anything else reads as `en`).
- The lookup's own codes, as for the lookup: `error_class`, `failure_stage`, `task_step`, `http_status`, `challenge`, `retry_after`, `via`, `agent_vendor`, `ahn_test`. A code you measured wins over the one chosen from `stop_point`. With `task_step=status_check` the answer stays a status check: the status page check (else the server's own action) comes first in `do_now`, and `server` is the lookup's answer for the same step (D110).
- What happened, chosen from fixed lists (none of it is counted or stored): `agent_platform` (`claude_desktop_browser`, `claude_in_chrome`, `claude_code`, `chatgpt_agent`, `meta_muse`, `gemini`, `perplexity_comet`, `other`), `agent_env` (`cloud_browser`, `on_device_browser`, `not_sure`), `external_browser` (`yes_same_account`, `no`, `not_tried`), `stop_point` (`before_visit`, `page_blank_or_blocked`, `human_verification`, `company_login`, `site_login`, `after_login_action_fails`, `tools_off_page_visible`, `timeout_or_5xx`, `extra_verification`, `not_sure`), `screen_message` (11 kinds, e.g. `access_denied`, `human_check`, `sign_in_required`, `approval_on_other_device`), `since_kind` (`today_first`, `worked_before`, `not_sure`), `since_date` (with `worked_before` only, `YYYY-MM-DD`, at most 90 days back; it only chooses the period of recorded changes shown), `task_context` (`my_account_consumer`, `my_account_work`, `public_read`, `other`).

Answer. Absent fields are left out, never null (the exception is `server`, which is the lookup's own answer copied as it is).

- `input_echo`: every accepted input (the lookup's codes and the choices), and only those.
- `where_to_look`: `first` (`site`, `platform`, `account`, `agent_env`, `task` or `unknown`), `layers` (the state of each: `evidence`, `your_answer`, `background`, `not_seen`, `not_reviewed`, `no_doc`, `unread`) and one fixed sentence. `first` is the first layer in the final order whose state is `evidence` or `your_answer`. Order only says where to look first; it is not a finding. The caller's stop leads (D110): `before_visit` and `tools_off_page_visible` make the platform layer `your_answer` and put it ahead of the site; `extra_verification`, `site_login`, `company_login` and `after_login_action_fails` put the account layer ahead of the site. The site goes ahead of such a stop only on direct evidence (a stored cause, a robots.txt refusal of the agent's token, or a provider incident); a change in AHN's own home-page check never does.
- `person`: `needed` (`yes`, `not_indicated`), `reasons[]` with `code` (`sign_in_is_the_account_holders`, `verification_on_person_device`, `approval_is_the_persons_decision`, `company_it_decides`, `platform_admin_decides`, `platform_refused_step`, `server_hand_off`, `page_visible_tools_off`, `check_needs_person`) and `who[]` (`user`, `it_admin`, `platform_admin`, `site_support`). `tools_off_page_visible` always gives `needed` `yes` with `who` `user`. When a `do_now` check is one only a person can take (`who` `person`), `needed` is `yes` (`check_needs_person` when no other reason applies). `not_indicated` means AHN's records do not show that a person is needed; it is not a statement that none is.
- `others_saw`: reports from the last 7 days that match the host (at most 5, each with `verified: false`), a coarse `lookup_band`, and one sentence. Absence of reports proves nothing.
- `server`: `summary_line`, `recommendation`, `next_action`, `cause`, `failure_stage`, `next_checks` exactly as `GET /v1/incidents/check` gives them for the same codes, and `position` (`first`, or `after_checks` when the lookup says to continue and the explanation's checks come first). With `lang=ko`, `server_note` (a fixed Korean sentence) says that `server.summary_line` is the lookup's own English text.
- `what_happened`: `layers[]` (at most 10 rows: `layer` `L1`, `L1a`-`L1e`, `L2`, `L3a`, `L3b`, `L4`; `state`; `template_id`; `text`; optional `source` with `kind`, `url`, `checked_at`) and `unknowns[]` (what AHN cannot see).
- `do_now.checks[]` (1 to 6): `id`, `who` (`person`, `agent`, `it_admin`, `platform_admin`), `text`, optional `url`.
- `timeline`: `window_from`, `window_to`, `items[]` (recorded changes of the host's declared policy, of AHN's own home-page read, and of a platform's public documentation; a home-page change is said as what AHN's request got ("AHN's home-page check started getting a X challenge"), never as a change the site made, and a value that came, went and came back in the period adds a sentence that AHN's check results wavered; `at`, `layer`, `kind`, `text`, optional `source_url`) and `limits_text`.
- `handoff[]` (1 or 2): a ready sentence for the person who can decide; without `stop_point`, the stop it names comes from `error_class` or `failure_stage` (`site_access`, `human_verification`, `service_error`, `before_target_response`, `login_auth`), and "an unclear step" only when neither names one (`to`: `it_admin`, `platform_admin`, `platform_vendor`, `site_support`, `user`).
- `rules_applied`, `render_order`, `basis_text`, `links.self` (the request again with the accepted codes only).

Fixed sentences. Every text is chosen from a fixed English or Korean template; blanks are filled only from AHN's records or fixed phrase tables. A text that would not fit its limit is left out, never cut. The templates avoid asserting a cause, advising a workaround, or saying that a site falls under a category.

- The pages `/en/why` and `/ko/why` are a form for this endpoint: one hostname field and fixed lists, no free text. The browser cuts a pasted address to its hostname (and a tenant or account subdomain to its registered domain, with the same tables the service uses) before it sends anything, then calls `GET /v1/why` and shows the answer's own sentences unchanged, with the lookup's `summary_line` labelled as given. Asking again keeps the previous answer on the page for comparison; each asking is one lookup.
- Reads: one lookup, then one short transaction (lock timeout 200 ms, one savepoint per read) over `host_access_changes` and `platform_doc_events`. If a read fails, that section is empty.
- Counts like one lookup; the choices above are not counted, stored or logged; no `feedback_token` is issued. Nothing here changes `recommendation`, `next_checks`, `next_action` or `summary_line` of a lookup (tests compare the two answers byte for byte), and the MCP tool definitions are unchanged (a failed `check_incident` call gets the one extra text line described above).
