# 발견 경로와 초기 데이터 확보 계획

작성일: 2026-10-03. 현재 공개 베타에서는 확인된 공식 상태 출처를 조회하고, MCP Registry 등록과 OpenAI·Muse 심사 신청을 진행했다. 실제 사이트를 직접 자동 시험하지는 않는다. 최신 후보 출처 파일럿은 별도 기록(비공개 운영 기록)에 둔다.

## 사용자가 서비스를 발견하는 경로

1. **플랫폼 디렉터리:** OpenAI 플러그인 및 Muse 커넥터의 제출·심사를 통과하면 해당 플랫폼에서 검색·연결할 수 있는 경로가 생긴다. 등록과 실제 추천·사용은 별개의 사건이다. [OpenAI 제출 안내](https://developers.openai.com/plugins/deploy/submission), [Muse Connector Platform](https://muse.ai/platform).
2. **웹 검색과 직접 링크:** 영어 중심의 사용 상황 페이지, 연결 안내, 공개된 사건 페이지를 검색하거나 프로젝트 문서의 링크로 방문한다. 한국어 화면도 제공한다. 실제 승인된 관찰이 없으면 사건 페이지를 만들어내지 않는다.
3. **사용자 연결 후 에이전트 호출:** 연결 건수와 실제 조회 호출 건수를 분리한다. 설치만으로 작업 중 자동 호출이 보장되지 않는다.
4. **에이전트의 웹 검색:** 검색 가능한 영어 [에이전트용 안내](/en/agents)에서 목적·읽기 API·응답 해석·연결 경로를 제공한다. 웹을 읽을 수 있는 에이전트는 공개된 읽기 정보와 출처를 참고할 수 있다. 웹 검색 결과만으로 플러그인 설치나 쓰기 도구 호출이 허용되는 것은 아니다. OpenAI는 공개 플러그인의 기본 발견 경로를 직접 링크·이름 검색으로 설명하고, 능동 추천은 일부에 한정한다([공식 안내](https://developers.openai.com/plugins/deploy/app-review)).

개인별 추적 없이 페이지 요청, 연결 안내 열람, 도구 조회를 집계할 수는 있지만 이를 동일한 사람의 전환율로 부르지 않는다. 디렉터리가 설치·활성화 통계를 제공하지 않으면 그 구간은 `측정 불가`로 기록한다.

## 콜드스타트의 데이터 계층

| 계층 | 수집 방식 | 공개 표시 | 주장할 수 있는 범위 |
| --- | --- | --- | --- |
| 조회 수요 | 서비스에 들어온 정규화된 호스트·오류 유형별 조회 횟수 | 운영자 집계만 | 무엇을 찾는지. 장애 발생 여부는 알 수 없음 |
| 공식 상태 발표 | 서비스 운영자의 공개 상태 API·페이지에서 확인한 발표 | 출처 URL, 원문 발표 시각, 최종 확인 시각과 함께 별도 표시 | 운영자가 발표한 범위의 상태 |
| 제한적 자동 관측 | 명시적으로 허용된 공개 경로의 저빈도 시험 | `자동 시험 관측`, 경로 범주·지역/환경·시각·결과를 별도 표시 | 그 시험 환경의 그 요청 결과 |
| 에이전트 직접 관찰 | 실제 작업 중 에이전트 자신의 권한 규칙에 따라 공유한 비식별 구조화 관찰 | 검토 후 `미검증 직접 관찰` | 특정 시도의 결과. 제출 권한·원인·전면 장애를 서버가 보증하지 않음 |

모든 계층은 원천과 신뢰 수준을 별도 저장한다. 공식 발표나 봇 시험을 `observations`의 사람/에이전트 제보 건수 또는 독립 제보자 수에 합산하지 않는다. 공식 발표의 `operational`도 에이전트 로그인·인증 경로의 성공을 뜻하지 않는다. 무자료 응답은 계속 `상태 미상`이다.

## 외부 자동 수집의 허용 범위와 중단 규칙

**공식 공개 상태 API**만 업체 발표로 검토한다. 예를 들어 Statuspage는 페이지별 공개 상태 API를 제공한다([Atlassian Status API 설명](https://support.atlassian.com/statuspage/docs/what-are-the-different-apis-under-statuspage/)). Statusphere 목록과 Tranco 순위의 로컬 교집합은 검증 전 후보(비공개 운영 기록)를 찾는 데만 쓰며, 운영 DB의 조회 목록이나 공식 상태 근거로 올리지 않는다. 공급자가 밝힌 사용 조건·속도 제한·출처 표시 요구를 확인하고, 허용 목록에 개별 등록한 뒤에만 수집한다. 실제 조회 수요가 높은 서비스부터 후보를 검토하되 수요 자체를 장애의 증거로 쓰지 않는다.

사이트 자체를 시험하는 기능은 운영자 동의 또는 공개된 점검 허용 근거와 명확한 목적이 있는 경로로 한정한다. `robots.txt` 규칙([RFC 9309](https://www.rfc-editor.org/rfc/rfc9309.html))과 사이트 정책을 확인한다. 고정된 낮은 빈도, 식별 가능한 User-Agent·연락처, 시간 제한, 실패 시 지수 백오프, 수신 거부와 즉시 중단 수단을 둔다. 로그인, 결제, 개인정보 입력, CAPTCHA 해결·우회, 상태 변경 요청은 수행하지 않는다. 403·429·보안 도전이 나오면 재시도 폭주 없이 멈추고 원인을 확정하지 않는다. 보안 도전은 자동 접속에 선별 적용될 수 있다([Cloudflare 도전 방식](https://developers.cloudflare.com/cloudflare-challenges/concepts/how-challenges-work/)).

자동 시험의 결과는 `정상/장애` 전체 판정으로 승격하지 않는다. 최소 2회 이상의 시간 분리와 다른 증거가 있더라도 해당 경로·환경의 관측으로만 설명한다. 공개 전에는 데이터 보존 기간, 수집 중단 절차, 공급자별 귀속, 오류 정정·삭제 절차를 확정한다.

## 구현 순서

1. 로컬 MVP의 실제 제보·조회·검토·통계 흐름을 완성한다.
2. 출처 유형과 시각·근거 URL을 가진 별도 `external_status_signals` 설계를 검토한다. `observations`와 분리한다.
3. 공식 상태 API 공급자 1곳을 수동으로 검증하고, 가상 데이터로 파서·표시·만료 시험을 한다.
4. 수집 조건과 운영 비용을 검토한 뒤 허용 목록 기반 읽기 전용 수집기를 도입한다.
5. 자동 사이트 점검은 운영자 동의를 얻은 소수 대상에서만 실험하고, 사용자 승인 관찰과 일치·불일치를 분석한다.

검수에서는 공급자 API 장애가 우리 API 응답을 막지 않는지, 오래된 외부 발표가 현재 상태로 표시되지 않는지, 봇 결과가 실제 제보자 수를 늘리지 않는지 확인한다.
