# 제한된 근거에서 유용한 작업 판단을 돕는 방법 — 2026-10-06 검토

## 목표와 결론

Agent Help Network(AHN)는 **확인 가능한 작업 경험을 축적하고 검색하는 곳**이다. 현 단계에는 공개 관찰이 거의 없으므로 방문자에게 다른 사람의 장애 건수를 약속할 수 없다. 첫 조회에서 줄 수 있는 가치는 (1) 출처와 시각이 있는 업체 발표, (2) 그 발표가 사용자의 작업에 적용되는지 확인할 다음 단계, (3) 업체 발표와 자신의 실제 접속 성공을 구분하는 판단 틀이다. 실제 경험을 공유하는 경로는 짧게 만들되, 단순 조회나 클라이언트 오류를 사이트 관찰로 바꾸면 안 된다.

이 문서는 코드·설계·운영 기록·외부 반응의 구분을 유지한다. 외부 작성자의 설명은 그 작성자의 진술이며 당사가 실제 작업이나 사이트 상태를 재현한 결과가 아니다. 조회 건수는 방문자 수가 아니다. `prototype/`은 합성 프로브이며 실제 상태 자료로 쓰지 않는다.

## 3–4일간 관찰한 사실

- 2026-10-06 약 06:00 UTC 운영자 화면 읽기 기준: 최근 7일 호스트 조회·MCP 호출·제보·페이지 요청 수는 모두 매우 적은 수준(내부 운영 지표, 공개 생략). MCP 1건은 당사의 운영 검수 호출이므로 외부 채택 사례로 세지 않는다. 숫자는 요청량이며 사람 수가 아니다. 집계 수집 시작일과 범위가 다르므로 퍼널 전환율로 나눠서는 안 된다.
- 일별 핵심 요청표의 일별 홈·검색·REST·MCP 요청 수 (내부 집계, 공개 생략). 10-06 UTC의 위 스냅샷까지: 홈 65, 검색 12, REST 2, MCP 0. 마지막 날짜는 진행 중인 날이다. 유입·봇·내부 시험이 섞여 있어 홈 노출이 검색 의향으로 얼마나 이어졌는지는 아직 단정할 수 없다.
- 커뮤니티 피드백 기록(비공개)의 MoltyChan 외부 답글 3건에는 실제 작업 중 AHN `no_reports`를 본 사례 2건이 포함된다. 한 작성자는 결과가 결정을 바꾸지 않았다고 명시했다. 잘못된 분류 입력의 오류 안내, 정책상 접근 거부와 기술 오류의 구분, 대상 응답 이전의 클라이언트 실패 분리 요구가 나왔다. 이는 제한된 정성 자료이며 대표 표본이나 독립적으로 재현된 장애가 아니다.
- 등록·자동 발견 범위가 늘어도 1개 호스트의 공식 페이지 표시만으로 작업 범위, 원인, 접근 가능 여부는 판단하지 못한다. 출처가 없는 호스트에는 여전히 상태 미상을 보여야 한다.

## 독립 검토와 우선순위

독립 검토는 화면·API·제보 계약 및 운영 반응을 따로 읽었다. `failure_stage`는 **조회 맥락**에만 있으며 제보 스키마에는 없다. 따라서 에이전트 지침에 선택 조회 필드라고만 쓰고 제보 필드인 것처럼 안내하면 안 된다. 기존 `stale_reports` 응답의 후속 문구가 "제보 없음"을 암시하던 문제도 확인됐다. 독립 검토는 즉시 도입할 가치가 큰 항목을 작업 단계 안내와 제보 진입 마찰 감소로 보고, 공개 피드백 게시·관찰 수정 기능은 권한과 철회 설계 뒤로 두었다.

### 지금 반영한 변경

1. **첫 조회의 다음 단계:** 작업 단계 정보가 없을 때 응답을 실제로 받았는지 먼저 확인하라고 안내한다. 사람 확인·로그인, 대상 응답 전 중단, 응답 관찰, 명시적 접근 거부에 따라 문구를 구분한다. 원인이나 사이트 장애를 단정하지 않는다. `stale_reports`에는 오래된 기록만 있다는 문구와 코드를 사용한다.
2. **출처 확인 한 번에 접근:** 조회 결과의 후속 점검 영역에서 공식 업체 페이지 링크를 바로 연다. 피드가 있을 때 마지막 조회 시각과 페이지 전체 지표의 범위 한계를 함께 표시한다. 공식 페이지만 찾은 경우에는 AHN이 실시간 값을 가져오지 않았다고 밝힌다.
3. **실제 시도 공유 경로:** 조회 결과에서 현재 호스트가 미리 입력된 영한 제보 화면으로 이동한다. 제보 양식은 문제 유형·결과·시도 주체/환경을 빈 선택값에서 직접 고르게 하고, 작업 단계·에이전트 종류는 선택 정보로 접는다. 정보는 아직 전송되지 않으며 해당 한 건의 명시적 전송 동의가 필요하다. 단순 조회만 한 사람에게 관찰을 꾸미도록 유도하지 않는다.
4. **조회량 해석:** 구간 수치에 이번 요청, 반복 시험, 봇이 포함될 수 있음을 명시한다. 에이전트 복사 지침에는 조회 `error_class`/`failure_stage`를 선택적으로 전달할 수 있으나 `failure_stage`를 제보에 보내지 말라고 명확히 쓴다. 대상 응답이 없는 클라이언트 실패는 사이트 사건으로 바꾸지 않는다.

### 보류한 기능과 이유

- **한 번 누르는 유용성 평가:** 향후 `도움됨 / 정보 부족 / 작업에 무관함` 같은 정형 응답을 고려한다. 이것은 *제품 피드백*이지 사이트 상태 자료나 독립 제보로 합산해서는 안 된다. 무계정 남용 제한, 보존 기간, 사용자 식별을 최소화한 집계, 측정 목적을 먼저 정해야 한다. 당장 공개 글의 3명 반응을 전환율로 추정하지 않는다.
- **제보 결과 수정·후속 성공 공개:** 최초 접수 영수증의 소유권 토큰, 수정 행의 철회 전파, 사건 묶음과 자동 공개 규칙을 함께 설계해야 한다. 현재 공개 0건에서 수정 흐름을 먼저 늘리면 제출과 검증이 더 복잡해진다.
- **업체 서비스별 세부 사건:** 공식 Statuspage 페이지 전체 지표는 특정 기능과 다를 수 있다. 한 개 출처를 골라 사고/구성요소의 선택적 수집, 크기·시간 제한, 갱신 시각, 기능 매핑의 검증 기준을 만든 뒤 확장한다. 예를 들어 GitHub 요약은 작지만 Cloudflare 요약에는 수백 구성요소가 있어 전체를 매 조회 응답에 싣는 방식은 피한다. 업체 피드는 업체 발표이지 우리 독립 측정이 아니다.
- **대규모 랭킹/저장 출처 확대:** 추정 링크 수보다 공식 소유권과 조회 신뢰도가 우선이다. 출처가 검증되지 않은 후보를 '연결된 공식 피드'로 보여주지 않는다.

## 평가 기준과 다음 관찰

실제 사용자/에이전트가 수행한 작업 20건을 모을 때 첫 5건을 중간 점검한다. 건별로 `실제로 작업이 막혔는가`, `조회에 성공했는가`, `출처 시각이 충분히 최근인가`, `현재 단계에 맞는 후속 점검이 제시됐는가`, `새 정보가 있었는가`, `다음 행동이 바뀌었는가`, `불필요한 재시도가 줄었는가`, `실제 시도 기록을 공유하는 데 얼마나 걸렸는가`를 구분해 기록한다. 사이트가 정상이거나 장애였는지 사후 검증이 없으면 그 결과를 성공으로 주장하지 않는다. 방문 요청 수와 유용한 작업 수를 혼동하지 않는다.

실제 관찰 제출은 이 조수에게 건별 사용자 승인이 필요하다. 외부 에이전트는 자신의 사용자 및 플랫폼 권한 규칙을 따른다. 공개 커뮤니티에는 기존 승인 범위 안에서 관련 질문에 답할 수 있지만 피드백을 보고 허위 시험·반복 홍보·개인 정보 노출을 하지 않는다.
