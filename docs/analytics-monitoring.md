# 베타 통계와 운영 모니터링 설계

작성일: 2026-10-03. [GOV.UK 서비스 지표 안내](https://www.gov.uk/service-manual/measuring-success/using-data-to-improve-your-service-an-introduction)는 성능 측정값의 정의와 분모를 명확히 하도록 안내한다. 여기서는 방문자 개인을 추적하기보다 제품 질문에 답할 수 있는 최소 집계를 우선한다.

## 답하려는 질문

1. 어떤 호스트·문제 유형의 정보가 필요한가? → `lookup_metrics`의 일별 조회 합계.
2. 조회 결과가 있는가? → `no_reports`, 단일, 복수, 후속 성공 응답의 일별 건수.
3. 제보가 쌓이고 수정되는가? → 제출·후속 결과·철회·숨김 건수와 검토 상태.
4. 연결/사용 중 오류가 많은가? → API 경로별 상태 코드 범주, 응답 시간 버킷, 서비스 가용성.
5. 실제로 도움이 되는가? → 향후 선택적 구조화 피드백의 “도움 됨/안 됨”과 “다음 행동 변경” 응답. 응답자가 없으면 효과를 추정하지 않는다.

## 저장 원칙

- 조회 수요는 `day + site_host + error_class`의 합계로 저장한다. 작업 단계, IP, 쿠키, 개인 URL, 원문 대화는 넣지 않는다. 조회 횟수는 방문자 수나 장애 건수가 아니다.
- 실제 조회된 공유 가능한 공개 루트 호스트만 `queried_hosts`에 최초·최근 조회 시각과 공식 Statuspage 발견 마지막 시도 시각을 유지한다. 10,000개 상한을 두고 검증된 고정 출처는 예외로 등록한다. 임의 하위 도메인은 제외한다. 현재 자동 삭제 기한은 없으며 일별 조회 집계도 보존 기간을 추후 정해야 한다.
- 서비스 성능은 `day + 정규화된 경로 + 상태 코드 범주 + 지연 버킷`의 합계로 저장한다. 경로에는 사건 UUID나 호스트를 포함하지 않는다. p95는 정확한 원시 분포가 아닌 버킷 근사치임을 표시한다.
- MCP `check_incident`의 **성공한 도구 실행**은 중앙 API가 공유 비밀에서 파생한 내부 표식을 확인한 뒤 `day + evidence_level + provider_signal`로 별도 집계한다. 표에는 호스트명·IP·클라이언트 키를 넣지 않고 90일 뒤 삭제한다. 표식 없는 REST 조회와 `/mcp` HTTP 연결 요청은 이 집계에 포함하지 않는다. 도구 호출 오류와 앱이 실제로 사용자의 작업을 바꿨는지는 아직 측정하지 못한다. 운영자 시험 호출도 포함된다.
- 제보 품질은 기존 `observations`와 `audit_events`에서 집계한다. 출처 수는 토큰 수일 뿐 독립 사람 수가 아니다.
- 데이터베이스 장애로 통계 쓰기에 실패하더라도 서비스의 핵심 읽기 응답을 잘못 바꾸지 않는다. 통계 누락을 운영 화면에 표시한다.
- 정책 화면에 수집 항목과 목적을 설명하고, 실제 공개 전에 보존 기간을 확정한다.

## 유입과 클라이언트 집계 (2026-10-04 추가)

- 공개 웹 요청에서 허용된 `utm_source`(MoltyChan, Get Posting Board, CAMPFIRE, Agentboard.ai, OpenAI, Muse, Google, Bing), `utm_medium`, `utm_campaign`과 알려진 Referrer **도메인 범주**만 일별로 집계한다. 전체 URL·검색어·임의 태그값은 저장하지 않는다. 분류에 없는 값은 `other` 범주로 합친다. 태그는 요청자가 붙일 수 있으므로 게시물에 기인한 실제 사용자 수나 전환으로 해석하지 않는다.
- 2026-10-05 이후 CAMPFIRE(`campfire`)와 Agentboard.ai(`agentboard`)도 허용된 유입 출처 범주에 넣는다. 기존 링크에 태그가 없으면 Referrer가 전달된 요청에만 적용되며 과거 방문을 복원할 수 없다.
- Render 경계가 전달한 주소가 `/owner` 허용 목록과 일치하면 유입 출처 대신 `owner_network`로 집계한다. 이는 운영자 시험을 다른 트래픽에서 **부분적으로 분리**하기 위한 네트워크 범주이며 해당 주소를 DB에 저장하지 않는다. 집 인터넷의 실제 사용·공유 사용자도 포함될 수 있고, 집 밖에서 한 운영 시험은 포함되지 않는다. 이전 기록은 소급 분류할 수 없다.
- User-Agent 원문은 저장하지 않고 `browser_hint`, `agent_or_script_hint`, `crawler_hint`, `unknown`으로 분류한다. 이는 쉽게 바뀌므로 사람과 에이전트의 검증된 구분이 아니다.
- Render의 공개 웹 경계에서 `CF-Connecting-IP`가 전달될 때만 주소를 비밀키 HMAC으로 날짜별 변환해 일별 요청 수를 센다. 원 IP와 변환 전 헤더를 DB/앱 로그에 저장하지 않고, `X-Forwarded-For`를 분석 식별자로 신뢰하지 않는다. 동일 주소가 공유 프록시일 수 있고 한 사람이 여러 주소를 쓸 수 있으므로 `클라이언트 키`는 방문자 수가 아니다. 14일 뒤 삭제한다. 키가 없으면 결측으로 둔다.
- 유입 범주 집계는 90일 뒤 삭제한다. 홈페이지·검색 결과 등에 UTM이 없는 후속 요청은 같은 방문의 유입 출처로 연결하지 않는다. 쿠키나 브라우저 세션 추적은 추가하지 않는다.
- 운영자 `/owner`와 `/health`는 유입 집계에서 제외한다. 기존 집계와 마찬가지로 앱에서 처리한 요청만 센다. Render 엣지에서 차단한 요청은 앱 집계와 다를 수 있다.
- 이미 기록된 요청의 과거 UTM·Referrer·User-Agent·IP는 복구하지 못한다. MoltyChan·Get Posting Board의 기존 링크에는 추적 태그가 없으므로 기존 유입 효과도 확정할 수 없다. 향후 링크에는 예를 들어 `?utm_source=moltychan&utm_medium=community&utm_campaign=beta_launch`를 붙일 수 있다.

## 운영자 전용 화면

로컬 모니터는 `127.0.0.1`에만 바인딩한다. 호스팅 운영 모니터 `/owner`는 Render가 생성한 별도 256비트 비밀값의 HTTP Basic 인증과 HTTPS로 보호한다. 검색 엔진에는 노출하지 않고 캐시도 금지한다. 주요 카드: 오늘/7일 조회, 페이지 조회(고유 방문자 아님), 제보, 공개/검토/숨김/철회, 오류 비율, 응답 시간, Render 웹 서비스의 월 누적 대역폭 측정치. 보류 사유와 최근 20건의 비민감 구조화 필드를 볼 수 있다. 원문 제보와 비밀값은 표시하지 않는다. 운영자 수동 조치는 CLI에서 실행하고 기록한다.

`AHN_OWNER_ALLOWED_IPS`에 쉼표로 구분한 개별 공인 IP를 설정하면 `/owner`는 Render 경계가 덮어쓴 `CF-Connecting-IP`가 목록에 있을 때만 비밀번호 창 없이 열린다. 이 모드에서는 다른 IP와 헤더가 없는 요청을 404로 거절하며 기존 Basic 비밀번호도 우회 경로가 되지 않는다. 변수를 비우면 기존 Basic 인증으로 돌아간다. 집 공인 IP가 바뀌면 Render 환경 변수에서 허용 목록을 갱신해야 한다. 사설 LAN 주소를 넣거나 광범위한 CIDR 범위를 허용하지 않는다. 이 설정은 공개 사이트·API·MCP에는 적용되지 않는다.

Render 대역폭 API의 시간별 지표는 약 60분 늦고 Hobby에서 최근 7일만 제공한다. 독립 Cron Job이 시간별 값을 DB에 저장해 월 누적치를 만든다. 이는 웹 서비스 지표이며 워크스페이스 전체 청구서 합계가 아니다. 검사 누락이 6일을 넘으면 스크립트를 실패 처리해 운영자가 Render Billing을 직접 확인해야 한다. 10 GB 경고와 20 GB 웹 서비스 중단은 사전 대응이며 정확한 청구 상한이 아니다.

같은 시간별 Cron Job은 Render API의 웹 서비스 CPU, 메모리, HTTP 요청 수 최신 측정치도 가져와 `render_metric_samples`에 최대 90일 저장한다. 최신 4시간 표본이 없으면 `—`로 표시한다. HTTP 요청 수는 Render 엣지 집계이고 앱의 `request_metrics`와 측정 범위가 다르다. DB 현재 크기와 연결 수는 PostgreSQL에서 직접 읽는다. Render API 키는 기존 Cron Job에만 두고 공개 웹 서비스에 추가하지 않는다. 지표 수집 실패가 대역폭 안전장치를 무력화해서는 안 된다.

Render 자체 대시보드는 HTTP 요청량·상태 코드, CPU·메모리, 외부 전송량, DB 활동을 제공한다. Pro 이상에서 개별 HTTP 요청 로그와 응답 시간 백분위수, 외부 메트릭 스트림을 사용할 수 있다. 현재 Hobby 환경에서는 개별 Render HTTP 요청 로그를 기대하지 않는다. 기본 로그·지표 보존은 Hobby 7일, Pro 14일, Scale/Enterprise 30일이며 요금제 변경으로 이미 만료된 과거 로그가 돌아오지 않는다. [Render 로그](https://render.com/docs/logging), [서비스 지표](https://render.com/docs/service-metrics), [플랜별 기능](https://render.com/docs/platform-features-by-plan), [Render API](https://render.com/docs/api).

## 접근 프로필 시드 선읽기 (2026-10-18 추가)

시드 선읽기: 크론이 5분마다 최대 10개(`AHN_WARM_BATCH`), 호스트별 주 1회 재읽기. 시드 목록 = `ahn/seed_hosts.txt`. 크론 로그의 `profile_warm read=.. ok=.. errors=.. remaining=..` 줄과 `/owner` 의 "접근 프로필 캐시 상태" 집계가 진행 증거이며, 목록 전체(약 1,100개)를 한 바퀴 읽는 데 약 10시간이 걸린다. 조회되지 않은 호스트도 읽으므로 공개 정책 화면에 그 사실을 밝힌다.

## 해석과 개선 주기

방문→연결→조회는 개인별 추적이 없으면 정확한 전환율이 아니다. 각 단계의 **집계량**으로 보여주고 같은 사람의 여정이라고 주장하지 않는다. 주 1회 조회 수요와 제보 부족 영역, 오류 증가, 허위·중복 제보, 영한 화면의 빈 결과를 살펴 개선 항목을 기록한다. 조회가 많아도 실제 관찰이 없다면 “정보 수요는 있으나 증거 부족”으로 처리한다.

운영 화면의 일별 핵심 활동은 홈·검색 결과·REST 조회 요청과 실제 성공한 MCP 도구 실행을 별도로 표시한다. 앞 세 열은 유입 계측이 시작된 뒤의 2xx 요청만 포함하며, MCP 열은 별도 도구 집계다. `owner_network` 열은 홈·검색·REST 중 허용 네트워크의 요청만 표시한다. 열을 순서대로 나눈 값은 전환율이 아니다. 4xx와 5xx는 합계 외에 서버 오류 5xx를 별도로 보아 실제 장애와 잘못된 입력·탐색 요청을 혼동하지 않는다.

## 검수 기준

- 조회 2회가 `lookup_metrics.checks=2`가 되어도 관찰/사건 수는 증가하지 않는다.
- REST GET만으로 MCP 도구 실행 수가 늘지 않고, 올바른 내부 표식을 실은 성공한 조회만 증가한다. 임의 표식은 무시한다.
- 합성 시험 요청과 실제 공개 요청을 통계에서 구분하거나 시험 통계를 배포 전 초기화한다.
- 운영 화면은 로컬에서는 루프백 주소에서만 접근하고, 호스팅 `/owner`에서는 별도 비밀번호 없이는 통계를 반환하지 않는다. 실제 호스팅 비밀번호 로그인은 별도 검수한다.
- 지표 표에 정의와 한계를 표시한다. 0건과 수집 실패를 혼동하지 않는다.
- 지표 수집이 실패해도 API의 조회·제보 무결성은 유지된다.
